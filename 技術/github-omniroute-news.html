OmniRoute 開源：一個端點打通 375 個 AI 供應商

2026年10月23日 04:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/cheaper-inference/OmniRoute

OmniRoute 是 2026 年 2 月建立的開源 AI 閘道專案，在 GitHub 累積 79,690 顆星標與 11,597 個分支，主要語言為 TypeScript，採 MIT 授權。它把 375 個模型供應商收進同一個本機端點，開發者只要把工具指向 http://localhost:20128/v1，即可在 Claude Code、Codex、Cursor、Cline 與 Copilot 等客戶端之間共用同一套憑證、路由與額度管理。

這個專案切入的痛點相當具體。多數團隊在同時使用三至五家模型供應商之後，會遇到三類反覆出現的問題：各家 SDK 與認證方式不同、免費額度分散在十幾個後台無人查看、以及單一供應商限流時整個工作流程中斷。OmniRoute 的答案是把這些差異全部收斂到一個 OpenAI 相容介面之後，讓上層工具完全不需要知道下游換了哪一家。

OmniRoute 是什麼？

OmniRoute 是 MIT 授權的開源 AI 閘道，以單一 OpenAI 相容端點連接 375 個供應商，內建容錯路由、權杖壓縮與本機憑證管理。

專案自我定位為「免費 AI 閘道」，核心主張是讓開發者不再因為額度、限流或帳單而中斷編碼流程。它在本機執行，控制平面同樣留在使用者自己的機器上，提示內容只會送往當次請求所選定的上游供應商，專案本身不加入額外的託管轉發層，遙測預設關閉，憑證以 AES-256-GCM 加密保存。

與單純的代理伺服器不同，OmniRoute 在轉發之外還包含路由決策、壓縮、快取、記憶體、護欄與審計等模組。這些模組可以獨立開關，也可以按不同路由組合分別設定，形成一層介於客戶端與供應商之間的中介層。這種設計讓它更接近一個可程式化的控制平面，而非一個只做位址轉換的通道。

OmniRoute 的項目背景與維護狀況如何？

專案於 2026 年 2 月建立，由開發者 diegosouzapw 主導，八個月內累積 79,690 顆星標，貢獻者超過八百人，推送紀錄與本文取材同日。

倉庫建立至今約八個月，星標成長速度在基礎設施類開源專案中屬於異常。分支數達 11,597，星標與分支比例約七比一，顯示相當比例的使用者不只是收藏，而是實際複製程式碼並在其上調整設定。貢獻者端點的分頁資訊顯示參與人數超過八百，與 README 所稱的九百餘位貢獻者大致吻合，這種分散程度在單一維護者主導的專案中並不常見。

維護節奏同樣密集。倉庫最近一次推送時間為 2026 年 10 月 22 日，與本文取材同日；版本線已推進至 v3.8.53 之後，並公布通往 v3.9.0 長期支援版本的藍圖。專案同時發佈 npm 套件、Docker 映像與 Electron 桌面版，並在文件中列出七千八百餘個受追蹤的測試檔案，試圖以測試規模回應外界對其穩定性的疑慮。

OmniRoute 如何處理供應商故障與限流？

它採三層獨立容錯：供應商層的斷路器、連線層的冷卻與指數退避、模型層的單模型鎖定。任一層失敗只影響對應範圍，其餘健康目標繼續服務。

第一層是供應商斷路器，作用範圍為整個供應商。它只在接收到 408 或 5xx 回應時跳脫，不同認證方式設有不同門檻：OAuth 連線為連續八次、API 金鑰為十二次、本機服務為兩次。跳脫後進入半開狀態進行探測，重設時間分別為六十秒、三十秒與十五秒，恢復過程採惰性策略，避免大量請求同時湧回。

第二層是連線冷卻，作用範圍為單一金鑰或帳號。基礎等待時間為 OAuth 五秒、API 金鑰三秒，之後以二倍指數退避，並設有防止驚群效應的保護；遇到 429 回應時會遵循上游給出的 Retry-After 指示。單一金鑰冷卻期間，同帳號的其他金鑰仍可繼續服務，成功請求會清除所有錯誤狀態。

第三層是模型鎖定，作用範圍最小，只針對單一模型。當某個模型出現 429、上游 404 或模式拒絕時，僅該模型被鎖定，不會波及整個連線。專案在文件中特別區分暫時性錯誤與終止狀態：被封禁、憑證過期或額度耗盡屬於需要人工處理的終止狀態，不會以冷卻機制自動重試。這三層之外，路由層另設四級降級順序，依序為訂閱額度、API 金鑰、低價模型與免費層級。

OmniRoute 的 20 種路由策略有什麼分別？

策略涵蓋優先順序、填滿優先、加權隨機、輪詢、二分選擇、最少使用、成本最佳化、重置視窗感知、上下文接力與配額加權等，可按每個路由步驟混搭。

最基本的用法不需要建立任何組合。使用者把模型名稱設為 auto，系統便依已連接的供應商即時評分並組成虛擬組合，預設行為帶有「上次良好供應商」的黏著性，避免同一段對話在不同模型之間反覆跳轉。在此之上另有多個變體，例如偏重程式碼品質的 auto/coding、偏重延遲的 auto/fast、只使用已付費訂閱額度且失敗即止的 auto/subscription，以及允許平行向多個模型提問再取一則回應的 auto/chaos。

需要精細控制時，開發者可以自行組合二十種策略，包括優先順序、填滿優先、加權隨機、輪詢、二分選擇、最少使用、成本最佳化、重置視窗感知、上下文接力、快取最佳化與配額加權等。最新加入的配額加權策略會先跳過已耗盡的帳號，再按剩餘額度與在途負載的比例於其餘帳號之間抽取，同時保持既有對話綁定在同一條連線上。

路由透明性是這套機制的配套設計。每個回應都附帶 X-OmniRoute-Decision 標頭，標明當次由哪個策略、哪個供應商、花費多少延遲完成；另有唯讀端點公開某個 auto 通道當下的候選池，便於排查為何某次請求流向特定模型。

OmniRoute 如何節省 15% 至 95% 的權杖？

它把十二個可組合壓縮引擎串成管線，預設執行 RTK 與 Caveman 兩級，官方給出的平均節省比例為 89.2%，程式碼與結構化資料受保護。

壓縮管線由十二個引擎組成，依序為跨回合去重、大區塊歸檔、空白與圖片網址精簡、工具結果過濾、Responses 工具輸出壓縮、表格緊湊化、相關性抽取、散文壓縮、漸進式老化摘要、語意剪枝、啟發式剪枝，以及實驗性的上下文轉圖編碼。每個引擎可獨立開關，也可按不同路由組合分別配置。

預設堆疊只執行其中兩級：RTK 負責工具結果的過濾、去重與截斷，會依指令類型判斷保留內容；Caveman 負責散文層的規則式壓縮。兩者作用於同一份內容時節省比例會複合，官方文件給出的計算方式為一減去兩者剩餘比例相乘，代入 80% 與 46% 後得出 89.2%，區間落在 78.4% 至 94.6%。專案同時強調，程式碼區塊、網址、JSON 與結構化資料一律由保護機制逐位元保留，避免壓縮破壞可執行內容。

對於風險承受度較低的場景，專案提供四種預設模式：輕度約節省 15%、標準約 30%、積極約 50%、極致約 75%，並附有防膨脹保護，當壓縮後長度反而增加時會回退原文。這組數字屬於文件記載的示例，實際效果取決於工作負載結構，工具輸出佔比愈高的專案，收益愈明顯。

OmniRoute 的免費額度數字應該怎樣理解？

每月約 16.2 億權杖是第三方免費層級聚合的估算值，並非 OmniRoute 發放的額度；使用者須自行註冊並提供憑證，各供應商保留調整權利。

這是全篇最容易被誤讀的數字。專案在 README 中以顯著篇幅說明，該數字是把三十四個可重複取得的額度池去重後，對其中十七個公布正向月度預算的池子加上五項按模型計算的 Groq 上限所得的估算總和，並非 OmniRoute 發放的權杖補助。使用者必須自行註冊帳號、取得憑證並連接可用的供應商，每家供應商各自控制其上限、可用性與條款。

口徑差異同樣需要留意。專案並列多組分母：375 個已登記供應商、153 個帶有免費標記的中繼資料、239 個聊天供應商對應 3,059 組供應商與模型配對、1,475 個原始模型識別碼，以及免費額度目錄中的 467 筆按模型列出的紀錄。這些數字分屬不同定義，不能互相換算。此外，需要地區身分驗證才能開通的額度（目前為 ModelScope）被單獨列出，不計入主標題。

專案亦主動標示風險。目錄中有十二家供應商被列為條款高風險，其中 Kiro 預設被排除於自動路由之外，即使使用者主動連接帳號也不會覆蓋該設定。文件中反覆出現一句提醒：這些數字每兩週重新稽核一次，供應商結束免費層級時數字會下降，新供應商加入時則上升。這種寫法在行銷導向的 README 中並不常見，某種程度上也解釋了專案為何能取得高分信任。

OmniRoute 支援哪些 AI 工具與整合方式？

它相容三十七款命令列工具與代理，並提供 MCP、A2A、REST、Webhook 與遠端 CLI 五種控制介面，代理可自行操作閘道本身的路由、金鑰與壓縮設定。

客戶端覆蓋面相當廣。文件列出 Claude Code、Codex CLI、Cline、Kilo Code、Zoo Code、Continue、Aider、OpenCode、Copilot CLI、Cursor CLI、Goose、Open Interpreter 與 OpenClaw 等三十七款工具，全部透過同一個端點接入。專案另提供 omniroute run 指令，可在不修改工具設定的前提下，以指定模型啟動其中七款命令列工具，憑證按程序注入，Qwen 與 Gemini 會取得隔離的臨時家目錄。

控制面同樣開放。MCP 以標準輸入輸出與 HTTP 串流兩種形式提供，HTTP 版本包含一百一十個工具與三十三個權限範圍；A2A 介面採 JSON-RPC 2.0 加 SSE，對外公布六項技能；其餘包括 OpenAI 相容的 REST 端點、可推送額度事件的 Webhook，以及帶範圍權杖的遠端 CLI 模式。這種設計意味著一個具備工具呼叫能力的代理，可以直接管理閘道本身，例如新增供應商、調整路由組合或查詢剩餘額度。

命令列本身亦非附屬功能。專案提供八十餘個指令，涵蓋供應商管理、OAuth 授權、金鑰池、組合設定、成本統計、壓縮模式、健康檢查、稽核日誌、備份與模擬等面向，並內建互動式聊天客戶端與診斷指令，用於排查連接埠、原生依賴與供應商狀態。

開放議題 444 項則是另一面訊號。對一個每兩週更新一次的大型專案而言，這個數字不算離譜，卻也說明使用者回報量已經超出小型維護團隊的即時處理能力。專案以測試規模作為品質背書，文件聲稱覆蓋七千八百餘個測試檔案與五萬六千餘條靜態測試宣告，實際覆蓋率仍待第三方驗證。

OmniRoute 值得一試嗎？與 LiteLLM 有何差異？

若需求是統一多家供應商並壓低權杖成本，它提供的路由與壓縮模組比多數同類專案完整；若需求是企業級審計與穩定保證，仍應先自行壓測，並留意免費層級的條款風險。

專案在文件末尾附上與 9router、OpenRouter、CLIProxyAPI 及 LiteLLM 的功能對照，宣稱在供應商數量、免費層級內建、路由策略、壓縮引擎、MCP 工具數、A2A 支援、記憶體與護欄等十三個面向取得領先。這類對照表由專案自行維護，日期與計數方式均可能變動，閱讀時宜視為功能盤點而非獨立評測。

真正的分野在設計取向。LiteLLM 以 Python 生態與企業部署為核心，強調一致的 SDK 介面與虛擬金鑰管理；OmniRoute 則以本機優先、壓縮與多代理協定為重心，並把控制面本身開放給代理操作。兩者並非互斥，同時部署的團隊亦所在多有。

適用判斷可以從三個問題出發。第一，團隊是否同時持有多家供應商的免費或訂閱額度而無力管理，若是，路由與額度池的價值最直接。第二，工作負載是否以工具呼叫與長上下文為主，若是，權杖壓縮的收益會被放大，反之在短問答場景的效果有限。第三，是否能接受相對年輕的程式庫與高頻更新節奏，若資安審查流程較長，宜先以獨立環境驗證，並確認所連接供應商的服務條款允許此類轉發。

出處連結有哪些？

原始碼、文件與版本紀錄位於 GitHub 的 cheaper-inference/OmniRoute 倉庫，採 MIT 授權釋出，可自行部署或審計。

倉庫位址為 https://github.com/cheaper-inference/OmniRoute ，文件包含供應商參考、免費層級方法論、路由與容錯指南、壓縮引擎說明，以及與同類專案的對照方法。專案另設官方網站、Discord 與 Telegram 社群，並在 npm 與 Docker Hub 同步發佈安裝包，桌面版則透過 GitHub Releases 提供。

總結：OmniRoute 適合什麼團隊？

它適合已持有多家模型額度、需要統一入口與成本控制的開發團隊，以及大量依賴工具呼叫的代理工作流；追求長期穩定支援的企業宜先評估其更新節奏。

OmniRoute 的實際貢獻，是把供應商差異、限流處理與權杖成本這三件長期困擾開發團隊的雜務，收斂成一個可設定、可觀測、可由代理操作的中介層；它宣稱的免費權杖數量只是行銷層的引子，並非產品本體。三層容錯與二十種路由策略解決的是中斷問題，十二引擎壓縮解決的是成本問題，而本機優先與加密憑證解決的是信任問題。

同時必須看清它的邊界。免費額度是第三方供應商條款的聚合結果，隨時可能變動，其中十二家被專案自身列為高風險；八個月八萬星標的成長速度帶來關注，也帶來維護壓力與四百餘項未結議題。把 OmniRoute 當作降低實驗成本的工具，而非保證可用性的基礎設施，是比較務實的定位。
