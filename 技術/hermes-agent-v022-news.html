Hermes Agent 0.22 登場：本地模型一鍵跑起

2026年10月20日 12:00 • 閱讀時間 4 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/NousResearch/hermes-agent

Hermes Agent（NousResearch/hermes-agent）是 Nous Research 開發的開源 AI 代理，於 2026 年 10 月 13 日發布 v0.22「門檻版本（The Threshold Release）」。此版本在 GitHub 累積 255,258 顆星標與 55,565 次複製，以 Python 撰寫、採 MIT 授權，自 2025 年 7 月建立以來已累積 56,817 次提交與 4,631 位貢獻者。新聞價值在於它的更新方向：過去兩年開源代理社群的競爭焦點集中在模型能力與工具數量，這次更新卻把資源投放在「第一次啟動」與「版本升級」這兩件長期被忽略的事情上。

Hermes Agent 是什麼？

Hermes Agent 是 Nous Research 開發的開源自主代理，具備技能自我建立與跨會話記憶，可執行於終端、訊息平台與七種遠端後端。

專案定位為「自我進化的 AI 代理」，核心機制是一條封閉的學習迴圈：代理在完成複雜任務後會自行建立技能，於後續使用中持續修訂，並主動提醒自己把關鍵知識寫入持久記憶。它同時以 FTS5 建立會話全文索引，讓跨會話的歷史對話可被檢索與摘要，並透過 Honcho 的使用者建模機制累積對操作者的理解。技能格式相容於 agentskills.io 開放標準，代表技能可以在不同代理框架之間流動。

執行環境的設計偏向「離開筆記本電腦」的使用方式。除了本機終端，它支援 Docker、SSH、Singularity、Modal、Daytona 與 Vercel Sandbox 七種後端，其中 Modal 與 Daytona 提供無伺服器持久化，環境在閒置時休眠、收到請求時喚醒。訊息入口涵蓋 Telegram、Discord、Slack、WhatsApp、Signal 與電子郵件，同一個閘道行程即可服務多個平台，並保留跨平台的對話連續性。這種架構讓代理可以長時間駐留在雲端，由使用者從手機下達指令。

專案的技術組成相當分散，主要語言為 Python（約 1.12 億位元組），其次為 TypeScript（約 3,913 萬位元組），另有 JavaScript、Shell、PowerShell、Rust、Nix 等。這種比例反映它的實際形態：核心代理邏輯以 Python 撰寫，桌面應用與介面則以 TypeScript 建構。

v0.22「門檻版本」帶來哪些關鍵變化？

首次啟動改為引導式對話並附免費試用模型、外掛目錄擴至 600 個、本地模型一鍵安裝、桌面版改簽名封裝、發布流程改走穩定 SemVer 通道。

官方在發布說明中把這個版本命名為「門檻」，指的是跨過門檻的那一步：從 v0.21.0 到 v0.22.0 之間累積約 24,200 次提交、約 6,080 個合併請求、約 15,600 個檔案變更與約 718 萬行新增程式碼，同時關閉約 7,180 個議題，參與貢獻者約 2,520 人。這個週期約為前一個版本的 2.5 倍，是專案歷來最大的一次視窗。

首次啟動的流程被徹底改寫。過去在全新電腦上開啟桌面應用，使用者會先看到設定畫面，需要自行填入供應商與金鑰；現在改為一段引導式對話，逐張卡片詢問名稱、強調色、版面、要連接哪些應用與要安裝哪些外掛，並以名為 nous/welcome 的免費試用模型驅動，每個作業系統使用者可啟用一次。換言之，使用者在尚未擁有任何 API Key 之前，就已經能與代理對話。代理同時取得 set_theme 工具，可以直接以自然語言調整介面配色與明暗模式。

連接器的設計也朝「降低前置成本」推進。代理可透過 Nous 的工具閘道在 Linear、Notion 等託管應用中執行操作，首次使用時在瀏覽器完成一次授權即可，不需要事先註冊 Nous 帳號；系統會為首次使用建立一個僅限連接器的免費身分。桌面版把託管應用與自架的 MCP 伺服器整合進同一個連接器頁面，並允許同一個應用連接多個具名帳號，方便區分工作與個人情境。

本地模型為何成為這次更新的重心？

因為它移除了帳號與金鑰這道前置條件：代理自動安裝對應硬體的 llama.cpp 引擎，依顯示卡與記憶體評估目錄模型，挑選可完整載入且品質最高的版本。

本地模型的實作方式值得細看。代理會自行安裝並維護 llama.cpp，依硬體選擇對應引擎：純 CPU、NVIDIA 的 CUDA、Apple Silicon 的 Metal、AMD 與 Intel 顯示卡的 Vulkan，以及 AMD 的 ROCm。它會依顯示卡記憶體與系統記憶體評估目錄中的每個模型，只推薦能完整載入顯示卡記憶體的版本，並在目錄中挑選品質最高者。下載支援暫停與續傳，伺服器跟隨代理啟動與停止，引擎更新為單一按鈕操作。

內建目錄包含 Qwen3.8 27B、帶 MTP 推測解碼頭的 Qwen3.8 Flash Next、Qwen3.6 35B-A3B 與 DeepSeek V4 Flash，亦可直接載入 Hugging Face 上的任意 GGUF。整個流程不需要帳號、不需要金鑰，資料不離開本機。對於處理敏感文件或受合規限制的團隊，這一點的意義大於效能數字本身。

v0.22.2 進一步補強了筆記本電腦上的長回合體驗。本地請求一律以串流方式輸出並顯示提示讀取進度，停滯計時器會跳過機器休眠的時間，復原的本地伺服器會重新嘗試而非被熔斷器永久標記失敗，壓縮流程亦不再因伺服器仍在讀取長對話而逾時。這些修正針對的是同一類問題：本地推論的速度波動遠大於雲端 API，若上層的重試與逾時邏輯沿用雲端假設，使用者就會感受到莫名的中斷。

為什麼要從逐次提交改為穩定版本通道？

因為追蹤主分支令每次升級都承擔未測試變更的風險；改為每個版本先通過原始碼、容器、簽名桌面建置與跨系統升級測試才發布。

這項改動的影響比表面看來深遠。過去原始碼安裝預設追蹤 main 分支的每一次提交，使用者執行更新時取得的可能是數小時前才合併、尚未經過完整驗證的程式碼。v0.22 之後，安裝預設跟隨經驗證的 SemVer 版本，每個版本在發布前須通過原始碼 CI、Docker、Nix、各作業系統的簽名桌面建置與安裝升級測試。偏好前沿功能者可執行 hermes update --set-channel main 切回主分支，桌面版的設定頁亦提供通道切換。

值得注意的是降級的處理方式。專案把移往較舊版本明確標示為「回滾」，且未經確認不會執行，安裝程式重跑亦會保留使用者選擇的通道。這種設計承認了一個現實：代理類工具的升級失敗成本很高，因為它同時牽涉憑證、排程任務與既有會話，隨意降級可能造成狀態不一致。

桌面版的派發方式同步改變。應用程式改為密封的簽名封裝，自帶 Python 與 Node 執行環境，首次啟動不再需要建置。Windows 取得簽名的 MSIX（x64 與 ARM64），可透過 App Installer 或 Microsoft Store 安裝；macOS 預設建置僅支援 Apple Silicon 並附公證。底層新增的統一套件管理器 hermes pm 負責所有固定版本、經雜湊校驗的工具與 Python 環境，更新時先建置新環境、通過檢查後才切換，避免更新中斷留下半套狀態。

600 個外掛的目錄如何改變生態？

每個外掛固定指向經審核的提交，並禁止修改代理內部或附帶無法掃描的二進位檔；記憶體供應商與家用整合改由原廠自行維護。

外掛目錄在這個週期從零成長到 600 個條目，每個條目固定指向一個經審核的提交，可從桌面版或命令列安裝，並依分類與星等排序瀏覽，每個外掛與作者各有獨立頁面。目錄規則明確禁止已收錄外掛修改代理內部實作，亦不接受無法掃描的二進位檔，這道限制在代理類專案中相當關鍵：外掛能存取的權限與代理本身相同。

記憶體供應商的位置也被重新安排。Honcho、Supermemory、Hindsight、Mem0、OpenViking 與 Holographic 六家廠商原本內建於專案，現在改為各自維護的目錄外掛，Home Assistant、Spotify 與 Langfuse 同樣遷出，既有使用者會在更新或首次啟動時自動遷移，資料保持完整。官方說明此舉令預設安裝更精簡，也把整合的維護責任交還給原廠。

代價落在外掛作者身上。舊的相容匯入層已移除，hermes sync（技能同步）與內建的 tirith 掃描器一併刪除，數個工具更名（todo 改為 todo_list、cronjob 改為 cronjob_manage、process 改為 process_manage，舊名仍可使用）。對長期維護外掛的開發者而言，這是一次需要排入時程的介面整理。

原始碼精簡三成四意味著什麼？

在行為不變的前提下，原始碼由約 106 萬行降至 69.8 萬行，主要閘道檔案由 34,847 行縮至 5,512 行；工具描述改為按需載入，固定提示詞減少約 2,100 個代幣。

官方將這輪整理描述為「零行為變更」的重構：原始碼由約 106 萬行降至 69.8 萬行，減幅約三成四，其中 gateway/run.py 由 34,847 行縮減至 5,512 行。這類數字在新聞稿中常被視為美化，但對代理框架而言有實質意義：程式碼量直接影響模型可理解的上下文範圍，也影響貢獻者理解架構的成本。

提示詞的精簡同樣具體。約 19 個較少使用的工具改為僅在代理主動搜尋時載入，使桌面版每次呼叫送出的工具結構描述約減少一半，固定提示詞另減少約 2,100 個代幣。對於按代幣計費的 API 使用者，這是可直接量化的成本下降；對於本地模型，則等於每次回合需要預填的內容更少，首次回應時間相應縮短。

多工處理的介面亦一併改善。執行中的子代理會即時顯示於輸入框上方，列出各自的任務、已用時間與即時逐字輸出，並提供轉向與停止按鈕，命令列的 F6、TUI 的 Ctrl+T 與桌面版皆支援。/stop 可觸及背景子代理並交回部分成果，delegate_task 亦能把截圖與設計稿傳遞給具視覺能力的子代理。

專案目前的規模數據如何？

儲存庫累積 255,258 顆星標、55,565 次複製、4,631 位貢獻者與 56,817 次提交，採 MIT 授權，主要語言為 Python 與 TypeScript。

從時間軸觀察，專案於 2025 年 7 月建立，至 2026 年 10 月累積 56,817 次提交，平均每日逾百次提交，這種節奏在單一代理框架中並不常見。星標與複製的比例約為 4.6 比 1，複製比例偏高，反映不少使用者選擇自行部署或作為二次開發基礎，而非單純關注專案。

待處理議題數達 50,055 個，這個數字需要放在規模脈絡下理解。以每日逾百次提交、逾兩千位貢獻者的流量計算，議題佇列的累積速度通常高於清理速度；專案在同一週期內關閉約 7,180 個議題，顯示清理工作持續進行，但佇列仍隨使用者基數擴張。

升級到 0.22 前應注意哪些變更？

執行環境升為 Python 3.14、Windows 桌面僅提供 MSIX、會話不再依閒置時間自動重置，逾 90 天未用的已結束會話會被清除。

第一項是執行環境。受管理安裝的執行環境升為 Python 3.14，由套件管理器自動安裝，但 KittenTTS 在 3.14 上無法使用。第二項是平台限制：Windows 桌面改為僅提供 MSIX，需要 Windows 11 22H2 或更新版本，舊的 NSIS 與 MSI 安裝程式已移除；macOS 預設建置僅支援 Apple Silicon。

第三項牽涉資料生命週期。會話不再依閒置或每日計時器自動重置，session_reset 的閒置與每日模式已退役，設定該模式的組態會記錄警告；同時 sessions.auto_prune 預設開啟，已結束且逾 90 天無活動的會話會在啟動時刪除，釘選與進行中的會話不受影響。若需要完整保留歷史，必須明確設為 false。

第四項是架構收斂。每台機器預設只執行一個訊息閘道與一個桌面後端，服務所有設定檔；hermes update 會在沒有衝突時把既有的逐設定檔閘道合併進來。這減少了行程數量與權杖衝突，但若過去依賴多個獨立閘道做隔離，需要重新確認權限與允許清單的邊界。

此外，v0.22.2 修復了一項與重啟有關的啟動問題：Linux 在重新開機後可能把一個較早的行程識別碼分配給無關行程，受監督的閘道因此誤判已有實例在執行而拒絕啟動。新版會記錄啟動所屬的開機週期，無法判定時則向僅有存活閘道持有的主機鎖詢問。官方同時註明一項已知問題：在 v0.22.1 閘道下執行過的會話，於 v0.22.2 無法刪除。

總結：哪些使用者適合升級到 0.22？

重視資料留在本機、需要長時間駐留雲端、或曾因升級失敗而中斷的團隊最適合；重度依賴自製外掛與舊工具名稱者宜先完成相容性檢查。

v0.22 的價值不在功能清單的長度，而在它處理了開源代理長期迴避的兩件事：首次使用的摩擦，與版本升級的不確定性。以引導式對話與免費試用模型降低起步門檻，以一鍵本地模型移除帳號依賴，以簽名封裝與穩定通道把升級變成可預期的動作，這些改動共同把「能不能裝得起來」轉為「裝起來之後要做什麼」。

代價同樣存在。Python 3.14 的執行環境、Windows 的 MSIX 限制、會話自動清除與單一閘道架構，四項都可能在升級當日造成可感知的變化；外掛作者面對的相容層移除與工具更名，則需要一段遷移期。對於把代理當成長期基礎設施、且資料必須留在自有環境的團隊，這輪改動的效益明確高於調整成本；若僅作短期試用，先觀察一個版本週期再升級亦屬合理選擇。
