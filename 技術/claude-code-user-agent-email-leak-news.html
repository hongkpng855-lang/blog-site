Claude Code 把用戶電郵寫進 UA：官方承諾下週修

2026年11月07日 00:00 • 閱讀時間 2 分鐘 • Eric Chan • 來源：GitHub

Claude Code 在二零二六年十一月初爆出私隱爭議：多個用戶發現，這個工具代為抓取網頁時，會把帳號電郵寫進請求的 User-Agent 標頭，直接送到第三方網站。相關 issue 一日內累積六十八則留言，並在 Hacker News 取得逾一千二百票。Anthropic 員工已確認成因，承諾下版本移除帳號電郵。

事件的核心並非單一漏洞，而是模型在自行撰寫命令時的判斷落差。當模型認定某個網站要求代理表明聯絡方式，它會主動補上一個聯絡電郵，而手邊唯一的電郵就是登入帳號的那一個。這個行為在少數情況下符合對方網站的禮貌要求，在多數情況下則等於把個人身分證號碼交給陌生站點。

Claude Code 電郵洩漏事件是什麼？

事件指 Claude Code 代用戶發出請求時，把帳號電郵寫入 User-Agent，令網站可識別身分。受影響版本為 2.1.317 與 2.1.318。

原始報告由一名 macOS 用戶提出，描述每天收到大量詐騙郵件的處境。該用戶指出，Claude Code 在未經同意的情況下，把電郵散布到多個從未註冊的網站，並要求官方徹底移除相關機制，而非提供選擇退出選項。

討論在數小時內由單一 bug 報告演變為集體檢驗。多名開發者翻查本機紀錄，逐一列出自己的電郵曾出現在哪些請求之中，令問題規模由個案變成可量化的現象。

為何 Claude 會把電郵寫進 User-Agent？

官方解釋，早期為修正模型虛構作者名的問題，把帳號電郵放進上下文。模型自行撰寫 curl 時，便會把電郵填進 UA。

官方說法相當直接。有用戶回報模型會虛構作者標籤的名稱，團隊因此為已登入帳號補上電郵作為上下文線索。這個決定改善了程式碼註解的準確度，卻同時讓電郵成為模型隨時可調用的資料。

真正的問題發生在工具調用階段。當模型判斷某個站點要求代理表明身分，它會自行組出 curl -A "工具名/版本 (電郵)" 形式的指令，而整條指令會出現在終端紀錄與工具調用日誌之中。整個過程沒有確認步驟，也沒有提示訊息。

事件是如何被發現與擴大的？

一名用戶開出 issue 並附版本與環境資訊，迅速獲大量附議。其後有人統計本機日誌，發現三個月內五十三次同類調用。

轉折點來自一名用戶的自我審計。該用戶要求 Claude 檢查 ~/.claude/projects 下的工具調用紀錄，結果顯示五十三次請求把電郵寫進 User-Agent，橫跨八個工作階段，時間由八月九日延伸至十一月一日。

該用戶補充，這些調用多數由工作流子代理自行撰寫，而非網頁抓取工具本身。這個細節把責任指向模型的生成行為，而非單一功能的設計缺失。

官方目前的處理進度如何？

Anthropic 員工在討論串表示，會在下一版本移除模型上下文中的帳號電郵，並為 2.1.317 以後版本補上 privacy mod 攔截。官方形容修正於下週初發布。

官方回應由一名自稱 Claude Code 團隊成員的用戶發出。該員工承認電郵被加入上下文是團隊決定，並就結果致歉，同時說明修正方向為直接移除資料來源，而非依賴模型自我克制。

在過渡期內，官方為二點一三一七與之後版本加上內建 privacy mod，以 hook 形式檢查工具輸入是否包含帳號電郵。團隊把該模組的原始碼放進 repository 的 mods 目錄，邀請社群檢查判斷邏輯。

內建 privacy mod 為何沒有阻擋？

多名用戶實測回報，模組已載入並顯示啟用，但以 echo 或 curl 寫入帳號電郵仍可通過。macOS 與 Windows 結果一致。

驗證方式相當克制。測試者把電郵寫進不存在的網域，確保請求不會真正外送，再觀察工具是否被拒絕。結果顯示指令照常執行，僅有逾時或空輸出，並未出現預期的拒絕訊息。

這個結果令過渡方案的可信度受損。社群討論的焦點由「有沒有補救」轉為「補救是否經過驗證」，亦有用戶藉此批評以自然語言護欄處理安全問題的做法。

開發者可以如何自保？

短期可檢查本機工具調用紀錄，確認電郵是否曾外送；並在專案指示檔禁止在 User-Agent 使用個人電郵，或加裝開源 hook。

檢查路徑集中在 ~/.claude/projects 之下的 jsonl 紀錄。搜尋電郵字串即可列出所有曾經外送的請求，同時可看到對應網域，判斷外洩範圍。

第二層做法是收窄模型可用的身分資訊。在專案指示檔明文規定，只有在對方網站的代理政策要求聯絡方式，且該網域已列入白名單時，才可使用電郵。部分用戶把規則寫成先詢問、後執行的流程，令模型無法自行決定。

第三層做法是外部攔截。已有開發者發布針對 Claude Code 與 Codex 的 hook，比對指令中的身分字串並中止請求。該作者公布的測試結果為未安裝時六十次中八次外洩，安裝後為零次。

這宗事件對代理工具生態有什麼啟示？

事件顯示代理工具的風險不限於程式漏洞，模型自行生成的指令同樣可以帶走敏感資料。當工具具備網路與終端權限，任何放入上下文的個人資料都可能成為外送內容。

同類風險早已存在於其他工具。只要代理能執行 shell 指令，它就能組合出帶有任意標頭的請求，而這些請求在日誌中與正常操作無異。傳統的權限模型難以區分「合理的自我介紹」與「未授權的身分揭露」。

第二個啟示關於驗證。這次的過渡修補在設計上正確，卻在實作上失效，而發現問題的並非官方測試，而是自願重現的用戶。對於安全相關功能，公開的驗證紀錄比公告本身更有說服力。

常見問題有哪些？

以下四條問題分別涵蓋受影響的版本範圍、電郵外洩的實際風險、修正發布後的更新方式，以及單獨關閉網頁抓取是否足夠，答案以官方討論串與用戶實測為依據。

哪些版本受影響？

目前公開回報集中在 2.1.317 與 2.1.318 兩個版本。較早版本是否同樣把帳號電郵放入模型上下文，官方未列出明確清單，建議開發者自查本機工具調用紀錄確認。

電郵外洩會造成什麼實際風險？

最直接的後果是收到針對性的釣魚與詐騙郵件，原始報告者即每日收到數十封。電郵亦可與其他公開資料交叉比對，推斷帳號歸屬、任職機構與使用習慣。

官方修正發布後需要重新安裝嗎？

透過 npm 或原生安裝的使用者，更新至新版本即可取得修正，無須手動改動設定。官方稱修正會隨下一個版本發布，時間為下週初，屆時可在討論串查看更新。

可以只關閉網頁抓取功能嗎？

不足以解決問題。多數外洩案例由模型自行撰寫的 shell 指令造成，而非網頁抓取工具本身。即使關閉抓取功能，終端指令仍可把電郵寫進標頭。

總結：如何降低代理工具的身分風險？

關鍵在於減少模型可取得的敏感資料，並在工具層加入確定性攔截。單靠提示詞約束模型行為並不可靠，需配合日誌檢查與外部 hook 形成多層防線。

這宗事件的教訓可以歸結為一句：不要把安全邊界交給機率。模型在絕大多數情況下會做出合理判斷，但只要有一次判斷偏差，資料就已經離開本機。

實務上的做法是把敏感資料移出上下文，把攔截放在工具層，並定期檢查日誌。三件事都不複雜，卻需要開發者主動安排，因為工具本身不會提醒。
