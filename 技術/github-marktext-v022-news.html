MarkText 回歸：6.2 萬星編輯器支援 GitHub Alerts

2026年10月21日 00:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/marktext/marktext

MarkText 於 2026 年 10 月 18 日發布 v0.22.0，為這款開源 Markdown 編輯器補上 GitHub Alerts 支援，並延續自 2026 年 5 月開始的版本節奏。專案目前累積 62,887 顆星標、4,643 個分支，全部版本的累計下載次數超過 350 萬次。對一個在 2022 年至 2026 年間幾乎沒有提交紀錄的專案而言，2026 年內連續推出 22 個版本，構成本次更新最值得注意的訊號。

MarkText 是什麼？

MarkText 是開源的 Markdown 編輯器，採 MIT 授權，支援三大桌面平台，以即時預覽與無干擾書寫為核心，在 GitHub 累積 62,887 顆星標。

專案定位寫得相當明確：即時預覽的所見即所得介面、支援 CommonMark 與 GitHub Flavored Markdown 規範、選擇性支援 Pandoc Markdown，並提供數學公式、front matter 與表情符號等擴充語法。編輯模式包含原始碼模式、打字機模式與專注模式，主題則涵蓋 Cadmium Light 與 Material Dark 等選項。

與同類工具相比，MarkText 的取向偏向純粹的編輯器，而非知識管理系統。它不建立雙向連結網絡，也不內建資料庫，僅處理單一 Markdown 檔案，並把圖片貼上、目錄導覽與匯出流程做得足夠順暢。對於只需要穩定書寫環境、不希望引入額外知識體系的使用者，這種克制本身即為一種產品選擇。

MarkText 為什麼沉寂四年後重新活躍？

專案於 2022 年 3 月發布 v0.17.1 後進入低度維護，2022 年至 2026 年初僅有 17 次提交；2026 年 5 月起恢復節奏，至 10 月 20 日已推出 22 個版本。

版本紀錄清楚顯示這段中斷。v0.17.1 於 2022 年 3 月 7 日發布，下一個正式版本 v0.19.0 直到 2026 年 5 月 28 日才出現。中間四年間，儲存庫僅有 17 次提交，多為依賴升級與說明文件修補，例如 2024 年 3 月的 Mermaid 10 升級與 2024 年 6 月的葡萄牙文翻譯改進。對於一個擁有六萬顆星標的專案，這種活躍度通常被社群解讀為維護終止。

恢復後的節奏則截然不同。2026 年 10 月 2 日推出 v0.20.0，10 月 8 日連續發布 v0.21.0 與修補 macOS 簽章問題的 v0.21.1，10 月 11 日推出 v0.21.2，10 月 18 日推出 v0.22.0，10 月 20 日仍有提交進入主幹。近 30 日內的提交數量已達 100 筆上限，顯示維護者 Jocs 與新加入的貢獻者正同步推進多條工作線。

值得注意的是，本次復甦並非單純的功能堆疊。v0.20.0 的變更清單包含大量底層搬遷項目，例如把編輯器核心 Muya 拆分為獨立套件、導入主題化 CSS 變數、重整區塊操作 API 與還原流程圖支援。這些工作對一般使用者不可見，卻是後續功能能否持續交付的前提。

MarkText v0.22.0 有哪些新功能？

v0.22.0 新增 GitHub Alerts 支援，涵蓋 NOTE、TIP、IMPORTANT、WARNING 與 CAUTION 五種類型，並整合語法轉換與右鍵選單。

GitHub Alerts 是 GitHub 於 2023 年底引入的引用區塊語法，寫法為在引用符號後加上 [!NOTE] 等標記，渲染成帶圖示的提示方塊。社群長期在議題 #3764 與 #1240 中要求支援此語法，本次由四個依序合併的拉取請求完成，分別處理語法與格式轉換、編輯器即時行為、桌面端設定與右鍵選單整合。

技術文件顯示，該功能會辨識合格頂層引用區塊中的獨立標記，加入對應的 token 與狀態表示，並在 Markdown 序列化時保留標記間距資訊。靜態轉換器與剪貼簿轉換器同步支援此語法，輸出成 HTML 後亦可反向還原為引用格式。測試涵蓋巢狀情境、參考連結、行內內容與空內容邊界，其中 Muya 單元測試 2,635 項、CommonMark 與 GFM 相容測試 1,347 項全數通過。

版本另外包含多項穩定性修補，包括 Windows 匯出時的磁碟機路徑保留、貼上網址後選取範圍被清除、清單內容在反向選取複製時遺失，以及圖片縮放於文件重建過程中被取消等問題。這些項目多對應具體議題編號，反映維護者優先處理長期累積的缺陷。

MarkText 的核心編輯器架構有什麼改變？

編輯器核心 Muya 已重寫為 TypeScript 並發布為 @muyajs/core，桌面端改用 Electron 42 與 Vue 3.5，儲存庫重組為三個套件。

架構層面的改動是本次復甦最實質的部分。舊版 Muya 以 JavaScript 撰寫並深度綁定桌面端，重寫後成為獨立套件 @muyajs/core，對外提供區塊複製與插入、游標座標查詢、格式狀態回報、表格建立、圖片插入、拼字檢查替換與復原歷史序列化等 API。這種切分使編輯核心理論上可被其他應用引用，也讓單元測試得以脫離 Electron 環境執行。

桌面端同步現代化。套件資訊顯示其依賴 Electron 42.1.0、Vue 3.5、electron-vite 5、electron-builder 26、electron-updater 6.8.9 與 Element Plus 2.14.7，並以 Pinia 管理狀態。儲存庫結構改為 monorepo，劃分為 desktop、muya 與 website 三個目錄，官方網站與說明文件一併納入版本控制。

這類重構的價值不在於立即可見的功能，而在於降低後續維護成本。舊架構中，編輯行為、選單狀態與匯出流程散落於多個檔案，任何改動都可能牽動全域狀態；新架構把職責收斂至套件邊界，並以型別檢查約束介面，使外部貢獻者更容易判斷修改範圍。

MarkText 與同類編輯器有何差異？

MarkText 專注單檔書寫，不建立知識網絡；相較 Obsidian 的連結資料庫與 Typora 的付費授權，它以 MIT 授權提供輕量替代。

把三款工具並置，差異相當清楚。Obsidian 以本地資料夾為基礎建立雙向連結與圖譜，本質上是知識管理系統，學習曲線與外掛生態構成了它的護城河。Typora 同樣採即時預覽，但為付費軟體，單機授權需一次性購買。MarkText 則維持免費與 MIT 授權，功能邊界劃在編輯與匯出，不涉入資料組織。

這種定位的取捨在實際使用中會浮現。需要跨檔案引用與標籤體系的使用者，會發現 MarkText 缺乏對應機制；但若工作流程是把單篇文章寫完、輸出 HTML 或 PDF、再交付給發佈系統，那麼多餘的知識管理功能反而增加干擾。約 219 筆貢獻者記錄與 350 萬次下載，說明這個細分需求具備足夠規模。

如何安裝與使用 MarkText？

可自 GitHub Releases 下載安裝檔，或透過 Homebrew、Winget 安裝。macOS 版本需 11 以上，首次啟動前須清除隔離屬性。

安裝路徑依平台而異。macOS 使用者可執行 brew install --cask mark-text，或下載 arm64 與 x64 的獨立安裝檔；Windows 使用者可透過 Microsoft Store 以外的套件管理器執行 choco install marktext 或 winget install marktext；Linux 使用者則依官方文件選擇 AppImage、deb、rpm 或 snap 格式。

macOS 使用者需注意兩項限制。第一，官方不再發布通用二進位檔，必須依機器架構選擇 arm64 或 x64 版本；第二，所有建置皆未經 Apple 開發者簽章，拖曳至應用程式資料夾後須執行 xattr -d com.apple.quarantine /Applications/MarkText.app 清除隔離屬性，否則系統會阻擋啟動。v0.21.0 曾因新增的 Electron fuse 改寫二進位檔而破壞臨時簽章，導致 arm64 版本一啟動即崩潰，該問題已於 v0.21.1 修補。

每個版本同時提供 SHA256SUMS.txt，下載後可執行 sha256sum -c SHA256SUMS.txt --ignore-missing 驗證檔案完整性。對於在企業環境部署的使用者，這道校驗流程可納入內部軟體審核程序。

MarkText 適合哪些使用者？

適合需要即時預覽、單檔書寫與免費授權的技術文件作者；若需求涵蓋知識連結、協作編輯或雲端同步，則應評估其他方案。

從功能邊界推導，受益族群相當明確。技術文件撰寫者需要程式碼區塊、數學公式與表格支援，並希望輸出格式穩定；學術寫作者需要 front matter 與 PDF 匯出；內容工作者則看重即時預覽帶來的心流狀態。這三類需求都在 MarkText 的能力範圍之內。

需要謹慎評估的情境同樣存在。專案目前仍有 298 個待處理議題，其中部分為 2022 年前累積的長期問題，修補速度取決於少數核心維護者。若團隊要求供應商支援、服務等級協議或長期維護承諾，開源單人主導專案難以提供相應保證。此外，專案不具備協作與雲端同步能力，多人同時編輯的流程需另尋工具。

較穩妥的做法是把 MarkText 視為寫作層工具，而非知識基礎設施。檔案以純 Markdown 儲存，本身不鎖定格式，即使日後更換編輯器，內容仍可完整移轉，這也是此類工具最主要的風險緩解機制。

出處連結有哪些？

專案原始碼、版本紀錄與說明文件均位於 GitHub 的 marktext/marktext 儲存庫，官方網站為 marktext.me。

儲存庫網址為 https://github.com/marktext/marktext，版本紀錄可在 releases 頁面查閱，使用者文件與開發文件則分別位於 marktext.me 的 docs 路徑之下。專案採 MIT 授權，允許商業使用與修改，第三方分散式版本需保留原始授權聲明。

總結：MarkText 值得重新評估嗎？

值得。專案已完成核心重寫與建置現代化，2026 年內推出 22 個版本，對需要免費即時預覽編輯器的使用者具備重新評估價值。

判斷一個復活專案是否可靠，關鍵不在版本數量，而在變更的性質。MarkText 本輪提交以架構重組、型別化與缺陷修補為主，功能新增相對克制，這種比例通常意味著維護者正處理技術債，而非追逐話題。GitHub Alerts 支援雖屬小型功能，卻由四個分工明確的拉取請求完成，並附上完整的相容性測試數據，過程透明度符合健康專案的標準。

風險仍然存在。專案由單一維護者主導，貢獻者雖然增加，但核心決策依賴度未見改善，298 個待處理議題也反映出長尾問題的處理壓力。對個人使用者而言，這些風險可由純文字格式與版本控制抵銷；對組織採用而言，則需把維護中斷納入備援規劃。至少就目前證據判斷，這款曾經停滯四年的編輯器已重回可用的技術軌道。
