n8n-MCP 開源：23,284 星讓 AI 直接改工作流

2026年11月20日 04:00 • 閱讀時間 2 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/czlonkowski/n8n-mcp

n8n-MCP 是一個開源 MCP 伺服器，把 n8n 自動化平台的操作權交給 Claude、ChatGPT 與 Cursor 等 AI 助理。專案於二零二五年六月建立，累積 23,284 顆星標與 3,676 個分支，內建 3,501 個節點與 2,352 個範本的知識庫，令助理配置真實節點而非憑空猜測。

版本節奏相當密集。專案在十一月十七日發布 v2.103.0，加入變數管理工具；十一月十八日再發布 v2.103.1，把技能包同步至 n8n-skills 1.38.0。這兩個版本相隔不足一日，反映作者對 n8n 主線版本的追趕速度。

n8n-MCP 是什麼？

MCP 伺服器，把 n8n 的公開 API 包成工具集，讓 AI 助理讀取執行、修改工作流、驗證節點與管理憑證，支援任何已開啟 Public API 的 n8n 實例。

專案由 Romuald Członkowski 維護，定位是讓語言模型接管自動化平台的日常操作。它透過 n8n 的公開 API 與實例通訊，把工作流、執行紀錄、憑證、資料表與變數逐一包裝成工具，助理因此可以完成讀取與寫入兩類動作。

工具分為兩層。七個核心工具負責節點查詢、節點驗證、工作流驗證與範本搜尋，毋須連接任何 n8n 實例即可運作，因為節點資料庫已隨套件打包。另外二十二個管理工具需要 N8N_API_URL 與 N8N_API_KEY，涵蓋執行、資料夾、變數、資料表、憑證與安全稽核。

安裝路徑有三種。npm 全域安裝後可直接以 npx n8n-mcp 啟動；官方映像託管於 GitHub Container Registry； Railway 另有最佳化版本。作者同時提供託管服務，免費層每日一百次工具呼叫，並以加密方式保存使用者提供的 n8n API 金鑰。

它與 n8n 內建 MCP 伺服器有何分別？

內建版本運行於單一實例，多數操作需要工作流開啟 Available in MCP 設定；n8n-MCP 為獨立伺服器，可同時連接多個實例，並補上憑證的建立、更新與刪除。

n8n 自 late 1.x 起內建實例層 MCP 伺服器，功能覆蓋工作流編輯、執行紀錄、版本歷史與資料表。作者的說明相當克制，明言 n8n-MCP 不會取代內建版本，兩者差異在於架構位置與權限邊界。若需要 n8n 本身的節點概念與安裝方式，平台介紹 另有完整說明。

差別最明顯的一項是實例數量。內建伺服器一次只服務一個實例，而 n8n-MCP 透過託管服務或 HTTP 模式的租戶標頭，可以同時登記生產、測試與客戶環境，每次呼叫時指定目標。對接案團隊而言，這一點直接決定工具是否可用。

另一項是版本兼容。內建工具多數要求 n8n 2.12 或以上，且每個工具有各自的最低版本；n8n-MCP 的工作流與執行工具可透過公開 API 在 1.x 系列運作。官方建議，若同時設定 N8N_MCP_ACCESS_TOKEN，兩者可經同一個連線並存，助理仍然只見到一個伺服器。瀏覽器操作類的 MCP 伺服器則以 Playwright MCP 的七十二個工具 為常見起點。

AI 助理如何修改既有工作流？

更新工具按請求指定的節點與連線套用局部操作，毋須重送整份工作流，並可在單一大欄位內做尋找取代。改動前預設保存版本，最多保留十個，供差異比對與回滾。

整份工作流的讀寫方式在實務上很難用。舊做法要求助理先讀取完整 JSON，修改後再整體寫回，長工作流一次往返就消耗數千個 token，而且容易在無關欄位出錯。局部更新工具改為按操作清單處理，只送出被改動的節點與連線。

相同思路亦用於除錯。執行工具加上錯誤模式後，會回傳失敗原因、出錯的節點，以及該節點前一步的樣本資料。這三項資訊足以判斷問題出在資料格式、憑證還是節點參數，不必逐層翻查執行紀錄。

風險在於併發。由於 n8n 公開 API 不支援條件式寫入，助理必須先讀取、再套用、最後整份寫回。若有人在助理工作期間於介面修改同一條工作流，該次修改會被覆蓋。作者在文件內明言，助理處理期間不要同時在介面編輯。

驗證機制能攔下哪些錯誤？

節點驗證檢查未知節點、版本不符、必填欄位缺漏與連線斷裂，工作流驗證再處理表達式。自動修復工具可補回常見缺漏，部署後另有實例層驗證。

驗證分為四層，與助理的建構流程同步。節點層分為快速與完整兩種模式，前者十毫秒內檢查必填欄位，後者按執行環境、AI 友善或嚴格等設定檔給出修正建議。工作流層再檢查連線結構與表達式語法。

作者把預設值視為最大隱患。README 明確指出，節點參數的預設值是執行期失敗的首要來源，因為多數節點即使缺少關鍵參數仍可保存，錯誤要等到實際執行才浮現。因此助理被要求逐項明示所有影響行為的參數。

自動修復工具處理常見缺漏，例如缺少必要欄位或連線指向失效節點。部署後的實例層驗證則回到真實環境檢查一次，把保存成功與實際可執行之間的落差補上。

唯讀部署如何限制 AI 權限？

以環境變數停用寫入與刪除類工具，或只封鎖個別破壞性操作而保留查詢。搭配唯讀 API 金鑰可形成兩層限制，適合受監管的生產環境。

把生產環境的操作權交給語言模型，本身需要額外設計。專案提供兩組環境變數：DISABLED_TOOLS 整支停用工具，DISABLED_TOOL_OPERATIONS 只封鎖指定操作。前者的例子包含建立、整份更新、局部更新、刪除工作流與部署範本共九個工具。

後者更細緻，用來保留查詢而封鎖寫入。README 點出兩個容易漏掉的位置：測試工具的四種執行方式都會真正跑一次工作流，只有準備模式屬唯讀；另外「暴露至 MCP」是一項獨立寫入動作，不屬於任何操作參數，漏寫該項就仍然可以開啟工作流的可用開關。

兩層限制之上還有第三層，就是 n8n 端簽發的唯讀 API 金鑰。作者建議三者併用，因為工具層的過濾發生在助理端，而金鑰層的限制發生在平台端，兩者失效條件不同。

星標 23,284、分支 3,676、未結議題 62 個、關注者 154 位，主要語言 TypeScript，授權為 MIT，最新版本 v2.103.1 於十一月十八日發布。

議題數量值得單獨看。六十二個未結議題對照二萬三千顆星標，比例遠低於同級專案的常見水平，說明維護者對回報的處理相當積極。專案於二零二五年六月建立，十七個月內達到這個規模，成長曲線集中在 n8n 內建 MCP 伺服器發布前後。

貢獻結構則較為集中。README 的贊助段落提到，專案由個人工具演變為數萬名開發者使用，維護工作與作者的付費工作競爭時間。這種單人主導加上自動化發布的模式，令版本節奏穩定，但同時意味著長期維護依賴單一維護者的意願。

出處連結有哪些？

原始碼位於 GitHub 的 czlonkowski/n8n-mcp 儲存庫，另有官方託管服務與自架文件，涵蓋 npx、Docker 與 Railway 三種安裝路徑。

專案位址為 https://github.com/czlonkowski/n8n-mcp，套件以 n8n-mcp 名稱發佈於 npm，容器映像位於 GitHub Container Registry。文件目錄收錄自架、HTTP 部署、唯讀部署與各編輯器整合的獨立章節，另有一份與 n8n 內建伺服器並存的設定說明。

本文數據取自儲存庫公開統計與 v2.103.0、v2.103.1 發布說明，時間為二零二六年十一月十九日。節點與範本數量、工具清單以 README 所列為準，實際行為仍需在測試實例驗證。

總結：n8n-MCP 適合哪些團隊？

同時維運多個 n8n 實例、需要 AI 直接處理憑證與執行錯誤，或仍停留在舊版 n8n 的團隊。單一實例且版本較新的使用者，內建伺服器已經夠用。

n8n-MCP 解決的是規模帶來的操作成本。當自動化流程由幾條增長到數十條，分散在生產、測試與客戶環境，逐條登入介面除錯的做法就難以為繼，而由助理代為讀取執行與套用局部修改，可以壓縮單次處理時間。

導入前有三件事值得先確認。其一，助理處理期間不要同時在介面編輯同一條工作流，避免整份寫回時覆蓋他人改動。其二，生產環境應先套用唯讀設定與唯讀 API 金鑰，觀察一段時間再放寬。其三，快照雖然預設開啟，但保存失敗不會阻止改動，重要工作流仍應自行保留匯出檔。
