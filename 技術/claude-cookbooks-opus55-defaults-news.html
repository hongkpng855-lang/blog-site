Claude Cookbooks 預設模型升至 Opus 5.5

2026年10月26日 16:00 • 閱讀時間 4 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/anthropics/claude-cookbooks

Anthropic 官方維護的 Claude Cookbooks 於 2026 年 10 月 24 日把預設模型升級為 Opus 5.5、Sonnet 5.5 與 Fable 5.1，單次提交涉及 1,765 行新增與 1,329 行刪除。這個累積 53,769 顆星標的食譜庫登錄 99 份食譜，本文拆解改動細節與升級時需留意之處。

Claude Cookbooks 這次更新了什麼？

2026 年 10 月 24 日的提交把預設模型改為 Opus 5.5、Sonnet 5.5 與 Fable 5.1，並同步更新 Bedrock 識別碼與文件網域。

提交編號 #924 於 2026 年 10 月 24 日進入主分支，標題為 Bump cookbook defaults to Opus 5.5, Sonnet 5.5 and Fable 5.1。改動共觸及三十餘個檔案，涵蓋筆記本、驗證腳本、CI 工作流程與貢獻指引，屬儲存庫近月規模最大的一次同步調整。

CLAUDE.md 的模型清單由原本的 Sonnet 5 與 Opus 4.8，改為 Opus 5.5、Sonnet 5.5、Fable 5.1 與 Haiku 4.5 四款。貢獻指引同時加入一條硬性規則，範例不得使用含日期的模型識別碼，一律採用不帶日期的別名。

文件網域亦一併遷移，由 docs.anthropic.com 改指 platform.claude.com/docs。稽核腳本 validate_notebook.py 在同一次提交內增加八十行驗證邏輯，配合 CI 的筆記本測試，讓模型別名在合併前先受檢查。

預設模型改成 Opus 5.5 有什麼實際影響？

範例預設執行模型仍留在 Haiku 4.5 以控制測試成本，文件與 Bedrock 端點則全面指向 5.5 世代；只走 InvokeModel 的整合仍須使用帶日期後綴的舊格式。

3.5 世代與 5 世代之間的落差，在這份儲存庫裡以兩種方式處理。文件層面把 Opus 5.5 列為旗艦、Sonnet 5.5 列為主力、Fable 5.1 列為特定風格用途，範例則統一改用這三個別名。

實際執行成本由另一個欄位控制。.env.example 的 CLAUDE_MODEL 仍設為 claude-haiku-4-5，註解由原本的「最新 Haiku 型號」改寫為「最新 Haiku 型號，也是目前最便宜的模型」。這個安排在跑通流程與計費之間取得平衡。

Bedrock 路徑的變化更值得留意。CLAUDE.md 給出 global.anthropic.claude-opus-5-5 這類全域端點格式，並說明只走 InvokeModel 的整合，例如 boto3 的 invoke_model 或微調任務，仍要使用 anthropic.claude-haiku-4-5-20251001-v1:0 這種帶日期後綴的形式。兩種寫法並存，直接影響企業內部部署時的設定檔。

Managed Agents 是什麼？

Managed Agents 是官方託管代理執行環境，食譜示範以代理、環境與工作階段三個物件組合出可長時間執行的任務，涵蓋資料分析、事件回應與提示版本回滾。

目錄 managed_agents 內含十三份筆記本，而 registry 標記為 Claude Managed Agents 分類的食譜共十八份，在十四個分類中排第三。這個板塊在 2026 年 4 月集中上線，十月仍有增補。

內容由入門教學延伸到生產維運。入門篇用一個計算套件、三個刻意植入的錯誤，帶出代理、環境、工作階段的建立流程與串流事件迴圈。生產篇交代 vault 管理的 MCP 憑證、session.status_idled 與 session.budget_reached 兩種 webhook 模式，把長時間連線改為事件驅動。

應用面則覆蓋數個具體職能。Slack 資料機器人可接收 CSV 並在同一工作階段追問，SRE 事件回應代理會讀取日誌與操作手冊、定位根因、開出修正 PR 並等待人工核准，另有提示版本管理與回滾的完整流程。

Claude Cookbooks 收錄哪些類型的食譜？

registry.yaml 目前登錄 99 份食譜，工具與代理模式各 27 份居首，其後是檢索增強 19 份、託管代理 18 份、整合 16 份、回應處理 13 份與代理 SDK 10 份。

registry.yaml 為每份食譜記錄標題、描述、路徑、作者、日期與分類，是目前最完整的索引。統計顯示工具使用與代理模式各 27 份並列第一，檢索增強 19 份、託管代理 18 份、第三方整合 16 份緊隨其後。

其餘分類呈現長尾分布。回應處理 13 份、代理 SDK 10 份、多模態 9 份、評測 8 份、可觀測性 6 份、技能 5 份，資安 3 份、延伸思考 2 份、微調 1 份。git 樹內 .ipynb 檔共 103 份，與索引數量的差額來自尚未登錄的教學與輔助筆記本。

時間軸由 2023 年 8 月 15 日開始，與儲存庫建立同日。最新兩份食譜落在 2026 年 10 月，分別處理代理工作階段的安全審查與 OpenTelemetry 追蹤，顯示維護方向正由單次 API 呼叫轉向長時間執行的工作階段。

可觀測性與成本追蹤怎麼用？

observability 目錄提供 OpenTelemetry 追蹤與用量成本 API 兩份筆記本，把請求和代理工作階段接入既有監控，並以帕累托流程平衡成本與通過率。

observability 目錄在 2026 年 10 月 14 日新增追蹤筆記本，說明如何把 Claude API 請求與 Managed Agents 的工作階段接入既有追蹤系統。做法沿用 OpenTelemetry 標準格式，理論上可與團隊現有的 Jaeger、Grafana 或雲端監控服務對接。

同一目錄的 usage_cost_api.ipynb 處理計費面。它以用量與成本 API 取得逐次呼叫的開支，再對照 cost_optimization 的帕累托流程，用任務通過率與單次成本兩個座標找出合適配置。

2026 年 10 月 17 日加入的代理安全工作階段審查食譜，把視角轉向事後檢查。它讀取代理執行期間的對話與工具呼叫紀錄，標記出權限越界、資料外洩與提示注入的可疑痕跡，適合放在上線前的檢查清單。

Claude Cookbooks 與一般官方文件有何差別？

官方文件說明規格與參數，Cookbooks 交付可執行的 Jupyter 筆記本，保留輸出供比對，並以 uv、pre-commit 與 pytest 建立可重複的驗證流程。

定位差異體現在交付物形態。API 文件條列參數與回應格式，讀者需要自行組裝；Cookbooks 直接把完整流程寫成筆記本，執行後保留輸出，讀者可以逐格比對預期結果與實際結果。

環境一致性由工具鏈保證。CLAUDE.md 要求以 uv sync --all-extras 安裝依賴，用 uv add 管理套件而非手改 pyproject.toml，並以 ruff 統一格式、行長上限一百字元。提交前要跑 make check 與 make test。

貢獻流程同樣明確。分支命名採用使用者名稱加功能描述，提交訊息遵循 conventional commits 規範，模型使用正確性由 PR 審查自動把關。這套規則讓外部貢獻的品質下限維持在可接受範圍。

專案數據反映什麼維護節奏？

53,769 顆星標對 6,482 個分支，比例約 8 比 1；87 位貢獻者、368 項未結問題、103 份筆記本，屬核心團隊主導的大幅改動節奏。

星標與分支的比例透露使用方式。53,769 顆星標對 6,482 個分支，約八比一，低於工具型專案常見的三比一。多數讀者把它當成閱讀材料，只有少數會複製整個儲存庫改寫。

貢獻者數量同樣偏低。87 位貢獻者對五萬星規模而言屬於核心團隊主導的結構，外部參與集中在文件與個別食譜，主幹由 Anthropic 工程師掌握。這也解釋了為何一次模型升級可以在單日內覆蓋三十餘個檔案。

問題追蹤的數量需要辯證看待。368 項未結問題中，相當比例屬於食譜請求與個別筆記本的環境差異回報，而非阻斷性缺陷。儲存庫體積約 221 MB，主要來自示範圖片，首次複製的等待時間不短。

Claude Cookbooks 有哪些限制？

食譜以示範為目的，筆記本保留固定提示與假設資料，直接搬入生產仍需補上重試、錯誤處理與金鑰管理；模型字串寫死者，每次版本更替都要逐檔替換。

示範與生產之間存在明確落差。筆記本刻意保留輸出以方便對照，也因此在同一個檔案內混用固定提示、示例資料與真實 API 呼叫。搬移到生產環境時，錯誤處理、重試策略、速率限制與金鑰輪替都要重新設計。

模型別名的維護成本在這次改動中顯露無遺。三個月前的主流型號已被列為退場對象，若開發者把範例中的字串直接複製到自有專案，升級時只能逐檔搜尋替換。選用別名而非帶日期識別碼，可把這個成本降到單一設定檔。

搜尋成本亦不可忽略。368 項未結問題與逾百份筆記本，令「找到對應自己情境的範例」需要一定時間。官方提供 registry 索引與 make 指令輔助，但要判斷哪份食譜仍適用當前模型，仍需讀者自行核對日期。

出處連結有哪些？

原始碼位於 GitHub 的 anthropics/claude-cookbooks，採 MIT 授權；模型規格與代理文件詳見官方平台。

主要入口是 GitHub 儲存庫 https://github.com/anthropics/claude-cookbooks，README 提供安裝前置條件、資源清單與完整食譜目錄，並連往官方開發者文件與支援中心。

本次改動的原始提交可在 https://github.com/anthropics/claude-cookbooks/commit/bfe50e59dbb4f5546a0af9ca36ebb77e637c9ce1 查閱，逐檔差異包含模型識別碼、Bedrock 端點格式與稽核腳本。索引資料則集中在儲存庫根目錄的 registry.yaml。

總結：Claude Cookbooks 適合哪些開發者？

適合正在評估 Claude API 或準備導入託管代理的團隊，可省下摸索架構的時間；若只需單次呼叫且已有成熟封裝，閱讀官方文件比複製整份儲存庫更有效率。

這份儲存庫的價值建立在「先跑通、再改寫」的使用方式上。開發者可以照抄一份筆記本，換上自己的資料與提示，先確認流程可行，再逐步替換為生產級實作。省下的是架構摸索與參數試錯的時間。

採用前應確認三件事。團隊是否使用 Python 與 uv 工具鏈，這決定範例能否直接執行；是否計畫使用託管代理或代理 SDK，這決定十八份代理食譜的參考價值；以及能否接受每季級別的模型字串更新。

這次改動本身提供一個觀察點。當官方在同一日內把文件、範例、CI 與稽核腳本一併推進到 5.5 世代，跟隨官方設定的專案可以維持低維護成本，自訂模型字串的專案則要為每次換代付出額外工時。
