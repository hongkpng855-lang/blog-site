LangChain 1.5：模型路由與工具風險攔截

2026年11月12日 16:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/langchain-ai/langchain

LangChain 於二零二六年十一月十一日發布 1.5.0，這個累積 149,365 顆星標的代理框架，把模型路由與工具風險攔截兩組中間件由外部套件移入主套件，並終止支援已停止維護的 Python 3.10，最低版本提升至 3.11。

同日發布的 langchain-core 1.8.0 加入決策模型介面，把二元判斷、分類選擇、評分與位置定位統一成一組可組合題型。兩個套件的最小版本互相綁定：langchain 1.5.0 要求 core 至少 1.8.0，仍停留在 Python 3.10 的專案則會解析到 1.4.x 系列。

LangChain 1.5.0 是什麼？

它是 LangChain 框架的主套件版本，以 middleware（中間件）為擴充單位，在代理執行流程的前後插入模型選擇、風險攔截、工具重試與上下文壓縮等行為。

專案建立於二零二二年十月，以 Python 撰寫，採用 MIT 授權，目前有 924 位訂閱者與 732 個待處理議題。它的定位已由早期的鏈式呼叫工具，轉為代理工程平台，核心是 create_agent 搭配可插拔的中間件層。

中間件目錄下現有二十個公開模組，涵蓋工具重試、模型備援、呼叫次數上限、摘要壓縮、待辦清單、個人資料偵測與沙箱執行。本次版本把原本獨立在 langchain-typesafe 的兩組中間件納入同一命名空間，讓使用者改由 langchain.agents.middleware 匯入。

為何這個版本終止支援 Python 3.10？

因為 Python 3.10 已達生命週期終點，官方停止接收安全性修補。維持相容會迫使套件長期帶著舊版分支，故此次直接提高最低版本要求。

版本說明寫得直接：1.5.0 移除對 Python 3.10 的支援，最低支援版本為 3.11，同時要求 langchain-core 至少 1.8.0。仍使用 3.10 的專案在安裝時會自動解析到 1.4.x，不會被強制中斷，但亦不會取得新功能。

這種做法在開源生態常見，代價落在維護方之外。企業內部的執行環境若綁定舊版直譯器，升級前需先協調基礎映像與相依套件，否則會停留在舊分支而被動承接後續的安全風險。

決策模型解決什麼問題？

它把語言模型的判斷輸出約束成四種帶機率與信心的結構化答案，讓程式可以按門檻決定後續行為，避免直接解析自由文字造成的格式不穩定。

langchain-core 1.8.0 新增的 langchain_core.decisions 模組定義了四種題型。Noul 回答一個是或否的機率，取值範圍為零到一。Choice 從給定的候選標籤中選一個，並附上完整機率分佈與信心值。Score 在有序評分表上給出期望位置。Box 則回傳圖像中目標區域的四邊座標，以長寬比例表示。

答案解析後仍保留分佈，應用可以自訂門檻，不必照抄供應商的預設值。介面以 BaseDecisionModel 為基底，繼承者可實作同步的 _classify，需要時再補非同步版本，其餘如回呼、追蹤與詞元統計由基底類別處理。

官方文件把適用場景寫得很清楚：分類、路由、風險評估與人工覆核的前置篩選。它的價值在於把「模型覺得怎樣」變成可量測的數字，而不是一段需要正則表達式拆解的句子。

ModelRouterMiddleware 如何選擇模型？

它在代理執行前只分類最後一則人類訊息一次，把選中的標籤與機率存入代理狀態，該次執行的所有模型呼叫都改用對應模型，中途不再重新判斷。

路由設定由兩部分組成。ModelChoice 描述一個可用模型與適用任務的判準，模型可以傳入字串交由 init_chat_model 解析，也可以直接傳入模型實例。instructions 則指示分類器在選擇時應遵循的原則，例如優先採用成本最低且足以勝任的模型。

分類結果以 ChoiceAnswer 形式寫入代理狀態的 model_route 欄位，之後每次模型呼叫都經過 wrap_model_call，把請求的模型替換為所選模型。單次分類的設計控制了成本，也令同一輪對話的模型保持一致，避免前半段與後半段由不同模型接續而語調跳動。

失敗處理方式是此設計的關鍵取捨。分類器出錯時錯誤會向上拋出並終止該次執行，不會默默退回預設模型。這個選擇讓故障顯而易見，代價是多了一個必須可用的外部依賴。若需要把路由限制在免費模型池內，可參考 FreeLLMAPI 的配額導向路由設計。

AutoModeMiddleware 如何在工具執行前攔截？

它只審查明確列入清單的工具，在執行前向決策模型詢問「這次呼叫是否具風險」，機率達 0.5 或以上即回傳錯誤訊息，工具本體不會被呼叫。

預設的風險判準寫得相當嚴格。工具描述與參數一律視為資料而非指令，只有明確的使用者訊息可以授權執行；破壞性操作、憑證存取、對外分享、安全繞過、持久化與受保護資源的變更，全部歸類為有風險。

分類器收到的輸入包含待執行的工具呼叫、工具描述，以及最近三十則訊息。未列入清單的工具直接放行，不進入分類。被攔截時回傳的是錯誤型態的工具訊息，內容包含工具名稱與風險機率，代理可據此改走其他路徑。

必須留意的是它只負責阻擋，不負責取得人工同意。需要暫停等待人工確認的場景，仍要搭配既有的中斷機制。兩者職責不同：一個是自動否決，另一個是停下來問人。

兩個中間件有哪些限制？

兩者都標記為 beta，介面可能隨時變動；分類器需自行接入供應商，路由只依最後一則人類訊息判斷，長對話中的前期任務描述不會被納入。

路由只看最後一則人類訊息，這是明確的簡化。若任務描述分散在多輪對話，較早的約束條件不會進入分類視野。專案對缺少人類訊息的狀態直接拋出錯誤，也意味著由排程或事件觸發的無人身分流程需另行處理。

風險攔截的門檻固定為 0.5，未開放設定。對於後果嚴重的操作，這個門檻偏寬鬆；對於唯讀操作，則可能出現不必要的阻擋。開發者可透過自訂指令與判準調整行為，但無法直接改動臨界值。

分類器方面，目前有兩條路徑。官方合作套件提供 OpenAI 決策模型實作，另一條是 TypeSafe 的分類器，需設定環境變數後使用。langchain-typesafe 0.1.0 同日發布，其舊有的實驗性中間件路徑已標記棄用，預計在 0.2.0 移除。

如何升級到 1.5.0？

先確認直譯器為 3.11 以上，再同步升級 core 至 1.8.0 與主套件至 1.5.0，最後把舊的 typesafe 中間件改由主套件匯入。

第一步是檢查執行環境。虛擬環境、容器映像與持續整合設定三處都要確認直譯器版本，任何一處停留在 3.10 都會令升級無法生效。

第二步是同步兩個套件。langchain 1.5.0 要求 core 至少 1.8.0，若只升級其中一個，套件管理員會解析出彼此不相容的組合。建議在同一次提交中固定兩者版本，並保留鎖定檔。

第三步是改寫匯入。舊路徑 langchain_typesafe.experimental.middleware 已棄用，應改為 from langchain.agents.middleware import AutoModeMiddleware, ModelRouterMiddleware，並以參數傳入分類器實例。這一步改動幅度小，但若沿用舊路徑，未來升到 0.2.0 時會直接中斷。

LangChain 的專案數據如何？

專案現有 149,365 顆星標、25,108 次分叉、924 位訂閱者與 732 個待處理議題，以 Python 撰寫並採用 MIT 授權，最近一次提交在十一月十一日。

發布節奏相當密集。單看 core 套件，十一月四日為 1.7.5，十一月五日 1.7.6，十一月十日 1.7.7，十一月十一日 1.8.0，一週內推進四個版本。主套件則在十一月四日與十日各推出修補版，十一日跟進 1.5.0。

待處理議題維持在七百餘個，與每週合併大量外部貢獻的模式一致。對導入方而言，這個數字同時提示應在鎖定檔中固定版本，並在升級前先跑一次既有測試，因為修補版之間亦可能夾帶行為變更。

出處連結有哪些？

原始碼、版本說明與議題追蹤位於 GitHub 的 langchain-ai/langchain 儲存庫，官方文件站點提供中間件與決策模型的用法說明。

版本說明列出本次合併的四項變更與一項文件補充，並附上與 1.4.10 的完整差異連結。決策模型的題型定義位於 core 套件的 decisions 目錄，兩個中間件的實作則在主套件的 agents/middleware 目錄，兩處皆有對應的單元測試。上一輪的 core 1.7 改動集中在工具呼叫串流，可對照 LangChain Core 1.7 的串流修正。

## 常見問題有哪些？ 以下整理升級版本要求、路由適用範圍、攔截門檻與分類器選擇四類問題，涵蓋導入前最常遇到的判斷點，並標明官方尚未開放的設定項目。 ### Python 3.10 的專案還能繼續用嗎？ 可以，但會停留在 1.4.x 系列。1.5.0 的最低要求為 Python 3.11，若專案無法升級直譯器，安裝時不會取得新功能，亦不會收到後續修補，長期需評估遷移時程。 ### 路由會每次呼叫都重新判斷嗎？ 不會。分類在代理執行前只發生一次，結果寫入代理狀態後於該次執行內重複使用。同一輪對話中即使工具回傳多次，模型選擇保持不變。 ### 攔截門檻可以調整嗎？ 目前不行。風險機率達 0.5 即攔截，臨界值寫在實作內。可調整的是分類指令與正反判準的描述，透過改變問題定義間接影響判定結果。 ### 沒有配置分類器會怎樣？ 建構時會觸發驗證錯誤，因為分類器為必填參數。這個設計有別於舊版可省略的寫法，遷移時需明確傳入實例，否則啟動階段即失敗。 ### 被攔截的工具會重試嗎？ 不會自動重試。被攔截的呼叫回傳錯誤型態的工具訊息，是否改走其他路徑由代理自行決定。需要重試邏輯時，應另外掛載工具重試中間件。 ### 這兩個中間件可以用在非 Python 專案嗎？ 目前不行。決策模型介面與兩個中間件都實作在 Python 套件內，其他語言的官方客戶端尚未見對應模組。

總結：哪些團隊適合升級？

已將代理投入生產、需要控制模型成本或限制高風險工具呼叫的團隊最適合；仍在原型階段且直譯器為 3.10 的專案，可等待環境整理完成後再跟進。

這次版本的實質變化不在功能數量，而在責任分配的位置。模型選擇與工具審查過去散落在應用程式碼裡，現在被收進框架的中間件層，成為可設定、可觀測的組件。

代價是依賴增加。路由需要一個可用的分類器，攔截需要一個判斷準確的分類器，兩者都引入外部服務與額外延遲。對於工具數量少、任務型態固定的專案，硬編碼的模型選擇仍然更直接。

值得留意的是設計上的兩個保守選擇：路由只分類一次，攔截只阻擋不求人。兩者都把複雜度推回應用層，換取行為的可預測性。這種取捨是否合適，取決於團隊願意為可預測性付出多少自訂成本。
