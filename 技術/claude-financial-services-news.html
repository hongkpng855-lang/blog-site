Anthropic 開源 Claude 金融代理：41,077 星

2026年11月07日 12:00 • 閱讀時間 2 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/anthropics/financial-services

Anthropic 於二零二六年二月開源金融服務代理專案，累積 41,077 顆星標、5,715 個分支，採 Apache 2.0 授權。專案把投資銀行、股權研究與私募股權的流程拆成十個具名代理與六組垂直技能，附十二個 MCP 連接器，同一份系統提示可安裝為外掛或經 API 部署。

這批內容的份量不在模型，而在流程。過去一年金融業對生成式 AI 的試用多停留在聊天視窗，真正的門檻是如何把估值模型、財報比較、盡職調查清單這些既有作業標準化為可重複執行的步驟。專案把行業慣例寫成技能檔案，等於把顧問與分析師的隱性知識攤開成可檢視的文字。

專案首頁有一段醒目的免責聲明，值得在閱讀功能之前先看清楚。

Claude 金融服務代理是什麼？

它是 Anthropic 開源的金融作業參考實作，內含十個端到端代理與六組垂直技能。所有產出皆需專業人員簽核，代理不執行交易或下投資建議。

專案定位為參考範本，而非可直接上線的產品。每個代理以它負責的流程命名，例如 pitch-agent 處理可比公司分析與槓桿收購模型，最終輸出一份帶品牌版型的簡報；gl-reconciler 則專門找出總帳對帳的差異，追溯成因後送交簽核。

這種命名方式反映設計取向。開發團隊沒有提供一個通用助手，而是把金融業既有的職務分工直接映射為目錄結構。使用者按工作性質安裝對應代理，代理本身自帶它需要的技能，安裝一個目錄即可運作。

專案建立於二零二六年二月二十三日，主要語言標記為 Python，但實際內容以 Markdown 與 YAML 為主，Python 僅用於部署與校驗腳本。最近一次提交在十月二十八日，處理的是核心外掛設定檔的 JSON 格式錯誤。

這個專案為什麼值得關注？

金融業對 AI 的採用瓶頸向來是流程與合規，而非模型能力。此專案把行業慣例寫成可檢視的技能檔案，並明確限定代理只起草、不決策，為企業提供一個可審計的起點。

企業導入 AI 代理時最常遇到的問題是責任邊界模糊。專案對此的處理相當乾脆，README 明列代理不執行投資建議、不執行交易、不約束風險、不記入總帳、不核准客戶開戶，每一項產出都停留在待簽核狀態。

這個設計同時降低技術與法務的評估成本。資訊部門看到的是純文字與設定檔，沒有編譯產物也沒有外部依賴；法務部門看到的是明確的行為邊界與可逐行審閱的提示內容。兩邊都能在自己熟悉的層面上完成審查。

從生態角度觀察，專案納入 LSEG 與 S&P Global 兩個合作夥伴外掛，顯示資料供應商願意把自家資料源接進這套結構。對金融資料商而言，被代理直接調用的價值高於被網頁介面查詢。

專案包含哪些代理與技能？

十個代理分屬四個職能：覆蓋與顧問、研究與建模、基金行政、營運與開戶。垂直技能包提供斜線指令，例如 /comps、/dcf，可單獨安裝而不啟用完整代理。

覆蓋與顧問職能包含 pitch-agent 與 meeting-prep-agent。前者的工作是把可比公司分析、先例交易與槓桿收購模型串成一份簡報，後者則在客戶會議前整理簡報包。

研究與建模職能有三個代理。market-researcher 由產業或主題出發，產出產業概況、競爭格局與同業比較；earnings-reviewer 把財報電話會議與申報文件轉成模型更新與報告草稿；model-builder 直接在 Excel 中建立現金流折現、槓桿收購與三表模型。

基金行政與財務營運職能包含四個代理。valuation-reviewer 讀取普通合夥人提供的資料包並執行估值範本，gl-reconciler 處理總帳對帳，month-end-closer 負責應計項目與差異說明，statement-auditor 在有限合夥人報表發出前進行稽核。營運職能則由 kyc-screener 處理開戶文件解析與規則引擎比對。

六組垂直技能包構成底層能力。核心的 financial-analysis 攜帶所有建模技能與資料連接器，其餘五組按業務線拆分，涵蓋投資銀行、股權研究、私募股權、基金行政與營運。使用者若只需要斜線指令，可以只裝垂直技能包而不啟用完整代理。

兩種部署方式有什麼差別？

Cowork 外掛適合個人與小團隊，貼上儲存庫網址即可挑選安裝。Managed Agents API 適合企業，經部署腳本建立子代理並由自家引擎派送事件。

Cowork 路徑的操作成本最低。使用者在外掛設定中貼上儲存庫網址，市場清單會列出所有代理與垂直技能，勾選後即完成安裝。另一種做法是把 plugins 目錄下的任一子目錄壓成壓縮檔上傳，適合內部已經改寫過的版本。

Managed Agents 路徑針對需要自建流程引擎的團隊。專案提供部署腳本，會解析檔案引用、上傳技能、建立葉節點子代理，最後把協調代理提交到 /v1/agents 端點。每個代理目錄下的設定檔會指定系統提示、可用技能與子代理層級。

兩條路徑共用同一份檔案，因此調整只需做一次。這個設計解決了企業常見的分裂問題：試用階段跑在一個環境，正式部署換成另一套實作，兩邊行為逐漸分歧。專案要求同一份系統提示與同一組技能雙邊引用，讓原型與生產環境保持同步。

專案另附一套 Microsoft 365 增益集的管理工具，供資訊部門在自己的雲端環境中派送，可指向 Vertex AI、Bedrock 或內部模型閘道，而不必經由 Anthropic 的介面。

資料連接器如何接上金融資料源？

十二個 MCP 連接器集中在核心外掛，涵蓋 FactSet、PitchBook、S&P Global 等資料商。多數需另備訂閱或 API 金鑰，並非開箱即用。

連接器清單反映目標客群的付費能力。終端機資料、研究平台與文件儲存三類系統各有對應服務，包括 Daloopa、Morningstar、FactSet、Moody’s、MT Newswires、Aiera、LSEG、PitchBook、Chronograph、Egnyte 與 Box，另加 S&P Global 的 Kensho 整合端點。

這些端點以遠端 MCP 服務形式提供，設定集中於單一檔案，其餘外掛共用同一份連線定義。若企業已有內部資料平台，替換設定檔中的端點即可接上自家系統。

授權提醒寫在 README 內。多數連接器需要資料商另行開通權限或計費，專案本身不含任何資料使用權。這一點對評估成本相當關鍵，因為代理的實際支出很大程度取決於資料訂閱而非模型呼叫。

專案架構有什麼技術特點？

整份專案為純檔案結構，僅 Markdown 與 YAML，沒有建置步驟。同步腳本把垂直技能複製到各代理目錄，校驗腳本則檢查清單格式、跨檔引用與技能是否漂移。

架構的核心是單一來源原則。技能在垂直外掛中撰寫一次，再由同步腳本複製到需要它的代理目錄，因此同一項能力不會出現兩份互不相符的版本。

三支腳本構成維護防線。check.py 檢查每個清單檔的格式，驗證所有跨檔引用可解析，並在任何捆綁技能與來源漂移時回報失敗；validate.py 處理設定內容的結構驗證；deploy-managed-agent.sh 負責把本地目錄轉成雲端代理。專案要求提交前執行檢查，把一致性變成可自動化的門檻。

檔案化的取捨相當明顯。好處是審閱、版本控制與差異比對都能沿用既有工程流程，任何人都能直接讀懂代理會做什麼。代價是缺乏型別約束，提示與技能的正確性只能靠人工審閱與少量格式檢查，無法用編譯器攔截語意錯誤。

數字結構值得解讀。四萬餘顆星標對應五千七百餘個分支，比例約為七比一，低於多數熱門專案的十比一以上水準，顯示取用者不只按讚，也實際複製內容進行改寫。待處理議題九十八項與待合併請求一百三十八項的比例，則反映外部貢獻意願高於維護速度。

金融業採用 AI 代理有哪些風險？

主要風險有四類：模型誤讀財務數據、連接器權限過寬、產出被誤當成建議、子代理委派的可追溯性。專案以人工簽核與行為禁制應對，企業仍需自行補上內部控制。

數據準確性是第一道關卡。專案明言代理只負責起草分析與對帳等成品，最終判讀由合格專業人員負責。模型在處理非結構化申報文件時仍可能錯配單位或期間，因此專案把多數產出設計成待審狀態。

權限管理是第二道。多個資料連接器需要長期有效的 API 憑證，若集中存放於單一設定檔，憑證外洩的影響範圍會擴及整個資料訂閱。專案在十月的一次提交中把憑證從查詢字串移到網址片段，正是針對這個風險的收緊。

子代理委派機制仍屬研究預覽階段，專案在對應說明中標示此為預覽能力，並附上各代理的安全與交接指引。企業若要把代理放進受監管的流程，仍需自行設計日誌留存、輸出覆核與異常中止的機制。

出處連結有哪些？

原始碼位於 GitHub 的 anthropics 帳號下，採 Apache 2.0 授權。文件分層於各代理目錄與部署說明，另附校驗與同步腳本供自建流程使用。

儲存庫的目錄分層清楚。plugins 之下分成代理外掛、垂直外掛與合作夥伴外掛三區，managed-agent-cookbooks 為每個代理提供雲端部署範例，scripts 目錄放置部署、校驗與同步四支工具。

說明文件的組織方式值得留意。每個代理目錄自帶系統提示與所需技能，安裝單一目錄即可運作，減少使用者追蹤跨目錄依賴的負擔。

貢獻規範要求提交前執行校驗腳本，並在新增技能後跑同步腳本，把變更傳播到所有捆綁該技能的代理。

總結：這個專案適合什麼團隊？

已具備資料訂閱與合規流程的中大型金融機構最適合，可把它當成內部工具的骨架。個人開發者與新創則適合閱讀其提示設計與責任邊界劃法，作為自建流程的參考。

專案的價值在於把一個高門檻行業的作業知識寫成公開可讀的檔案。對金融機構而言，這是一份現成的流程骨架，省去從零討論代理該做什麼、不該做什麼的時間；對外部開發者而言，這是一份難得的樣本，可以看到專業領域如何把責任邊界落實在提示與指令設計中。

限制需要如實看待。專案明確定位為參考範本，README 反覆強調需按自家流程調整，並非可直接投產的產品。十二個資料連接器的多數需要另行付費開通，實際可用範圍取決於企業既有的訂閱。代理產出的正確性最終仍由簽核者承擔，這個責任不會因自動化而轉移。

務實的起步方式，是挑一個邊界清楚且產出可驗證的流程，例如財報比較或總帳對帳，先以現有資料跑通一次完整鏈路，確認輸出品質與憑證管理方式，再擴大到需要跨代理協作的場景。
