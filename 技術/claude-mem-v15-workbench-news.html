claude-mem 15.5 開源：代理記憶變成工作台

2026年10月29日 20:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/thedotmack/claude-mem

claude-mem 是一套開源的代理記憶系統，在 GitHub 累積 104,156 顆星標與 9,190 次複製，以 TypeScript 撰寫、採 Apache 2.0 授權。專案於 2026 年 10 月下旬連續發布 v15.0 至 v15.5 六個版本，把記憶插件擴充為附帶工作台的系統。

claude-mem 是什麼？

claude-mem 是一套開源的代理記憶系統，透過生命週期鉤子擷取代理的工具使用紀錄，壓縮成語意摘要並注入後續工作階段，讓編碼代理在跨工作階段時仍保有專案脈絡。

專案的運作方式建立在六個生命週期鉤子上，包括工作階段開始、提示送出、工具呼叫前後、回合結束與工作階段結束。每個鉤子都是一行無殼層指令，由安裝器放進系統路徑的啟動器執行。

紀錄寫入本地的 SQLite 資料庫，並以 Chroma 向量資料庫支援語意與關鍵字的混合檢索。使用者的操作介面是一個由 Bun 管理的本機 HTTP 服務，同意安裝的代理工具包括 Claude Code、Codex、Gemini、Copilot、OpenCode 與 OpenClaw。

專案自 2025 年 8 月建立至今累計 379 個版本與 312 位貢獻者，版本節奏密集，這次 v15 系列屬於功能層級的整併。

v15 系列帶來哪些結構性改動？

六個版本分別處理檢索方式、介面形態與留存機制。v15.0 改寫召回流程，v15.1 換上即時工作台，v15.3 加入交付檔案，v15.4 引入焦點領域。

版本序列顯示這批改動沿著同一條主線推進。10 月 20 日的 v15.0.0 先把記憶召回改為三步式，10 月 25 日的 v15.1.0 把檢視介面從靜態頁面換成 React 即時工作台，同日 v15.2.0 把首次安裝導向瀏覽器流程。

10 月 26 日的 v15.3.0 引入交付檔案保存，讓代理產出的簡報、報告與網頁在卡片上一鍵可取。10 月 28 日的 v15.4.0 把工作台重新組織為焦點領域，10 月 29 日的 v15.5.0 則集中修補遮蔽規則與跨代理的相容性。

功能重心由「把記憶塞回提示」轉向「把記憶整理成可檢視的工作紀錄」。這項轉向對重度使用者的影響，比任何單一功能更明顯。

My Work 工作台解決了什麼問題？

原本的檢視頁只列出記憶條目，使用者難以回答「哪些請求仍在進行」。My Work 以每個人類請求為單位建立卡片，顯示進度、目標對齊與交付檔案，並保留待處理的審閱隊列。

v15.1.0 以 React 重寫本機檢視頁，資料直接取自執行中的 worker，更新即時送達。舊有的靜態檢視頁並未移除，改為掛在 /viewer 路徑，供既有使用者沿用。

卡片的組織邏輯值得留意。它不以工具呼叫或檔案為單位，而以一次人類請求為單位，把該請求底下的工具使用、子代理與產出收攏在同一張卡片。

v15.4.0 進一步在工作台頂層加入焦點領域。每個領域附有一句目標描述、合併進度、使用者原話與尚未開始的待辦，系統也會自動建議新領域，交由使用者決定保留、改名、合併或略過。

記憶檢索為什麼改成三步式？

舊流程一次取回完整內容，容易把大量無關紀錄塞進提示。新流程先取精簡索引，再查看時間軸脈絡，最後只取相關編號的細節，官方稱可節省約十倍 token。

v15.0.0 把預設召回改為 Smart 模式，由代理在三個步驟之間自行判斷相關性。第一步 search 回傳精簡索引，每筆約五十至一百 token；第二步 timeline 顯示特定結果附近的時間軸；第三步 get_observations 只取已篩選編號的完整內容。

原本的一步式查詢改名為 dumb_search，官方對它的描述相當直白，說明它不做相關性判斷、速度快但內容淺。舊有的引導模式與續接游標在此版移除，既有 MCP 連線需要重新整理才會載入新的工具目錄。

這項改動把判斷成本從檢索層轉移到模型層。代理需要多一輪推理，換來的是更小的提示佔用。

安裝流程如何變成瀏覽器引導？

v15.2.0 把首次安裝改為瀏覽器流程，掃描本機近三十日的代理歷史，抽出目標、規則與請求分組，使用者確認儲存方式後才完成設定，可選擇留在家中或跨裝置使用。

指令仍未改變，執行 npx claude-mem install 後會依序完成安裝、掃描、顯示與儲存選擇四個階段。掃描階段讀取近三十日的本機代理歷史，排除已設定的專案與代理自行產生的提示，並在顯示之前完成去重與遮蔽。

專案同時擴充了代理清單。除 Claude Code 之外，安裝器現時支援 OpenCode 1.3.4 以上版本、T3 Code、Antigravity CLI、Pi 與 DeepSeek Harness，各自透過原生插件或工作階段紀錄擷取。

開發團隊亦標明 npm 全域安裝只會取得函式庫，不會註冊鉤子與 worker，正式安裝仍須走上述指令或插件市集。

雲端與本地的資料邊界在哪裡？

本地的紀錄、摘要與向量索引存放於使用者機器。雲端路徑把過濾後的提示壓縮上傳做意圖抽取，使用者可改用自備金鑰或本機觀察器。

安裝引導的掃描階段有一個需要留意的環節。經過過濾與遮蔽的使用者提示會以 gzip 形式上傳至 CMEM Cloud 進行意圖抽取，回傳的目標、規則與請求分組再填入本機快照。

專案為此提供多條退出路徑。使用者可以指定 --provider 參數、設定 CLAUDE_MEM_ONLINE_OPTIN=false，或在持續整合等非互動殼層執行，安裝器便不會進行任何帳號互動。

既有隱私機制仍然有效。提示中標記為私密的區段不會留下紀錄，遮蔽規則也在 v15 系列持續加厚，涵蓋金鑰名稱、權杖格式與多種資料庫密碼鍵。

v15.5.0 修補了哪些安全細節？

此版擴大遮蔽覆蓋面，涵蓋裸 token、secret 與 api_key 鍵名、bearer 權杖與 Slack 權杖格式，並修正 Windows 短路徑查詢問題。

遮蔽規則的補強集中在鍵名辨識。過去的規則依賴完整鍵名比對，遇到只寫 token 或 secret 的鍵便會漏掉，此版改為一併處理這類裸鍵名。

權杖格式亦有新增。Slack 的應用層權杖與更新權杖前綴被納入辨識範圍，Authorization 標頭物件內的 bearer 值同樣列入。

跨代理相容性同時修正。Antigravity 的 MCP 呼叫改用真實工具名稱與穩定識別碼記錄，專案脈絡亦可正確解析；Windows 的八點三短路徑查詢由 %~I 改回 %I，修正了路徑展開的錯誤。

升級時需要注意什麼？

舊版的一步式檢索與續接游標已被移除，依賴舊介面的腳本需要改寫。MCP 連線必須重新整理，本機檢視頁的網址亦已變更，舊連結會跳到 /viewer。

接口變更是升級時的主要成本。mem_search 與 flash_search 的呼叫方式不再支援，若要維持一步式行為，需明確改用 dumb_search。

執行環境的要求沒有放寬。系統需要 Node.js 20 以上版本、可支援插件的 Claude Code，以及 Bun 與 uv，兩者會在缺少時自動安裝。

專案現時有 141 個未結問題，活躍度反映功能仍快速調整。生產環境部署宜固定版本，並先行測試鉤子在自訂殼層下的行為。

出處連結有哪些？

原始碼位於 GitHub 的 thedotmack/claude-mem，官方文件站 docs.claude-mem.ai 提供安裝與整合指引，版本記錄另附各版改動明細。

總結：claude-mem v15 適合什麼使用者？

適合長時間使用編碼代理、且需要跨工作階段追溯決策的團隊。若只偶爾使用代理，或對提示上傳雲端有顧慮，自建輕量紀錄方式仍是成本較低的選擇。

這批版本的價值在於把記憶從隱形基礎設施變成可見的工作紀錄。使用者可以逐項檢視代理做過什麼、哪些請求仍在進行、哪些交付檔案已經落地。

代價是複雜度提升。工作台、焦點領域與交付目錄各自需要設定與維護，安裝引導亦引入帳號流程，使用者需要清楚自己選了哪一條資料路徑。

對已累積數百個工作階段的專案，這套整理能力的回報相對明確。對剛起步的使用者，先確認遮蔽規則與儲存位置是否符合組織要求，再決定是否深入採用。
