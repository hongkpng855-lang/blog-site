Streamlit 1.67 開源：資料 App 變成 AI 可操作工具

2026年11月18日 04:00 • 閱讀時間 4 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/streamlit/streamlit

Streamlit 是 Python 資料應用框架，GitHub 累積 46,399 顆星、Apache 2.0 授權。2026 年 11 月 5 日發布的 1.67 版把 agent API 轉為公開，代理可透過 HTTP 或 MCP 端點驅動同一個應用，讀取元件狀態並取回資料表格，不必另外建置一套 API。

Streamlit 是什麼？

Streamlit 是以 Python 撰寫資料應用的框架，單一檔案即可產生儀表板、預測與工作流程應用，前端、狀態管理與 API 層均由框架處理。

專案由 Streamlit 團隊於 2019 年 8 月建立，主要語言為 Python，採 Apache 2.0 授權。README 統計，GitHub 上已有超過一百萬個儲存庫依賴此框架，定位是資料應用的第一選擇。

框架的核心主張是減少層數。開發者只需撰寫 Python，瀏覽器端的介面、狀態同步、快取、登入與主題一致性由框架承擔。專案文件把這件事描述為「生成的應用很便宜，擁有它的成本不便宜」，指向的是長期維護負擔而非開發速度。

維護者的提交帳號帶有 sfc-gh 前綴，與 Snowflake 的企業帳號命名一致，這也解釋了 README 中「可原生部署於 Snowflake 內」的敘述。專案同時提供免費的 Community Cloud，連接 GitHub 儲存庫即可取得 streamlit.app 網址。

Streamlit 1.67 版的 agent API 是什麼？

agent API 是 1.67 版公開的介面，代理以 HTTP POST 送出元件值，取回整頁元素樹，另可透過 MCP 端點接入 Claude、ChatGPT 或 Cursor。

這套介面預設關閉，由 server.enableAgentApi 開啟，並標記為實驗性。開啟後，程式可向 /_stcore/agent/interact 送出 JSON 格式的元件值，取回完成的頁面，回應內容是一棵以 st.* 指令命名的元素樹。

規格描述另有一個 /_stcore/agent/openapi.json 端點，用來描述協定本身。搭配的 MCP 端點位於 /_stcore/agent/mcp，貼上一條網址即可把應用加入 Claude、ChatGPT、Cursor、VS Code 或 Claude Code，兩個固定工具分別是 interact 與 get_data。

代理驅動應用需要哪些資源控制？

1.67 版一併公開五個 server.agent 參數，涵蓋等待逾時、工作階段存活時間、並行上限與預覽列數，讓部署方能為代理流量設定邊界。

代理與人類使用者最大的差異是呼叫頻率。單一使用者在瀏覽器上操作，一次只發出一個請求；代理可以在數秒內連續改動數十個元件。若沒有上限，一個失控的迴圈就足以讓應用無回應。

五個參數因此在 1.67 版一併移除隱藏標記，納入 streamlit config show 與官方設定文件：server.agentWaitTimeout 控制單次互動的等待時間，server.agentSessionTTL 決定工作階段的存活長度，server.agentMaxSessions 限制並行數量，server.agentPreviewRows 設定資料預覽的列數上限。這些選項過去只存在於規格文件，部署者無法從設定介面得知。

同一個版本也為快取加上預算：server.maxCacheDataSize 提供全域的資料快取上限，st.cache_data 則新增逐函式的 max_size。對於長時間由代理反覆呼叫的應用，這兩項設定直接影響記憶體曲線。

為什麼資料應用要變成 MCP 伺服器？

因為代理需要讀寫真實資料才有決策價值。應用本身已是資料入口，接上 MCP 後代理沿用同一套邏輯與權限，不必另建介面或複製業務規則。

傳統做法是為代理另寫一組工具函式，把應用內的查詢、篩選與寫入重新實作一遍。這種做法會產生兩份邏輯，時間一久必然分歧，而分歧出現在資料權限上時，後果並不只是顯示錯誤。

MCP 端點的設計選擇是讓應用本身成為工具。代理呼叫 interact 時，走的是與瀏覽器使用者相同的程式路徑，同一組身分檢查、同一組元件狀態。官方規格在選擇回應碼時曾遇到一個細節：當 API 關閉，MCP 路由回應 400 而非 403，因為官方 TypeScript 客戶端會把 403 解讀為授權失敗，既不退回初始化流程，也不顯示訊息。

規格另列出四項後續工作，包含在 serverInfo 補上應用標題與描述、作者宣告 interact 為唯讀、為 st.login 應用加入 OAuth 登入，以及為文字與 JSON 加上分頁。這些項目顯示目前的實作仍在補齊企業場景所需的基本條件。

代理與測試工具如何分工？

代理透過 agent API 在運行中的應用上驗證改動，AppTest 則把同一組檢查留在 CI。前者觀察真實渲染結果，後者防止回歸。

專案隨附的 developing-with-streamlit 技能在 1.67 版加入一條規則：代理在回報完成之前，必須先在運行中的應用上驗證每一項改動。做法是啟動只監聽本機的實例並開啟 API，驅動被改動的元件，讀取狀態與受影響的元素，同時觀察伺服器日誌中快照看不到的警告。

測試與驗證的分界寫在技能的 references/testing.md 開頭。AppTest 適合在持續整合中執行，速度快且不依賴瀏覽器；agent API 適合檢查真實渲染；需要完整前端行為時，則由 Playwright MCP 這類瀏覽器工具接手。三者並非替代關係，而是成本與覆蓋範圍的取捨。

這個安排回應的是一個具體問題。編碼代理在一輪對話中可能改動數十行，若只依賴它自行宣稱完成，錯誤會累積到使用者開啟頁面才浮現。把驗證動作寫進技能，等於把檢查義務從人轉移到流程。

如何快速開始使用 Streamlit？

先以 pip 安裝，撰寫單一 Python 檔案，執行 streamlit run 啟動。若要代理協助，先在專案目錄執行 streamlit skills 安裝對應技能。 

# 安裝（需求 Python 3.11 以上）
pip install streamlit

# 在專案目錄安裝對應版本的代理技能
streamlit skills

# 啟動應用
streamlit run streamlit_app.py

streamlit skills 是 1.67 週期新增的指令。它會安裝與當前 Streamlit 版本相符的技能檔，支援 Claude Code 以及讀取共用 .agents 目錄的代理，目的是讓代理依循當版最佳做法，而非憑訓練資料中的舊版印象作答。

安裝後即可用自然語言描述需求，例如要求建立一個讀取 sales.csv 並提供價格與成長假設滑桿的預測應用。若不使用代理，官方 README 提供一份完整範例：以 st.cache_data 載入歷史資料，用 st.slider 調整月成長率，以 st.data_editor 讓規劃人員直接修改預測值，最後以 st.button 提交並寫入資料庫。

企業環境另有三個部署選項：自建雲端環境、Community Cloud 與 Snowflake 原生部署。st.login 提供內建登入，無需自行串接身分供應者。

Streamlit 的技術架構有哪些關鍵設計？

架構以單層 Python 為核心，搭配片段重跑、背景快取刷新與 URL 綁定篩選。元件選擇事件讓儀表板可交叉篩選，無需自行實作前端狀態同步。

效能設計集中在兩個方向。@st.fragment 讓單一區塊獨立重跑，使用者操作圖表時不會觸發整頁重新計算；@st.cache_data 支援 ttl 與 refresh_mode="background"，讓快取的查詢在背景更新，使用者不必等待冷啟動。

互動能力則靠事件回傳。on_select 讓圖表與表格的選取結果回到 Python 端，可實作連動的下鑽與交叉篩選；綁定 bind="query-params" 的篩選條件會寫入網址，任何一個檢視狀態都能直接分享。

資料層的處理方式是按需載入。表格隨捲動逐段取列，讓大資料集維持可用的反應速度；原生圖表涵蓋多數視覺化需求，ECharts、Altair 與內建圖表會在資料量增長時自動切換至較快的渲染路徑。1.67 版另讓 st.echarts_chart 以 Arrow 格式傳送資料框，並在圖表下方顯示對應的資料表。

擴充路徑留了兩個出口。需要高度客製的畫面時可寫自訂元件，以 React 或任何前端技術實作；需要 webhook 或自有 API 路由時，可用 st.App 挂載。

Streamlit 在生態上處於什麼位置？

它以最低層數換取維護穩定性，與 BI 工具、自建 React 前後端形成三種取捨。對代理場景而言，應用同時是介面與工具，這是差異化所在。

與 BI 工具相比，Streamlit 的優勢在於邏輯不受限。任何 Python 函式庫都能直接呼叫，模型推論、最佳化求解與外部 API 整合都不需要在工具框架內找對應元件；代價是複雜的企業級治理功能需要自行補齊。

同屬 Python 生態的 Gradio 以模型示範介面為起點，元件導向的設計適合快速展示單一模型；Streamlit 則把範圍擴展到多頁儀表板與工作流程應用，兩者面對的場景不同。

與自建前後端相比，差異在於擁有成本。由代理生成的 React 前端、Python 後端與中間 API 三份程式碼，需要有人審查、保持同步並長期修補；單層 Python 把這部分轉為框架責任。專案同時強調破壞性變更極為罕見，多數數年前的應用仍可在最新版運行。

貢獻模式值得注意。README 明確表示已暫停接受維護團隊以外的拉取請求，但仍歡迎缺陷回報、功能建議與自訂元件貢獻。這種封閉核心、開放周邊的安排，常見於已有商業母體的開源專案，也意味著外部開發者難以影響框架走向。

Streamlit 有哪些限制與風險？

agent API 仍標記實驗性且預設關閉，MCP 僅有兩個工具，文字與 JSON 尚無分頁，OAuth 登入與唯讀宣告仍在後續清單。

實驗性標記不只是一句免責。規格列出的後續項目包含企業採用時會直接詢問的幾件事：應用在 serverInfo 中的名稱與描述、作者能否宣告某個應用為唯讀、以及 st.login 應用在代理連線時如何完成授權。這些缺口意味著現階段適合試點，不適合直接放上生產環境。

第二項風險是並行行為。代理可在極短時間內連續觸發互動，而 Streamlit 的執行模型以腳本重跑為基礎。即使有 agentMaxSessions 與 agentSessionTTL 控制，開發者仍需自行確認應用在併發呼叫下的資料一致性，特別是涉及寫入的流程。

第三項是相容性清理。1.67 版移除部分隱藏的設定項並重寫描述，st.echarts_chart 的資料傳輸改為 Arrow，若先前依賴舊行為的私有欄位，升級時需要檢查。專案雖以穩定著稱，這一輪改動的範圍仍橫跨設定、圖表與資料格式。

原始碼、版本說明與代理介面規格均位於 GitHub 的 streamlit/streamlit 儲存庫，設定文件與技能說明另見官方文件站。

  • 官方設定文件：https://docs.streamlit.io

總結：Streamlit 適合什麼團隊？

適合已有 Python 資料流程、希望代理與人員共用同一介面的團隊，以及需快速交付內部儀表板與審批流程的組織。需要完全自訂前端或成熟代理授權機制的團隊，宜再等。

這個版本真正的訊號不在功能數量，而在定位轉向。把框架描述為代理原生，等於承認未來有相當比例的應用操作不會由人發起。當應用同時是介面與工具，維護的對象就從兩套系統收斂為一套，這是 1.67 版最實際的價值。

導入時的合理順序是先在小範圍開啟 server.enableAgentApi，以一個唯讀儀表板測試 MCP 接入，確認代理讀取的數字與瀏覽器顯示一致，再逐步擴展到寫入流程。專案的版本節奏穩定，現有應用升級風險低，真正的變數在於組織是否準備好讓代理持有操作權限。
