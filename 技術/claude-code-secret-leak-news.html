Claude Code 密碼外洩：1994 個公開倉庫中招

2026年11月09日 00:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：Apiiro

資安廠商 Apiiro 於十一月五日公布掃描結果，GitHub 上共有一千九百九十四個公開倉庫存有二千五百三十九條真實憑證，涵蓋資料庫密碼、雲端金鑰與 SSH root 登入。源頭是 Claude Code 的「是，且不再詢問」把含密碼的完整指令寫入專案設定檔，隨後隨一般提交進入版本歷史。

這批憑證多數並非刻意上傳。開發者要求代理檢查資料庫或呼叫 API，指令本身必然帶著連線字串，核准一次之後即被記錄成允許規則。受影響組織達六十三個，從學生社團、新創、軟件代理商到成熟廠商，其中一間資料庫廠商外洩的是自身具管理權限的雲端金鑰。

Claude Code 的「不再詢問」按鈕做了什麼？

Claude Code 把核准過的完整指令寫入專案內的 .claude/settings.local.json，指令含密碼時原文一併落地，該檔只加入全域忽略清單。

開發者要求代理檢查資料庫或呼叫 API 時，代理提出的指令必然帶著連線字串或權杖，否則無法執行。Claude Code 每次執行 shell 指令前都要確認，一個工作階段可能打斷十次以上，多數人到了後段已不再逐字細看，而密碼往往只是長長一行指令裡的其中一個詞。

按下「是，且不再詢問」之後，代理會把該指令原文寫成允許規則，存入專案內的設定檔，之後不再提示。Apiiro 強調這是 Claude Code 工具層的行為，與模型本身無關，並以 Opus 5.5 與 Fable 5.1 重現。檔案建立時只被加入開發者層級的全域忽略清單，因此換機器、資料夾後來才成為倉庫、或檔案早已被提交的情況，全部不受保護。

更值得注意的是提交者身分。在一千一百零五個確認含真實密鑰的倉庫中，有五百三十九個的該檔案改動來自 Claude 共同署名的提交，涉及 Sonnet 4.5 至 Opus 5.5 各代模型。換言之，工具本身既產生檔案，也參與把它送進版本控制。

有多少密鑰已經進入公開倉庫？

GitHub 上有十萬四千一百八十五份該設定檔，其中一千一百二十二份、約百分之一點一存有真實密鑰，合計一千三百七十九條憑證。

按 Apiiro 的分類，這批檔案裡的憑證以資料庫存取為主，另有相當比例屬於第三方服務與模型供應商的 API 權杖。檔案體積與風險呈明顯正相關，超過 8KB 的允許清單每十份有一份存有真實密鑰，低於 500 字元者不到五百分之一。

外洩並不限於目前版本。以中位數計算，含真實密鑰的檔案首次提交發生在十一月二日的二百一十七日之前，一百一十八個倉庫超過一年。另有二百一十一份分叉复制了七十四個倉庫的同一批密鑰，而曾經刪除檔案的倉庫中，歷史版本仍保留七百三十四條在現行版本已不存在的憑證。

為什麼通用密鑰掃描工具漏掉大半？

掃描工具依賴供應商金鑰格式，寫在指令中的密碼如 PGPASSWORD= 或 mysql -p 後只是普通詞彙，故 gitleaks 只命中五百六十四份。

Apiiro 以兩款主流工具重跑全部十萬四千份檔案，結果顯示二百一十五份帶有真實密鑰的檔案被兩者同時漏掉。缺口集中在「指令內密碼」這種沒有格式特徵的字串，工具無從辨識，只能靠上下文判斷。

同一個模式並不止於此。凡代理記錄自己執行過什麼的地方，包括對話逐字稿、記憶檔、交接筆記，都會重複出現同類字串。Apiiro 指出，這意味把掃描規則調校到只認金鑰格式，等於在所有這類檔案上留下同一個盲區。

只有這一個設定檔有問題？

不止一個。團隊刻意提交的共用 settings.json 有二百九十八份含真實密鑰，代理逐字稿、記憶檔與交接筆記亦有中招案例。

研究團隊另外抽查了幾個代理相關檔案類別，全部發現同類問題。團隊共用的設定檔因為被刻意提交，風險最高；交接筆記中有三分之一由代理自行撰寫，等於代理把含密碼的指令抄進另一個公開檔案。

外溢範圍亦包括其他平台。三萬一千零五十三個 Hugging Face Spaces 中有一百二十六個存有該設定檔，其中一個的允許規則含資料庫服務金鑰與使用者密碼；GitLab 上抽查的六十九份公開副本有兩份含真實憑證。研究團隊亦比較十六款編碼代理的核准機制，只有 Claude Code 被確認會預設把完整指令寫入專案檔案。

Anthropic 與社群如何回應？

Claude Code 負責人 Boris Cherny 在 Hacker News 表示，該檔本應留在本機，團隊正研究防範方式，密鑰掃描是其中一個方向。

Cherny 的回應集中在責任邊界，指 .claude/settings.local.json 設計上不應進入版本控制，工具建立檔案時已自動忽略，問題出現在資料夾後來才變成倉庫、或於另一台機器複製的情況。他同時表示權限規則已是舊方法，建議改用自動核准模式。

這個說法在討論串引來大量反駁。多位開發者指出，自動核准模式並不提供可驗證的安全保證，把風險轉移到使用者習慣，等於要求所有人承擔同一個預設值。亦有人提到企業環境中，同一部門的開發者未必應該擁有生產資料庫密碼。

時間線同樣受到質疑。Claude Code 使用者自二零二五年八月起已在 GitHub 提出相關問題，編號包括 5544、11982、13106 與 91270，全部未獲回覆，其中三項被系統以不活躍或重複自動關閉。Apiiro 在發布前已向 Anthropic 通報，並於十一月初逐一通知六十三個受影響組織，其中一間確認金鑰當時仍然有效。

開發者可以如何自查與補救？

先在組織內搜尋 .claude/settings.local.json 與 settings.json，並查各倉庫歷史紀錄。找到後應先輪換憑證，其次清理檔案。

補救順序比補救動作重要。憑證一旦進入公開倉庫，即使當日刪除，歷史、分叉與他人的複製仍然存在，Apiiro 在報告中明確把輪換放在清理之前。

  1. 以 GitHub 組織搜尋找出所有 .claude/settings.local.json 與 .claude/settings.json，逐份開啟允許清單，檢查是否含密碼、權杖或連線字串。
  2. 檢查每個倉庫的提交歷史，即使檔案今日已不存在，歷史仍隨分叉擴散。
  3. 已被追蹤的檔案以 git rm –cached 取消追蹤，並寫入該倉庫自身的 .gitignore，而非只依賴全域設定。
  4. 輪換檔案曾經持有的全部憑證，包括已刪除規則中的舊值。
  5. 之後改為核准指令模式而非逐字指令，例如 Bash(npm run:*)；密碼以環境變數引用，讓規則記錄 $DB_URL 而非原文。

對安全團隊而言，Apiiro 建議把 .claude/、.cursor/、.gemini/、.specstory/ 與代理記憶檔視同 .env 管理，納入提交前檢查與持續整合掃描，並確認掃描器能辨識指令內密碼，而非只認供應商格式。代理工具的權限邊界亦需一併檢查，可參考 Crawl4AI v0.9.5 修補六個漏洞的案例。

常見問題有哪些？

最常見的疑問是責任歸屬與實際風險。Apiiro 認為機制令使用者難以察覺，Anthropic 強調檔案本不應提交，憑證有效性未經驗證。

沒有使用「不再詢問」，是否仍然受影響？ 風險主要來自含密碼的指令被寫入允許清單。若從未核准過同類指令，設定檔通常只有路徑或指令名稱，不含憑證。

檔案已刪除，是否仍要輪換？ 需要。Apiiro 在五百零九個倉庫的歷史版本中找到七百三十四條現行檔案已不存在的憑證，刪除只影響最新版本。

私人倉庫是否安全？ 風險較低但未消失。私有倉庫的存取者仍可讀取檔案，一旦倉庫轉為公開、被分叉或由外部協作者複製，憑證即隨之外流。

其他編碼代理有同樣行為嗎？ 研究團隊比對十六款工具的文件，只有 Claude Code 被確認預設把完整核准指令寫入專案檔案。其餘工具的核准紀錄多存於使用者層級目錄。

企業應該先做哪一項？ 先掃描並輪換同時對應公開主機的憑證。Apiiro 指出這類組合直接提供存取能力，包括 SSH root 登入與生產資料庫密碼，優先度最高。

這件事對代理工具帶來什麼提醒？

代理為完成任務必須接觸真實憑證，便利的核准機制卻把憑證寫進可提交檔案。工具應預設隔離敏感值，而非依賴使用者逐行檢查。

這批案例的共同點是使用者並非主動上傳密碼。指令由代理提出，核准由使用者按下，落地由工具完成，三個環節都沒有標示風險，最後由版本控制系統忠實保存。任何一個環節加入提示或遮蔽，外洩數量都會顯著不同。

第二個提醒關於掃描能力。當代理開始大量生成指令、筆記與記憶檔，憑證會以自然語言的形式散落在各種檔案中，傳統以格式為基礎的偵測方式覆蓋不足。安全流程需要把「代理產生的檔案」視為新的資產類別，而不是附帶產物。

對自架與小團隊而言，最實際的做法是減少密碼出現在指令中的機會。改用環境變數、短期權杖與權限較窄的資料庫帳號，即使設定檔被提交，可造成的損害亦有限。同類的供應鏈風險案例，可比較 Claude Code 擴充套件後門事件 與 Open WebUI 0.12.5 一次修補 166 個安全公告的做法。
