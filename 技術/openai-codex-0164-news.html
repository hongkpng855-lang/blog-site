Codex CLI 0.164：13 萬星的權限與沙箱改造

2026年10月28日 00:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/openai/codex

OpenAI 開源的 Codex CLI 於 2026 年 10 月 23 日推出 0.164.0 版，這個以 Rust 撰寫的終端編程代理在 GitHub 累積 131,143 顆星標。新版本把提示詞、模型與權限切換收進行內指令，並補上企業級模型上下文協定認證、憑證遮蔽與 macOS 沙箱加固，指向可稽核的執行邊界。

Codex CLI 是什麼？

Codex CLI 是 OpenAI 以 Rust 撰寫的終端編程代理，可於本機讀寫儲存庫並執行指令，採 Apache-2.0 授權。2026 年 10 月累積 131,143 顆星標。

官方說明把它定位為跑在使用者電腦上的編程代理，並提供三條使用路徑：終端機、編輯器整合與桌面應用程式。倉庫同時是發佈管道，每個版本都附上對應平台的執行檔，包括 macOS 的 Apple Silicon 與 x86_64、Linux 的 musl 靜態版本。

安裝方式分為三類。官方提供 shell 與 PowerShell 的一行安裝腳本，也支援 npm 全域安裝與 Homebrew cask，使用者亦可以直接下載二進位檔。這種多路徑設計反映採用者背景差異很大，既有雲端環境的自動化腳本，也有個人筆記型電腦的臨時試用。

授權模式則與帳號綁定。使用者可以透過 ChatGPT 的 Plus、Pro、Business、Edu 或 Enterprise 方案登入，亦可以使用 API 金鑰，但後者需要額外設定驗證流程。這個安排把成本計算與既有訂閱綁在一起，企業採購時通常會影響決策。

0.164.0 版改了哪些使用流程？

0.164.0 版新增十個編號提示詞插槽與行內模型、權限參數，並讓企業級 MCP 連線支援專用登入與 OAuth 密鑰，Amazon Bedrock 設定精靈改為預設啟用。

版本紀錄把新功能分成六項。其中五項直接影響日常操作：提示詞可以存進十個編號插槽並以鍵盤選單呼叫；模型、推理強度、速度與權限檔可以寫在指令參數之後即時生效；支援 Kitty 與 Sixel 圖形協定的終端可以全屏預覽檢視或生成的圖片。

第六項與連線有關。企業級模型上下文協定連線可以使用既有的帳號授權，或走獨立的登入流程，包含需要密鑰的 OAuth 用戶端。這個改動的意義在於把代理的外部工具存取納入既有的身分系統，而不是靠環境變數傳遞長期憑證。

設定精靈的調整同樣值得注意。Amazon Bedrock 的精靈改為預設啟用，當系統偵測到既有憑證時，API 金鑰輸入會與其他登入方式並列顯示。對同時使用多雲模型的團隊而言，這減少了切換供應商時的設定摩擦。

前一個版本 0.163.0 的方向相近。該版加入可搜尋的設定面板、回覆中途插入的轉向指令、可自訂的領導鍵，以及讓獨立的唯讀工具平行執行。兩個版本合起來，可以看出維護團隊正把互動細節逐項補齊。

為何提示詞、模型與權限要改成行內指令？

把常用設定從選單搬到指令參數，可以讓同一條命令重現完整狀態。這對腳本化與團隊協作特別有用，因為設定不再依賴個人本機的互動選擇。

舊流程依賴互動選單。使用者先啟動代理，再逐層進入設定頁面調整模型或權限，這種方式在單人使用時足夠，但難以寫進自動化腳本或共用的說明文件。

行內參數改變了這一點。/model 可以同時指定模型名稱、推理強度與速度，/permissions 則直接切換權限設定檔。兩者都接受參數形式，意味著同一串命令可以完整描述一次執行所需的環境。

預設提示詞插槽解決另一個重複問題。安全審查、重構、撰寫測試這類固定任務，過去每次都要重新輸入長段指示；現在可以存成編號插槽，用鍵盤選單在幾秒內呼叫。

對團隊而言，這些改動降低的是溝通成本。共用文件可以直接寫出完整命令，而不必附上一段操作步驟的截圖說明。

企業級 MCP 認證解決了什麼問題？

過去 MCP 連線多靠環境變數保存憑證，難以對應企業的身分治理。新版支援帳號授權與專用登入，把外部工具存取納入既有的驗證流程。

模型上下文協定在過去一年成為代理連接外部工具的主流方式，但認證環節一直是導入障礙。個人開發者可以把權杖寫進設定檔，企業環境則通常要求短效憑證與可撤銷的授權。

0.164.0 版允許符合條件的帳號授權直接用於企業連線，也支援走獨立登入流程的用戶端。這種設計讓憑證的發放與回收回到組織既有的目錄服務，代理本身只持有短期憑證。

同一版本亦處理憑證外洩的路徑。支援的遠端 Bash 指令與 Zsh 快照工作階段會在輸出時遮蔽憑證，包含來自自訂供應商的憑證。這類遮蔽過去常見於單一供應商整合，改為通用處理後，覆蓋面明顯擴大。

三項改動合起來構成一個閉環：授權由組織控管、憑證壽命縮短、輸出經過遮蔽。對需要通過內部資安審查的團隊，這是能否採用代理工具的關鍵門檻。

憑證遮蔽與沙箱加固處理哪些風險？

新版本修補 macOS 上大小寫變體中繼資料路徑與可替換符號連結的沙箱檢查。壓縮失敗亦不再留下半截摘要，避免後續回合讀到不完整的脈絡。

沙箱相關的修補集中在邊界判斷。版本紀錄指出，macOS 上以大小寫變體表示的中繼資料路徑，以及用於定位執行檔的可替換符號連結，都可能繞過既有的路徑檢查；新版本把這兩類情況納入驗證範圍。

壓縮失敗的處理同樣屬於資料完整性問題。過去的失敗會把半截摘要留在對話歷史中，後續回合可能基於不完整內容繼續推理；新版本改為不寫入部分結果，背景壓縮失敗時亦回退而不中斷。

Windows 環境的網路連線亦有調整。HTTPS 與 WebSocket 連線現在可以用已登入使用者的 Negotiate 或 NTLM 憑證回應代理的認證挑戰，這對企業內網環境是必要能力，因為多數代理伺服器不接受匿名連線。

還有一項容易被忽略的修正。佇列中的提示詞會等待未完成的權限選擇，避免在權限狀態未定時繼續執行。這種排序問題在互動式工具裡很常見，卻往往造成難以重現的異常。

查詢當日專案有 131,143 顆星標、20,711 個分支與約 479 位貢獻者，Rust 佔 79.2 MB。三週內連續推出三個穩定版，節奏相當密集。

星標對分支比約為 6.3 比 1。這個比例低於工具類專案常見的十倍區間，通常意味著採用者傾向直接使用官方發佈的執行檔，而非自行複製倉庫修改。

未結問題數達到 25,051 項，數量偏高。對照 479 位貢獻者與密集的提交節奏，可以推測問題佇列的吸收速度跟不上使用者增長，這是高速擴張階段常見的現象。

版本節奏提供了另一個觀察角度。穩定版 0.162.1 於 10 月 9 日發佈，0.163.0 於 10 月 15 日，0.164.0 於 10 月 23 日，三週內推出三個版本。版本頁的累計數量超過一千二百個，反映專案採用高頻小步的發佈策略。

語言組成則說明重心。Rust 程式碼約 79.2 MB，Python 約 1.7 MB，其餘為 Starlark、TypeScript 與 Shell 等輔助部分。主體以系統語言撰寫，與需要低延遲啟動的終端工具定位一致。

與其他終端編程代理相比如何定位？

同期競爭者包括約 108,567 顆星標的 Gemini CLI。Codex CLI 的差異在於以 Rust 實作、與 ChatGPT 訂閱綁定，並把權限與企業認證放在更新重心。

同類工具的星標規模接近。Gemini CLI 在查詢當日累積約 108,567 顆星標，定位同樣是終端內的編程代理，並以開源方式釋出。兩者的使用者群高度重疊，選擇往往取決於既有訂閱與模型偏好。

差異出現在實作與治理兩層。Codex CLI 以 Rust 撰寫，啟動延遲與記憶體佔用較低；權限模型則分成多個設定檔，配合沙箱與網路代理控制外部存取。這些設計對需要在受管裝置上執行代理的組織更有吸引力。

生態整合是另一個分野。官方提供編輯器擴充與桌面應用程式，同一帳號可在多個入口使用；這種一體化路線降低切換成本，但也意味著使用深度與訂閱方案綁定。

對評估者而言，值得先釐清的是需求邊界。若重點在模型能力比較，多數工具都能切換供應商；若重點在權限稽核與憑證治理，版本更新中反覆出現的沙箱與認證修補，會比功能清單更能說明維護團隊的優先順序。

升級到 0.164.0 需要注意什麼？

升級前應確認企業 MCP 連線的 OAuth 用戶端支援新版登入，並重檢 macOS 沙箱路徑假設。使用遠端 Bash 的團隊需確認憑證遮蔽不影響輸出解析。

憑證遮蔽是第一項要驗證的行為。若既有腳本依賴輸出中的憑證字串做後續處理，新版遮蔽後可能導致解析失敗；這類依賴通常不會寫在文件裡，需要實際跑一次流程確認。

MCP 認證的變更需要對照組織的授權政策。使用需要密鑰的 OAuth 用戶端時，密鑰的保存與輪換流程要一併規劃，否則容易退回以環境變數長期保存憑證的舊做法。

磁碟佔用的調整屬於內部行為，但仍有觀察價值。新版本會清理未使用的安裝、廢棄的市集檢出目錄並限制常駐服務日誌大小，若維運流程依賴舊的日誌位置或保留期限，需要同步更新監控設定。

最後是版本鎖定。三週三個穩定版的節奏，意味著團隊不宜長期停留在浮動版本；在正式環境採用固定版本並保留回退方案，比追求最新功能更符合維運現實。

專案原始碼與文件位於 https://github.com/openai/codex，版本紀錄與執行檔在同一倉庫的 Releases 頁面發佈。官方文件另設於開發者網站，內容涵蓋安裝、驗證與權限設定的完整說明。

## 常見問題有哪些？ 常見問題集中在安裝路徑、訂閱要求、權限設定與企業導入四類。以下依官方文件與版本紀錄整理，答案以 2026 年 10 月 27 日的倉庫狀態為準。 ### Codex CLI 是否必須付費才能使用？ 工具本身以 Apache-2.0 授權開源，但實際執行需要模型存取權限。官方建議以 ChatGPT 的付費方案登入，亦可以使用 API 金鑰，成本依用量計算。 ### 支援哪些作業系統？ 官方提供 macOS、Linux 與 Windows 的安裝路徑，包括 shell 與 PowerShell 安裝腳本、npm 與 Homebrew 套件，以及各平台的預編譯執行檔。 ### 權限設定可以限制檔案存取範圍嗎？ 可以。工具提供多個權限設定檔，配合沙箱控制可讀寫的目錄與網路存取。版本紀錄顯示這些邊界持續被修補，包括路徑大小寫變體與符號連結的處理。 ### 與 ChatGPT 網頁版的 Codex 有何差別？ 終端版本在本機執行，可直接讀寫本機儲存庫並執行指令。網頁版本屬於雲端代理，兩者共用帳號但執行環境與適用場景不同。 ### 企業導入需要哪些前置條件？ 需要可用的身分驗證機制，包含支援企業級 MCP 連線的授權方式。同時應規劃憑證輪換流程與版本鎖定策略，並為沙箱與網路代理設定安排測試。

總結：哪些團隊適合採用 Codex CLI？

需要在本機或受管裝置上執行編程代理，並要求權限邊界可稽核的團隊最適合。若只需雲端環境的程式碼生成，網頁版代理或訂閱方案已能滿足大部分需求。

0.164.0 版的改動沒有增加新的模型能力，重點落在操作效率與治理邊界。行內指令與提示詞插槽處理的是日常重複，企業 MCP 認證、憑證遮蔽與沙箱修補處理的則是採用門檻。

這種取向說明專案的階段。當工具從個人試用走向組織部署，版本更新的重心自然會從功能清單轉向可維運性；星標數字與貢獻者規模亦支持這個判斷。

評估時值得先問一個問題：團隊目前卡住的是產出速度，還是稽核與合規。若是前者，功能層的比較更有意義；若是後者，近幾個版本的修補清單會比任何功能介紹都更值得細讀。
