n8n 3.0 預覽：npm 安裝退場與節點大清倉

2026年11月09日 12:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/n8n-io/n8n

n8n 3.0.0 於十月二十七日以早期預覽形式發布，是這個累積二十萬九千顆星標的平台近年幅度最大的破壞性更新。自架部署只保留 Docker，約三十個舊節點與 AI Agent 第一版退場，Slack 憑證強制要求簽名密鑰。官方在設定頁加入遷移報告，預先列出需要處理的工作流。

n8n 3.0 是什麼樣的版本？

n8n 3.0 是 n8n 第三次主版本更新，定位在部署方式、節點生命週期與安全預設三條線的收斂，目前以早期預覽形式發布，尚未進入正式穩定通道。

此版本延續 2.0 把工作流啟停改為發佈與取消發佈模型的收緊方向，處理的是長期累積的技術債。官方文件把變更分為部署、社群節點開發、節點移除、行為變更與安全五個章節，每一項都附有建議處置方式。

專案由 Jan Oberhauser 於 2019 年 6 月建立，以 TypeScript 撰寫，採 fair-code 模式發佈。截至十一月初，儲存庫累積二十萬九千八百四十顆星標與六萬一千四百零六次分叉，貢獻者約八百五十人。

n8n 3.0 為什麼取消 npm 安裝？

n8n 3.0 不再向 npm 發佈可執行套件，自架部署必須改用 Docker 或 Podman；官方提供一行安裝腳本，會檢查 Docker 並啟動新實例。

npm install n8n 與 npx n8n 兩種方式的支援在 3.0 終止。既有 npm 安裝目前仍可運作，但新安裝與日後升級都要改用容器，官方建議以一行腳本起步，或使用 Docker Compose 搭配 Postgres，取代內建的 SQLite。

連帶影響延伸到社群節點開發。n8n-node dev 不再以 npx n8n@latest 啟動，改為在容器內執行官方映像，開發機必須具備 Docker 或 Podman；測試期間產生的資料改存於每個映像各自的容器磁碟區，舊版資料不會自動帶過去；–custom-user-folder 參數亦只在 –external-n8n 模式下生效。

有哪些節點在 n8n 3.0 被移除？

移除清單涵蓋 Function、Item Lists、Cron、HTML Extract、Read PDF、OpenAI 舊節點與多個向量 Insert 與 Load 節點。

Cron 與 Interval 由 Schedule Trigger 取代，Function 與 Function Item 由 Code 節點接手，前者對應一次處理全部項目，後者對應逐項處理。Item Lists 依操作拆成 Split Out、Aggregate、Sort、Limit、Remove Duplicates 與 Summarize 六個節點；HTML Extract 併入 HTML 節點的擷取內容操作；Read PDF 併入 Extract from File。

檔案與向量層同樣大改。Read Binary File、Read Binary Files 與 Write Binary File 統一為 Read/Write Files from Disk；In Memory、Pinecone、Supabase 與 Zep 的 Insert 與 Load 節點合併為單一向量市集節點，改由操作選單決定寫入或讀取。LangChain Code、Motorhead、Zep 記憶、SerpApi 與 Orbit 沒有直接替代品，其中 Orbit 服務已經關閉。

表示式層面移除 $getPairedItem，改以 $(‘節點名稱’).item、itemMatching 與 pairedItem 三種形式處理項目連結。Execute Sub-workflow 的本機檔案與 URL 兩種來源同時取消，只保留資料庫與直接貼上 JSON；Code 節點的 $evaluateExpression 方法在不安全執行模式下失效。

AI Agent 節點與舊模式如何處理？

AI Agent 第一版連同 SQL Agent、ReAct Agent 等五種模式一併移除，全部由 Tools Agent 取代，升級節點版本即可沿用。

既有工作流只要升級節點版本即可沿用 Tools Agent 行為，原本設定為 Tools Agent 的流程不受影響。SQL Agent 的用途改由 Postgres 或 MySQL 工具子節點搭配新版 AI Agent 達成，查詢語句則交由模型在工具呼叫中產生。

Edit Image 節點的第 1 與 1.1 版同步退場，第 2 版改用另一套影像處理函式庫，輸出結果可能與過往不同。遷移會轉換模糊設定但移除 Sigma 參數，文字位置可能位移，PNG 與 TIFF 輸出忽略品質設定，縮放尺寸為零或負值時直接報錯。

n8n 3.0 的安全預設有什麼變化？

3.0 預設開啟加密金鑰輪換，Slack 憑證強制填寫簽名密鑰，SSRF 封鎖清單新增四段位址，包括 100.64.0.0/10 電信級 NAT 區段。

Slack 的影響最直接。凡是使用 Slack Trigger 的工作流，憑證缺少簽名密鑰就無法發佈；已經發佈的工作流在升級後不會啟動，事件停止送達。其他 Slack 工作流可在下次編輯憑證時補上，密鑰位置在 Slack 應用設定的基本資訊頁。

加密金鑰輪換由選填改為預設開啟，憑證與其他資料在升級前已加密者仍可讀取，下次更新該筆記錄時會以當前金鑰重新加密。SSRF 保護啟用且封鎖清單包含預設值時，新增的位址段還包括 IPv6 未指定位址 ::/128 及另一組專用區段。

行為層面有兩處容易誤判。Always Output Data 在多輸出節點上改為全部輸出皆空時才補一個空項目，過去每個空輸出各自補項，導致分支在不該執行時啟動；Gmail Trigger 低於 1.4 的版本統一按 1.4 行為執行，草稿預設不再納入，已寄出與排程郵件亦不再觸發。Chat Trigger 的 WebSocket 改為每格皆為帶 type 欄位的 JSON 物件，自行編寫客戶端者要按 type 分派，嵌入 @n8n/chat 者需升級至 1.31.0 以上。

3.1 版本又加入了什麼？

3.1.0 於十一月三日發布，加入 Apps 前端模組與發佈流程、代理版本歷史與發佈時間軸、代理工作階段日誌的 MCP 工具，並把助理改為可用環境變數開關。

Apps 是一條新的產品線，前端已具備列表頁、詳情路由與藍圖卡，建立應用前會先顯示藍圖再進入設定。代理層加入版本歷史與發佈時間軸，草稿與已儲存的版本可以分開發佈，工作階段追蹤則補上記憶召回與標記的顯示。

維運相關的調整包括知識庫檔案上傳上限提高至 25 MB、情節記憶召回邏輯重寫、Sentry 升級至第 11 版並在啟動時只初始化一次 OpenTelemetry、WhatsApp 樣板訊息可在客服時段外送出。3.1.0 與 3.0.0 同樣標記為預先發佈，正式穩定標籤仍停在 2.46.6。

升級前應該先做哪些準備？

升級前應先備份資料庫，於設定頁開啟遷移報告，逐條處理被標示的工作流；報告可匯出 CSV，並能把 AI Transform 節點直接轉為等效的 Code 節點。

遷移報告是這次升級的主要配套。它會列出實例上受影響的工作流與設定，並為每條發現標示影響級別，包括「執行可能失敗」一類需要優先處理的項目；工作流編輯者可以只檢視自己所屬專案內的發現，分工處理。

AI Transform 的轉換路徑較特別。報告會保留節點曾經產生的 JavaScript 並改寫為 Code 節點，行為維持不變；若該節點從未產生程式碼，報告無法轉換，只能手動改寫。升級完成後應重測模糊與縮放、加字、讀取影像資訊，以及 PNG 與 TIFF 的品質設定。

n8n 的技術數據與授權如何？

專案以 TypeScript 撰寫，採 fair-code 模式，依 Sustainable Use License 公開，允許內部使用與修改，對外託管轉售受限。

授權模式一直是 n8n 與純開源專案的分界。Sustainable Use License 允許內部業務使用與修改，對外提供託管服務或轉售則受限制，企業版功能另需付費授權。對自架團隊而言，這意味著內部自動化沒有額外成本，把它包裝成產品則需要法務確認。

專案活躍度維持在高位。3.0.0 與 3.1.0 相隔七日發布，其間另有 2.46.4 至 2.47.2 多個修補版本；十月二十七日至十一月四日的提交集中在遷移報告、代理建置器與 Apps 前端三處。

出處連結有哪些？

原始碼與版本說明位於 GitHub 的 n8n-io/n8n 儲存庫，破壞性變更與遷移報告的完整說明位於官方文件站的 Changelog 章節。

儲存庫網址為 https://github.com/n8n-io/n8n ，版本頁可查 3.0.0 與 3.1.0 的完整提交清單與合併請求編號。官方文件的 v3.0 Breaking changes 頁面按部署、節點、行為與安全分章說明，並附遷移工具入口。

同類自架服務的大版本升級風險，可對照 Open WebUI 0.12.5 涵蓋 166 個安全公告的經驗；部署方式的遷移考慮，另可參考 Dokploy 3.1 的自架 PaaS 做法。

總結：n8n 3.0 適合什麼團隊？

3.0 適合已用容器維運、願意一次清理舊節點的團隊；仍依賴 npm 安裝或大量使用舊向量節點的實例，宜先留在 2.x。

這次更新把 n8n 從「一套可以隨意安裝的工具」推向「一套需要維運紀律的平台」。部署收窄到容器、節點生命週期明確終止、安全預設全面收緊，代價是升級前的準備工作無法省略，好處是往後的版本可以少背一批歷史包袱。

對正在評估自動化平台的團隊，3.x 的早期預覽提供了觀察窗口，但不適合直接上生產。穩定標籤仍停在 2.46.6，官方亦把 3.0.0 標為早期存取版本；較穩妥的做法是在測試環境走一次遷移報告，把受影響的工作流數量與改寫工時量化後，再決定升級時機。
