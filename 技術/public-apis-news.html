public-apis 開源：2038 個免費 API 總表

Eric Chan

IT 顧問・實測主義者

2026年10月07日 16:00 • 閱讀時間 3 分鐘

來源：GitHub

內容創作者： https://github.com/public-apis/public-apis

public-apis 是 GitHub 上累積 486,557 顆星的免費 API 目錄專案，由社群自 2016 年 3 月起共同維護，以 51 個分類收錄 2,037 個公開 API，逐條標註認證方式、HTTPS 支援與 CORS 狀態。專案採用 MIT 授權，並於 2026 年 9 月新增 MCP 伺服器專區，把部分介面整理成可供 AI 代理直接呼叫的工具格式。

public-apis 是什麼？

public-apis 是由社群維護的免費 API 目錄，自 2016 年建立，依 51 個分類收錄 2,037 個公開介面，並標註認證、HTTPS 與 CORS 狀態，採 MIT 授權。

該專案的定位在說明文件中寫得相當清楚：它是一份由社群成員與 APILayer 團隊共同維護的公開 API 清單，目的是讓開發者不必逐一搜尋，就能在同一個頁面找到可用於產品的介面。清單本身不是程式庫，而是索引與規格表，真正的服務仍由各自的第三方提供者維運。

這種形態決定了它的使用方式。開發者開啟儲存庫後，先依領域定位分類，再從表格中挑選條目，表格同時列出該介面的用途、認證方式、是否支援 HTTPS 以及跨來源資源共享的狀態，讓技術評估能在點入官網之前完成。專案建立於 2016 年 3 月 20 日，至今已近十年，仍持續接受社群提交的新條目。

public-apis 收錄了多少個 API？

清單收錄 2,037 個 API，分佈於 51 個分類，其中 Development 以 204 個居首，Government 與 Games & Comics 分別為 118 與 108 個。

依儲存庫說明文件逐一統計，索引區共列出 2,037 筆條目，分佈於 51 個分類。數量最多的分類是 Development，共 204 筆；其次為 Government 的 118 筆、Games & Comics 的 108 筆、Geocoding 的 107 筆，以及 Cryptocurrency 與 Transportation 各 90 筆。分類規模最小的則是 Events 與 Patent，各僅 4 筆，Programming 為 5 筆。

分類的分布也反映開發需求的實際樣貌。開發工具、政府公開資料與地理定位長期是外部介面需求最集中的領域，而加密貨幣與交通運輸的高占比，則對應了近年在金融科技與物流應用上的投入。相對稀少的類別並非缺乏價值，而是該領域的公開服務本來就有限，條目審核的門檻也相對嚴格。

  • 2,037收錄 API 數
  • 51分類數量
  • 204最大分類（Development）

public-apis 為什麼新增了 MCP 伺服器專區？

因應 AI 代理需要可直接呼叫的工具，專案於 2026 年 9 月新增 MCP 專區，列出 10 個 Model Context Protocol 伺服器，並標示傳輸方式與安裝來源。

這是清單近期最值得注意的變化。專案在 2026 年 9 月 21 日於說明文件中加入 MCP 伺服器區段，並同時訂立該類條目的填寫格式。MCP 是 Model Context Protocol 的縮寫，用於讓 AI 代理把外部服務當成工具呼叫；與傳統 REST 介面不同，這類伺服器通常由使用者在客戶端安裝，而非直接由應用程式發送 HTTP 請求。

因此表格欄位也隨之調整。MCP 區段不再標示 HTTPS 與 CORS，改為列出認證方式、傳輸類型（例如標準輸入輸出或 HTTP）以及可安裝的位置，例如套件庫或代理目錄。目前該區段的 OpenSwissData、GitHub、Filesystem、Silicon Floor、Twinbay、Vuntum 等條目共 10 筆，數量雖少，但顯示清單的定位正從「人類查閱的目錄」延伸為「代理可讀取的資源表」。

public-apis 的授權與使用條件是什麼？

專案以 MIT 授權釋出，清單內容可自由使用與再利用；但各條目對應的第三方服務各有條款與用量限制，商業使用前仍須逐一查核原始提供者。

儲存庫本身採用 MIT 授權，這是相對寬鬆的條款，允許使用、修改、合併、發布與再授權，只需保留著作權聲明。就清單內容而言，開發者可自由將其納入內部文件、教材或工具，無須另行取得同意。

需要留意的是清單與服務的區別。MIT 授權只涵蓋這份目錄的整理成果，並不延伸到表格中的任何一個第三方介面。實際呼叫時，開發者面對的是各提供者自訂的服務條款、免費額度與速率限制，部分條目甚至在名稱上標示需要付費方案。因此在把某個介面納入產品之前，仍應回到該服務的官方文件確認授權範圍與用量上限。

public-apis 與其他 API 目錄有何不同？

差異在於以表格逐條標註認證、HTTPS 與 CORS 三項技術欄位，讓開發者無須點入官網即可完成初步評估，且長年由社群審核維護。

多數 API 目錄只提供名稱與簡短描述，開發者必須逐一開啟官網才能判斷是否合用。這份清單選擇把評估所需的欄位前置：認證方式區分為免認證、API 金鑰與 OAuth 三類，統計上分別有 974、905 與 150 筆；HTTPS 欄位中 1,948 筆標示支援、89 筆標示不支援；CORS 欄位則有 789 筆支援、231 筆不支援，另有 1,016 筆狀態未明。

這組欄位對前端專案的影響尤其直接。若某個介面不支援跨來源請求，瀏覽器端將無法直接呼叫，必須改由伺服器代理；而缺乏 HTTPS 支援的服務，在多數現代部署環境中已難以採用。把這些資訊寫進表格，等同於把第一輪技術篩選自動化，這也是清單能長期被引用的原因之一。

如何開始使用 public-apis？

直接開啟 GitHub 上的清單，依分類或關鍵字定位條目，檢視認證、HTTPS 與 CORS 欄位後，點入該服務官網取得金鑰即可；無須安裝工具或註冊。

使用流程不涉及任何安裝步驟。開發者開啟儲存庫說明文件後，可先瀏覽索引定位分類，再於該分類的表格中尋找符合需求的介面。表格的每一列都是一個外部連結，點入後即為該服務的官方網站或文件頁面。

實務上建議以需求反推分類，而非從分類尋找需求。例如要製作天氣資訊頁面，可直接查看 Weather 分類；要處理匯率換算，則對應 Currency Exchange。選定條目後，先確認 CORS 欄位是否支援，若專案為純前端架構而該欄位標示不支援，就需預留伺服器端代理的設計。若打算以 AI 代理串接，則可優先查看 MCP 伺服器區段，挑選已提供傳輸方式與安裝來源的條目。

public-apis 的數據與社群規模如何？

專案累積 486,557 顆星、53,807 次複製與 4,738 位關注者，提交次數約 5,944 次，貢獻者超過 420 位，未結議題 2,039 個，主要語言為 Python。

  • 486,557GitHub 星標
  • 53,807複製次數
  • 4,738關注人數
  • 5,944提交次數
  • 421+貢獻者人數
  • MIT授權條款

從提交結構可以看出專案的協作模式。約 5,944 次提交分散在超過 420 位貢獻者之間，平均每人約十四次，且多數提交以單一條目的新增為主。檢視近期的提交紀錄，可以看到大量以「Add … to …」為名的合併請求，內容涵蓋加密貨幣、金融、機器學習與影片等分類，說明清單的擴充主要依靠外部貢獻，而非由核心團隊集中開發。

未結議題的數量同樣值得注意。儲存庫目前有 2,039 個未結議題，多數屬於新增條目的提議或既有條目的修正，反映待審核佇列的規模。專案並未發布任何正式版本，因為它以文件形式存在，內容持續累積而不需要版本號；好處是使用者永遠取得最新狀態，代價是若需在文件中引用特定內容，只能自行記錄查詢時間。

常見問題有哪些？

以下整理四個常見疑問，涵蓋費用、商業使用、AI 代理串接與條目品質，答案依儲存庫的說明文件與實際結構整理而成。

public-apis 需要付費嗎？

清單本身完全免費公開，瀏覽與取用不收費用。表格中的第三方服務則依各自條款而定，部分提供免費額度，部分需付費方案才能使用完整功能。

public-apis 可以商用嗎？

清單採用 MIT 授權，可自由使用與再利用。但授權僅涵蓋目錄的整理成果，各條目對應的服務條款、用量上限與資料使用範圍，仍須回到原始提供者確認。

public-apis 支援 AI 代理嗎？

支援。專案於 2026 年 9 月新增 MCP 伺服器區段，目前列出 10 個 Model Context Protocol 伺服器，並標示認證方式、傳輸類型與可安裝的位置。

public-apis 的條目品質如何？

條目由社群提交並經審核合併，但服務品質、穩定度與維護狀態差異不小。使用前建議確認該服務的更新時間與可用性，避免採用已停止維運的介面。

總結：public-apis 適合哪些開發者？

適合需要快速尋找現成介面的開發者、進行技術選型的團隊，以及正在為 AI 代理規劃工具來源的人；偏好官方文件與最新版本資訊者，仍應以各服務官網為準。

這份清單在 2026 年的價值相當明確：它以 486,557 顆星成為開源 API 目錄的代表，用 51 個分類與 2,037 筆條目，把「去哪裡找可用介面」這個反覆出現的問題變成一次查表，並且首次把 MCP 伺服器納入收錄範圍，對應了開發流程正在轉向代理協作的趨勢。

選擇使用方式仍取決於目的。需要快速驗證想法、或為專案尋找外部資料來源的開發者，能在這裡省下可觀的搜尋時間；而在正式導入前，逐一確認服務條款、用量限制與更新狀態，仍是不可略過的步驟。清單提供的是起點，最終的技術判斷仍須由使用團隊自行完成。
