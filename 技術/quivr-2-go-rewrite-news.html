Quivr 2.0 重寫：39.6k 星改寫為 Go 內容引擎

2026年11月13日 12:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/The-Vibe-Company/quivr

Quivr 2.0.0 於 2026 年 10 月 29 日發佈，把這個累積 39,644 顆星標的專案，從文件問答工具改寫為 Go 內容引擎。新版本取消聊天介面，只以 HTTP 介面接收持續湧入的文件，保留每個版本，建立關鍵字與語意搜尋，並以主題警報與簽名 Webhook 通知上層系統。

Quivr 2.0 是無介面的 Go 內容引擎。應用程式經 /v0 HTTP 介面送入文件，或由 RSS、Microsoft 365 信箱與 X 列表收集，引擎保留全部版本。

Quivr 2.0 是什麼？

Quivr 2.0 於 2026 年 10 月 29 日發佈首個穩定版，是集中儲存、搜尋與監控持續湧入內容的開源引擎。它沒有介面，可經 quivr mcp 供 AI 代理調用。

倉庫在 2023 年 5 月建立，早期定位為文件問答與個人知識庫，讓使用者上傳檔案後以對話方式提問。專案目前由 The Vibe Company 維護，該公司為 Quivr 團隊成立的 AI 代理機構，重寫工作於 2026 年完成。

2.0.0 是重寫後第一個穩定版本，先前的 alpha 版本只供評估，不支援原地升級。發佈說明列出三項可依賴的承諾：HTTP 介面在整個 2.x 系列維持 /v0 路徑且只增不改，跨版本升級會執行 quivr migrate 並在原地保留資料，外掛需宣告支援的 Plugin API 版本，不相容者拒絕啟用。

Quivr 為何從 Python 改寫為 Go？

重寫目標是營運保證。專案改以單一 Go 二進位交付，內含 api、worker、migrate 等六種角色；資料層用 PostgreSQL 加物件儲存，索引可隨時重建。

語言欄已由 Python 換為 Go，這個改動直接反映在部署形態上。過去使用需安裝整套 Python 依賴，現在只需一個二進位檔，配合 Docker Compose 啟動周邊服務，安裝腳本與映像檔皆固定依賴版本。

架構上的核心保證寫在文件裡。文件只有在完成儲存後才會被確認，之後才進入背景處理，因此服務中斷只會延遲處理，不會遺失已確認的內容。搜尋索引與儲存分離，索引損壞或格式升級時可重新建置。搜尋在資料庫重啟後會恢復緩衝區，並限制補水工作的範圍。

專案結構亦反映這種分層。cmd/quivr 放置單一二進位，internal 按領域切成獨立套件，contracts 保存 HTTP 介面與外掛協定的 OpenAPI 描述，client 為由協定自動產生的 Go 客戶端，migrations 管理 PostgreSQL 結構變更。

Quivr 的搜尋與引用機制如何運作？

搜尋支援關鍵字、語意或兩者混合三種模式。每個結果都會標明來源段落、所屬文件與版本，開發者可直接引用；混合模式在同一請求內同時比對字面與向量相似度。

引用能力是這套設計的分水嶺。多數檢索系統回傳文件片段，讀者難以確認段落出自哪一次修訂；Quivr 把版本視為一等公民，同一份文件的更正會產生新版本，舊版本維持可讀，因此答案永遠可回溯到具體時點。

版本機制與警報互相扣連。文件被撤回時會立即退出搜尋，先前命中該文件的主題警報亦會收到通知。這對法規追蹤、供應鏈監控或新聞監察類應用有實際價值，因為錯誤資訊不會靜默留在索引內。

主題警報功能有什麼實際用途？

主題警報可存成布林查詢或自然語言描述。引擎逐份比對新文件並記錄命中理由，應用程式可主動讀取，或接收帶簽章的 Webhook 通知。

警報把被動搜尋變成主動通知。使用者不需要反覆輸入查詢，只需一次定義關注範圍，之後每份新進文件都會被自動比對，命中時附上判定理由，方便覆核判斷是否合理。

簽名 Webhook 是為生產環境設計的細節。推送帶有簽章，接收端可驗證來源真偽，避免偽造通知觸發下游流程。對於把警報接入工單系統或即時通訊機器人的團隊，這比輪詢介面更省資源。

插件架構如何擴充功能？

檔案格式、來源、嵌入模型、排序與警報規則皆為外掛，形式為小型 HTTP 服務，可用任何語言撰寫。專案另附 Go 與 Python 開發套件。

外掛以協定邊界取代函式庫耦合。核心只負責儲存、排程與協定，實際的解析、切分、向量化與評分交由外掛執行，替換模型或加入新檔案格式時不需修改核心程式碼。

這種設計的代價是部署複雜度。每個外掛都是獨立服務，需要各自的執行環境與健康檢查；換來的是語言中立與故障隔離，單一外掛失效不會拖垮整個引擎，worker 只會延後處理該批文件。

Quivr 有哪些已知限制？

官方限制頁列出四項：只搜尋文字、不支援 OCR、沒有使用者帳號體系、每份文件與每次搜尋設有大小上限。掃描版 PDF 或需要多人權限隔離的場景，目前須自行在外層補足。

缺少帳號體系是一項明確的架構選擇。Quivr 假設呼叫端已處理身分驗證與授權，引擎本身只認 API 金鑰，因此多租戶應用需自行在介面層做隔離，不能依賴引擎內建的權限模型。

OCR 缺席影響最大的是紙本檔案數位化流程。純圖像 PDF 送入後不會產生可搜尋文字，需先以外部工具辨識再匯入。團隊若以掃描發票或舊檔案為主要來源，必須在流程前端加一層處理。

如何在本機啟動 Quivr 2.0？

需求為 Linux x86_64 或 Apple Silicon Mac、Docker Compose v2 與 Python 3.12。首次啟動下載 1GB 映像，執行 make dev。 

git clone https://github.com/The-Vibe-Company/quivr.git && cd quivr
make dev
eval "$(make -s env)"

啟動後依照官方快速入門操作，約十五分鐘可完成建立集合、加入文章、以關鍵字與語意各搜尋一次，並設定一個主題警報。執行 make demo 會額外啟動示範網頁，監聽本機 5183 連接埠，用於觀察介面回應。

伺服器部署另有路徑。官方提供已簽章的映像檔，支援 linux/amd64，可依單機、Railway 或 Kubernetes 三種方式安裝，不需保留原始碼目錄。專案以 Go 1.27.3 建置，並修補了相依套件中的已知漏洞。

Quivr 與傳統 RAG 框架有何差別？

傳統 RAG 框架多為函式庫，切分與向量化須自行組裝；Quivr 以獨立服務運行，把版本保留與索引重建納入職責，並內建 MCP 介面。

定位差異決定適用場景。需要完全掌控提示詞與生成流程的團隊，函式庫仍是更合適的選擇；關注點在內容持續進站、需要可信引用與即時通知的系統，服務化的引擎可省下大量基礎建設工作。

與同類產品相比，Quivr 2.0 明確放棄生成層。它不負責撰寫答案，只提供可引用的段落與變更訊號，因此可與任何語言模型搭配，也避免把模型版本綁進資料層。

Quivr 2.0 的規模數據如何？

截至 2026 年 11 月 13 日，倉庫累積 39,644 顆星標、3,729 次分支與 30 位貢獻者。主要語言為 Go，採 MIT 授權，最新版為 2.0.2。

版本節奏值得注意。2.0.0 於 10 月 29 日發佈，同日推出 2.0.1，翌日再推出 2.0.2 修正工作目錄消失後的分支行為與 Anthropic OAuth 版本回報，顯示重寫後的維護反應相當快。

倉庫自 2023 年 5 月建立至今，星標增長集中在近兩年，而同期的程式碼幾乎完全替換。這種「高星標配新架構」的組合，意味著大量既有關注者其實從未使用過現在的版本。

出處連結有哪些？

原始碼在 GitHub 的 The-Vibe-Company/quivr，文件站為 docs.quivr.thevibecompany.co，發佈檔見 releases。

倉庫網址為 https://github.com/The-Vibe-Company/quivr ，內含 README、版本相容說明、貢獻指南與安全政策。文件站為 https://docs.quivr.thevibecompany.co ，分為概念、快速入門、營運、外掛與參考五個區塊。

版本細節可查閱 https://github.com/The-Vibe-Company/quivr/releases ，2.0.0 的發佈說明列出三項相容承諾與實驗性功能清單。完整變更記錄則在倉庫根目錄的 CHANGELOG.md。

總結：Quivr 2.0 適合什麼團隊？

適合需要持續接收外部內容、要求每條結果可回溯版本、並希望以事件方式驅動下游流程的團隊。若需求集中在單次問答或掃描檔辨識，現階段的文字限制會令其不合適。

這次重寫的意義不在技術棧更換，而在責任範圍的重新劃定。Quivr 選擇承擔儲存、版本、索引與通知，把生成與介面留給上層應用，這種分工讓它更像基礎設施而非應用框架。

判斷是否採用的關鍵在於內容流動方式。若資料是一次性匯入後偶爾查詢，函式庫加上現成向量資料庫更輕便；若內容每天持續進站、需要知道某項變化何時出現、又要對外提供可引用的答案，服務化的引擎能省下自建版本管理與告警管線的成本。

風險同樣需要評估。專案剛完成大規模重寫，alpha 至穩定版僅隔數週，長期穩定性仍待觀察；缺少帳號體系與 OCR 也意味著外層需要補上這兩塊，實際整合工作量比快速入門所示更多。同樣以 Go 重寫換取部署便利的案例，可對照 RAGFlow v1 的 Go 重寫經驗；若流程需要視覺化編排，Dify 1.19 的巢狀追蹤設計 提供另一種對照。
