Godot 118k 星開源引擎：完全免費無抽成

Eric Chan

IT 顧問・實測主義者

2026年10月07日 10:00 • 閱讀時間 3 分鐘

來源：GitHub

內容創作者： https://github.com/godotengine/godot

Godot Engine 是採用 MIT 授權的開源遊戲引擎，在 GitHub 上累積 118,192 顆星與 26,962 次複製，是目前星標數最高的開源遊戲引擎專案。它讓開發者以單一介面製作 2D 與 3D 遊戲，並一鍵輸出到桌面、行動、網頁與家用主機平台，且不收取授權費或營收抽成。專案於 2026 年 8 月先後發布 4.7.2 與 3.6.3 兩個穩定版，顯示 4.x 與舊版 3.x 兩條分支仍在同步維護。

Godot Engine 是 MIT 授權的開源遊戲引擎，GitHub 星標達 118,192，支援 2D 與 3D 開發並可一鍵輸出多個平台，且不收授權費與營收抽成。

遊戲引擎長期是開發成本中最容易被忽略、卻又最難替換的一環。它同時牽動專案的技術債、發行成本與團隊技能，一旦選定，轉換的代價往往高得驚人。正因如此，當一個引擎在授權條款上選擇完全不收費，這件事本身就具備新聞價值。

2023 年 9 月，Unity 公布依安裝次數收費的方案，引發全球開發者反彈，其後公司調整並撤回部分內容。同一時期，Godot 的下載量與社群關注度明顯上升，成為許多團隊評估替代方案時的第一個選項。這段背景，是理解 Godot 目前聲量的關鍵。

Godot Engine 是什麼？

Godot Engine 是 2014 年 2 月開源的跨平台遊戲引擎，由 Juan Linietsky 與 Ariel Manzur 開發，現由非營利基金會維護。

Godot 最初並非商業產品，而是 Juan Linietsky 與 Ariel Manzur 為承接外包專案而自行打造的內部引擎，先後用於數款受僱開發的作品。專案於 2014 年 2 月正式開源，把整套引擎程式碼交給社群，並在此後逐步建立獨立的開發節奏。

治理結構是它與多數商業引擎最根本的分歧。Godot 的開發完全獨立、由社群驅動，並由非營利的 Godot Foundation 支持，資金來自捐款與企業贊助，而非軟體銷售。這個安排讓專案不必為了財報調整授權條款，也讓貢獻者能直接影響引擎的走向。

Godot 的架構與技術特色有哪些？

Godot 以節點與場景組織遊戲結構，內建 GDScript，並支援 C# 與 GDExtension；4.x 改用 Vulkan 渲染。

在架構層面，Godot 以「節點」為最小單位，再由節點組成「場景」，並允許場景彼此嵌套。這種設計讓專案的結構與畫面層級直接對應，開發者可以重複使用既有場景，而不必為每個物件重寫初始化流程。對 2D 專案而言，這套模型的直覺程度尤其明顯。

腳本語言的選擇相對開放。引擎內建的 GDScript 針對遊戲邏輯設計，語法接近 Python，學習門檻低；需要效能或既有程式庫時，則可使用 C#，或透過 GDExtension 介接 C、C++ 與 Rust 等語言撰寫的原生擴充。引擎本體以 C++ 實作，開發者可以閱讀原始碼理解底層行為，這在除錯深層問題時往往是決定性的優勢。

渲染方面，4.x 版本改用 Vulkan 為基礎，並提供 Forward+、Mobile 與 Compatibility 三種渲染路徑，分別對應高效能桌機、行動裝置與較舊硬體的相容性需求。同一份專案可以依目標平台切換設定，不必維護多套分支。此外，編輯器本身支援 Linux、macOS 與 Windows，專案輸出則涵蓋桌面、行動、網頁與家用主機。

Godot 為什麼吸引 Unity 開發者？

2023 年 Unity 提出依安裝次數收費的方案引發反彈後，部分開發者轉向 Godot；其 MIT 授權、免抽成與開放治理，成為評估替代引擎時的主要理由。

授權爭議是最直接的推力。Unity 當年提出的收費方案直接改變了既有專案的成本結構，即使後來調整，仍在開發者社群留下信任問題。相較之下，Godot 的 MIT 授權條款簡單且穩定，專案不會因為公司策略調整而改變收費方式。

技術面的吸引力則在於可預期性。引擎完全開源，任何行為都能追溯到原始碼；遇到問題時，社群可以自行提交修正，而不必等待官方排程。對長期維護的專案而言，這種可掌握性往往比單一功能更關鍵。

不過轉換引擎並非沒有代價。既有專案需要重寫遊戲邏輯、重新調整資源管線，團隊也得重新熟悉工具鏈。因此實務上，轉向 Godot 的多為新專案、獨立團隊，或原本就沒有深度綁定特定引擎的工作室。

Godot 的授權與商業模式有何不同？

Godot 採 MIT 授權，開發者不需支付授權費、訂閱費或營收抽成，專案由基金會以捐款與企業贊助維持；商業引擎則多以訂閱或分潤方式收費。

MIT 授權的實際含義是：開發者可以自由使用、修改與再散布引擎，包含商業專案，且無須支付授權費、訂閱費或營收抽成。專案說明中提到，使用者製作的遊戲完全屬於使用者，授權不附帶任何附加條件。

這種模式之所以能維持，靠的是基金會與贊助體系，而非軟體銷售收入。資金來源包括個人捐款與企業贊助，以及社群在翻譯、文件與測試上的投入。對開發者而言，這代表引擎的存續與商業成績脫鉤，但也意味著部分高階工具與主機輸出服務需要由第三方生態補上。

Godot 目前的社群與生態規模如何？

Godot 在 GitHub 累積 118,192 顆星與 26,962 次複製，提交次數超過八萬六千次，貢獻者接近四千人，並同時維護 4.x 與 3.x 兩條版本分支。

統計數據顯示，Godot 的星標數為 118,192，複製 26,962 次，提交 86,916 次，貢獻者接近四千人，最新穩定版 4.7.2 於 2026 年 8 月 18 日發布。

儲存庫的活躍程度同樣值得注意。專案建立於 2014 年 1 月，提交次數已達 86,916 次，且近期仍有合併紀錄，顯示核心開發並未放緩。貢獻者接近四千人，涵蓋引擎核心、文件、翻譯與平台移植等不同領域。

版本策略上，團隊同時維護 4.x 與 3.x 兩條分支。4.7.2 穩定版於 2026 年 8 月 18 日發布，舊版 3.6.3 則在四天後推出，讓仍依賴舊架構的專案有更新路徑。這種新舊並行的做法，對於生命週期較長的遊戲專案而言相對友善。

Godot 有哪些實際應用場景與限制？

Godot 常用於獨立遊戲、2D 作品、原型開發與教學；限制在於官方不提供家用主機輸出，需經第三方服務，而高階 3D 工具鏈與外掛生態亦不及成熟商業引擎。

實際應用集中在獨立遊戲與中小型專案，包括以 Godot 開發的《Brotato》等作品。2D 專案、快速原型與教學場景受益最大，因為引擎體積輕、啟動快，且不需處理授權啟動流程。學校與個人開發者也能在無額外成本的前提下取得完整工具。

限制則在於生態成熟度。家用主機的輸出需要透過第三方服務處理，無法像部分商業引擎一般直接支援；高階 3D 內容製作、動畫與特效工具鏈仍在補強，外掛與中介軟體的選擇也相對有限。對人力充足、管線複雜的大型工作室而言，這些落差需要納入評估。

如何開始使用 Godot？

使用者可直接由官方網站下載免安裝的編輯器，建立專案後以 GDScript 撰寫腳本，再下載匯出範本輸出到目標平台；上手過程不需付費或註冊帳號。

入門流程相當直接。開發者由官方網站下載對應系統的編輯器，解壓後即可執行，無須安裝或登入帳號。建立專案後，可依官方教學以 GDScript 撰寫第一個場景，理解節點與腳本之間的關係。

需要輸出成品時，再下載對應版本的匯出範本，即可把專案打包為桌面、行動或網頁版本。官方文件與社群教學數量充足，範例專案也以獨立儲存庫形式公開，適合按步驟實作。對於首次接觸遊戲引擎的學習者，這條路徑的前置成本明顯低於商業引擎。

常見問題有哪些？

以下整理五個常見疑問，涵蓋收費方式、主機輸出、程式語言選擇、與 Unity 的差異，以及商業作品採用情況，答案依官方說明整理。

Godot 需要付費嗎？

不需要。Godot 採用 MIT 授權，開發者不需支付授權費、訂閱費或營收抽成，商業專案同樣適用。

Godot 可以輸出到家用主機嗎？

官方並未直接提供家用主機輸出，相關能力需透過第三方服務處理，這是與部分商業引擎的差異之一。

Godot 支援哪些程式語言？

引擎內建 GDScript，並支援 C#；需要與既有程式庫整合時，可透過 GDExtension 使用 C、C++ 與 Rust 等語言。

Godot 與 Unity 的主要差別是什麼？

最明顯的差別在授權與治理方式。Godot 為 MIT 授權、由非營利基金會支持；Unity 則採商業訂閱與分潤模式，兩者的工具鏈成熟度亦不同。

有商業遊戲使用 Godot 開發嗎？

有。市面已有以 Godot 開發並商業發行的作品，例如《Brotato》，主要集中於獨立遊戲與中小型專案。

總結：Godot 適合什麼團隊？

Godot 適合獨立團隊、2D 開發者、預算有限與重視開源的專案；若需要完整主機輸出支援與成熟的大型 3D 工具鏈，仍需評估替代方案。

Godot 在 2026 年的處境相當明確：它以 118,192 顆星成為開源遊戲引擎的代表，並用 MIT 授權與免抽成模式，提供商業引擎之外的另一條路。它的價值不只在於免費，更在於開發者能掌握工具本身，不必擔心授權條款隨公司策略變動。

選擇引擎終究是取捨。獨立團隊、2D 專案與重視長期可維護性的開發者，能在 Godot 取得明顯的成本與自由度優勢；需要完整主機支援與大型 3D 管線的工作室，則應把生態成熟度納入評估。對多數仍在起步階段的團隊而言，這個門檻低、條款單純的選項，值得認真列入比較清單。
