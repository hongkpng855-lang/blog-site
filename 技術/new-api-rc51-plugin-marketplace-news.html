New API 1.0 RC.51：插件市集把閘道變平台

2026年11月16日 04:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/QuantumNous/new-api

New API 於 2026 年 11 月 13 日發布 v1.0.0-rc.51，這個累積 51,949 顆星標、以 Go 撰寫的自架 AI 閘道，在 rc.50 一次加入提供商插件、請求處理插件與社群插件市集，把原本固定的協議轉換服務變成可擴充的平台，rc.51 則修復了不支援 AVX 指令集的 x86-64 機器上反覆崩潰的問題。

專案由 QuantumNous 維護，自 2023 年 11 月建立以來，把 OpenAI、Anthropic、Google Gemini、Azure OpenAI、AWS Bedrock、Vertex AI、DeepSeek 與 Qwen 等上游服務收斂成同一個入口。它同時提供 OpenAI Chat Completions、Responses、Anthropic Messages 與 Gemini 四套文本協議，並以 RelayKit 負責請求、回應與串流之間的格式轉換。

版本節奏相當密集。近三十日內發布七個版本，由 10 月 17 日的 rc.45 到 11 月 13 日的 rc.51，平均每四日一次更新，並累積 340 位貢獻者。這種節奏意味着單一版本的變更清單本身就構成一份升級風險文件。

New API RC.51 是什麼？

RC.51 於 2026 年 11 月 13 日發布，是 New API 1.0 系列的第 51 個候選版本，主要修復 rc.50 在部分 x86-64 處理器上處理請求時崩潰的問題。

這個版本本身屬於修補性質，內容集中在一個崩潰缺陷。rc.50 在具備 AES-NI 但沒有 AVX 指令集的 x86-64 處理器上，處理聊天等請求時會以 SIGILL 訊號結束進程。

受影響的硬件包括 Celeron、Pentium 與 Atom 系列，例如常見於軟路由與迷你主機的 J4125，以及只提供 AES 而不提供 AVX 的虛擬機。表現形式容易誤判，模型列表與管理後台仍可正常打開，只有請求路徑中斷，看起來像間歇性的 502。

修復方式是升級 JSON 程式庫 MoeForge moego 至 v0.1.0-alpha.3，令這類處理器改用 SSE 編碼的 AES 指令，輸出結果與其他處理器一致。官方明確建議在該類機器上運行 rc.50 的部署升級至本版本。

插件系統如何改變閘道的角色？

提供商插件把上游廠商接成一種渠道類型，請求處理插件在請求與回應上運行，兩者令閘道從固定的協議轉換器變成可按團隊規則擴充的中介層。

在插件出現之前，接入一個新的上游廠商需要改動核心程式碼，協議差異由 RelayKit 統一處理。提供商插件把這個過程外置，一個插件可以帶來路由、協議轉換、模型列表、需要登入的上游、權杖更新、餘額查詢與定時維護。

請求處理插件則運行在請求與回應之上，作用範圍可按全局、分組、渠道與模型分別設定。內建項目覆蓋請求過濾、請求脫敏、全局參數覆蓋、自動推理強度、圖片壓縮與內容審核。

兩類插件都可以先試運行，每處修改會記入用量日誌。這項設計讓管理員能在正式攔截流量之前，先確認插件對既有請求的實際影響，對於需要審計的企業部署尤其關鍵。

插件市集新增社群來源，官方與社群插件皆可按 8 位插件碼安裝，安裝時顯示使用說明與更新日誌，管理員亦可選擇主站或備用站下載。這種分發方式降低了自架用戶追蹤插件版本的難度。

請求過濾的相容性有什麼變化？

舊的敏感詞設定在首次啟動時遷移成一個請求過濾實例，命中時由原本的 500 錯誤改成 400 並回傳 request_rejected，舊設定項會被移除。

回滾需要特別留意。降回舊版本之後，敏感詞檢查處於關閉狀態，必須重新填寫，否則過濾機制形同失效。

錯誤碼的改變亦會影響既有客戶端。若上層應用依賴 500 狀態碼判斷是否重試，改為 400 之後便不會再觸發重試邏輯，這一層需要同步調整。

Vertex AI 插件在 1.3.1 版起把視頻請求發往渠道設定的部署地區，不再固定送往 global。升級前必須確認所使用的視頻模型在該地區可用，否則請求會被上游拒絕。

多節點部署有什麼變化？

設定、權限、插件、登入方式、模型、訂閱方案與渠道的手動改動，會在各節點數秒內同步，系統資訊頁可看到同步進度與載入失敗的節點。

這項改動把多節點部署從「逐台設定」推向「一次生效」。管理員在任一節點修改設定之後，其餘節點會在數秒內跟隨，系統資訊頁同時列出同步進度與失敗節點，便於排查。若需要回顧這個專案在十月時的閘道定位，可參考New API 早前版本的整理，兩次更新的重心分別落在協議覆蓋與擴充機制。

負載分配亦有調整。由 CHANNEL_UPDATE_FREQUENCY 控制的定時餘額更新，改為只在主節點運行，避免多節點重複向上游查詢餘額而觸發限流。

系統任務記錄改為每日自動清理，預設保留三十天。需要更長保留期的部署，必須先在系統設定、運維、日誌維護的路徑中調整天數，否則記錄會在期限後消失。「更新全部餘額」亦改為後台任務，列表隨進度刷新。

計費與支付有哪些調整？

圖片張數改按最終發往上游的請求計算，涵蓋 SiliconFlow 與 Replicate 的批次參數；易支付的簽名方式可選 MD5 或 RSA。

預扣邏輯同步跟隨。當插件或渠道覆蓋改動了張數，預扣金額會依最終數量調整，避免出現按預設值收取而實際用量更多的落差。Imagen 的 sampleCount 在不填寫時按四張計算，這一點在批次生成場景中容易造成估算偏差。

支付方面，易支付的簽名方式新增 RSA 選項，與原有的 MD5 並存。企業環境若要求非對稱簽名，這一項調整可以直接套用。

其他細項包括新增 HOST 環境變數以設定監聽位址，DeepSeek 渠道的 Chat Completions 請求會把 developer 角色轉成 system。修復項目則涵蓋透傳請求重試時新渠道收到殘缺請求體，以及切換渠道後模型重定向錯誤帶入前一渠道模型名的問題。

從生態角度看，閘道層的競爭已不限於協議數量。LiteLLM 1.108 則以長週期支援版本回應企業的升級焦慮，New API 選擇以插件擴充與多節點同步作為差異點，兩者針對的維運場景並不相同。

總結：哪些團隊適合升級到 RC.51？

在 Celeron、Pentium 或 Atom 等無 AVX 指令集的機器上運行 rc.50 的部署應立即升級；計劃試用插件系統的團隊則要預留回滾方案與過濾規則重建時間。

RC.51 的價值集中在穩定性。它不引入新功能，卻修掉一個表現隱蔽的崩潰缺陷，對於以迷你主機或虛擬機自架閘道的小型團隊，這一項修復足以影響服務可用性。

真正的架構變化發生在 rc.50。插件把閘道從固定的轉換器推向可編程的中介層，請求過濾、脫敏與參數覆蓋可以在不修改核心程式碼的前提下完成，並保留試運行與日誌紀錄。

代價是升級路徑變得更需要規劃。敏感詞設定遷移、錯誤碼改動、視頻請求地區、多節點同步行為，四項變化都會影響既有部署，任何一項遺漏都可能令服務在升級後才出現異常。對於依賴閘道承載生產流量的團隊，較穩妥的做法是先在測試節點完成遷移驗證，再逐台推進，並保留可回滾的舊版本映像。
