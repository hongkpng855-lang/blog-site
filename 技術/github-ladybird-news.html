Ladybird 瀏覽器：66.6K 星引擎邁向 alpha

2026年10月19日 00:00 • 閱讀時間 4 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/LadybirdBrowser/ladybird

Ladybird 是一個以自研引擎為基礎的獨立網頁瀏覽器專案，完全沒有採用 Chromium 或 Gecko 的程式碼，由非營利組織 Ladybird Browser Initiative 主導開發。截至 2026 年 10 月 17 日，該儲存庫在 GitHub 累積 66,552 顆星標、3,165 次複製與 88,575 次提交，貢獻者規模約 1,547 人，採用 BSD-2-Clause 授權。專案在 2026 年 9 月與資安公司 Trail of Bits 完成為期一週的聯合審查，贊助方為 OpenAI，同時推出一系列效能、記憶體與媒體播放架構的調整，並把 Web Platform Tests 分數推高至 210 萬項以上，為進入 alpha 測試階段鋪路。

Ladybird 是什麼？

Ladybird 是一套使用自研引擎的獨立開源瀏覽器，不依賴 Chromium 或 Gecko，目前仍屬 pre-alpha 階段，主要供開發者試用。

專案在 2024 年 6 月自 SerenityOS 分叉獨立，同一時期成立了 501(c)(3) 非營利組織 Ladybird Browser Initiative，並組成包含瀏覽器業界人士的董事會。儲存庫建立於 2024 年 5 月 30 日，官方網站明確標示專案仍處於 pre-alpha 狀態，只適合開發者使用，距離一般使用者的日常瀏覽需求仍有一段距離。

技術上，Ladybird 採用多行程架構。主介面行程之外，每個分頁都有自己的渲染行程，並以沙箱與系統其餘部分隔離；影像解碼與網路連線各自交由獨立行程處理，以降低惡意內容造成的影響。核心組件多數繼承自 SerenityOS，包括網頁渲染引擎 LibWeb、JavaScript 引擎 LibJS、WebAssembly 實作 LibWasm、密碼學與 TLS 函式庫，以及負責行程間通訊的 LibIPC。

專案在語言策略上也有明確轉向。2026 年 2 月，團隊宣布採用 Rust 作為 C++ 的接續語言，並借助 AI 代理加速移轉；至 2026 年 10 月，儲存庫中 Rust 程式碼量已達約 3,100 萬位元組，與 C++ 的 3,760 萬位元組相當接近。

Ladybird 在 2026 年 9 月完成了哪些安全強化？

該月專案收緊了行程隔離與權限邊界：Cookie 改由網路行程處理，擅自索取特權的渲染行程會被終止，macOS 與 Linux 的沙箱同時收窄。

安全模型的前提是假設渲染行程可能被攻破。團隊指出，即使惡意網頁利用漏洞取得渲染行程控制權，其他行程仍必須把該行程送出的訊息視為不可信，並逐一驗證請求的操作；每個行程只應擁有執行本職工作所需的最低系統存取權限。

其中一項具體調整與 Cookie 有關。被攻破的渲染行程原本可以要求瀏覽器讀取或覆寫任何網站的 HttpOnly Cookie，而這類 Cookie 正是刻意對網頁 JavaScript 隱藏的內容。現在網路行程統一處理 HTTP 回應與 WebSocket 握手過程的 Cookie，一旦渲染行程索取這項特權存取，瀏覽器會直接終止該行程。

輔助行程的沙箱亦同步收緊。macOS 端限制服務與檔案存取，並啟用強化執行環境，阻止從可寫入記憶體執行程式碼；Linux 端則禁止輔助行程連線至使用者工作階段中的任意 Unix 網域通訊端，並在 GPU 驅動執行緒啟動前套用 Landlock 檔案系統限制，使這些執行緒同樣受到約束，輔助行程預設在缺少 Landlock 時拒絕啟動。此外，跨站 iframe 現在可以獨立於所屬頁面存在於不同行程，網頁測試執行器預設演練這條路徑。

Trail of Bits 與 OpenAI 在這次審查中扮演什麼角色？

Trail of Bits 花一週審查 Ladybird，並以 OpenAI 的前沿模型找尋安全問題、建構攻擊鏈，活動由 Patch the Planet 計畫贊助。

2026 年 9 月，Ladybird 團隊與資安公司 Trail of Bits 的工程師合作一週，活動屬於 OpenAI 贊助的 Patch the Planet 計畫。團隊在月報中說明，這是專案第一次被以如此強度檢視，對方不僅找出多項安全問題，還實際建構了幾條完整攻擊鏈。

這場審查的產出之一是一份相當長的安全待辦清單，也讓團隊重新校準安全模型的假設。團隊強調，安全維護不會是一次性的專案，只要 Ladybird 持續存在，這類工作就會持續進行，因此這次合作既是壓力測試，也是後續開發的基準線。

Ladybird 的效能與記憶體表現改善了哪些部分？

該月修正了計時器鏈、隱藏分頁與離螢幕動畫的資源浪費，並解決文件無法回收的問題；Linux 的 Speedometer 3 分數上升約五成。

效能修正多數來自真實網站的案例。一個新聞網站的廣告函式庫在被內容封鎖器攔截後，仍以連續的零延遲計時器反覆檢查，而引擎未在回呼之間保留計時器鏈的嵌套層級，導致瀏覽器規定的四毫秒最小延遲沒有生效，檢查以最快速度反覆執行；補上延遲後，輪詢的處理器成本降到極低。

隱藏分頁與離螢幕內容是另一類問題。團隊比照其他瀏覽器，對隱藏頁面的計時器加入節流，並停止為視窗外內容產生動畫影格、跳過沒有變化的畫面呈現，使渲染行程與合成行程幾乎進入閒置。記憶體方面，部分新聞網站會以計時器重新載入頁面，而被替換的文件一直未被釋放，其中兩個網站在背景分頁分別累積到 11 GB 與 20 小時後的 15 GB；團隊修補了導航請求、待處理動畫影格與閒置回呼所持有的參照，讓被替換的文件可以回收。字型檔案不再重複複製，CSS 資料也改為共享與壓縮。

成果反映在跑分上。2026 年 9 月，專案的 Linux 持續整合環境中，Speedometer 2 分數上升約 30%，Speedometer 3 上升約 50%，專注於 CSS 重算的 StyleBench 上升約 80%。同時，原生的 Task Manager 視窗取代了先前的行程檢視頁面，提供可搜尋的行程樹、可排序的處理器與記憶體欄位，以及結束行程的操作。

Ladybird 的媒體播放與繪圖架構有什麼變化？

macOS 端改用 VideoToolbox 硬體解碼，支援 H.264、HEVC、VP9 與 AV1；音訊與視訊管線移入獨立媒體行程，OffscreenCanvas 擴充。

視訊播放路徑出現兩項變化。在 macOS 上，播放改用 VideoToolbox 進行硬體解碼，處理器負載明顯低於以 FFmpeg 軟體解碼，並在硬體支援時涵蓋 H.264、HEVC、VP9 與 AV1；解碼後的影格直接送達合成器，不再複製像素。與此同時，音訊與視訊的解碼與播放管線移入獨立的媒體行程，媒體行程崩潰只會造成播放錯誤，渲染行程也不再需要解碼器服務權限。

為了準備日後的分發，團隊從內建的 FFmpeg 組建中移除受專利限制的 H.264、HEVC 與 AAC 解碼器；Linux 在系統提供時改為載入系統版 FFmpeg，macOS 則使用 VideoToolbox 與 AudioToolbox。

繪圖與動畫方面，合成器可獨立於頁面主執行緒處理的動畫範圍擴大，新增不透明度、變形、背景色與濾鏡等情形；OffscreenCanvas 在頁面與工作執行緒中的 2D、WebGL 與 WebGL2 渲染已可用並預設啟用，頁面可將畫布交給專屬工作執行緒，由該執行緒直接向合成器提交影格。其他實用修正包括支援把桌面圖片貼入網頁的可編輯內容、修正 Slate 類編輯器的輸入法組字事件，以及針對 GitHub 檔案列、半島電視台、日本時報與 Shopify 的相容性調整。

程式碼組成反映語言移轉正在進行。以位元組計算，C++ 約占 3,760 萬、Rust 約占 3,100 萬，其後依序為 HTML、JavaScript 與 Python，另有組合語言、CMake 與 Objective-C++ 等部分。提交密度極高，2026 年 10 月 17 日當天的提交紀錄涵蓋 Qt 介面的自動完成彈出樣式、內容封鎖彈出視窗的操作行為，以及 macOS 工作管理員的樣式調整。

網站相容性的進展同樣可量化。團隊以 Web Platform Tests 作為主要指標，分數由 2,088,677 上升至 2,109,072，單月增加 20,395 項子測試；其中約一半來自上游當月新增的測試，主要為 SVG 互動與 HTML／DOM 相關項目，其餘增量則以 OffscreenCanvas 約 1,500 項與 contain-intrinsic-size 約 500 項最為明顯。

Ladybird 如何準備進入 alpha 測試？

團隊把桌面介面收斂到 Qt 單一前端，重寫 macOS 圖形呈現路徑，並加入可離線保存、可選擇是否上傳的崩潰回報機制，同時完成篩選清單自動更新。

進入 alpha 前的整備工作集中在收斂與可診斷性。專案過去維護數個圖形介面前端，現在 Qt 是唯一的桌面前端，所有介面開發集中於此。macOS 的圖形呈現路徑亦重新設計，合成器影格直接送往原生顯示層，省下一次 Metal 渲染與介面執行緒等待可繪製物件的流程，改善低耗電模式下的捲動遲滯。

診斷能力方面，專案加入崩潰回報器。當 macOS 或 Linux 上的輔助行程崩潰時，系統會保存本機報告，內容包含回溯、斷言失敗或 Rust panic 細節與建置資訊，且不含瀏覽資料與本機檔案路徑；頁面崩潰時，崩潰畫面會說明報告內容並允許使用者補充幾句說明，由使用者自行決定是否送往回報服務。報告檔案也可從設定的一般分頁開啟所在資料夾。

團隊指出，篩選清單自動更新與無需終端機的崩潰回報，正是上個月路線圖上用於 alpha 的兩項待辦；這兩項如今已經到位。

Ladybird 與主流瀏覽器有何不同？

差異在於引擎完全自研、以非營利組織與贊助者資金運作，且不跟隨 Chromium 架構；代價是相容性與功能覆蓋仍需時間累積，目前僅適合開發者試用。

多數新興瀏覽器選擇以 Chromium 為基礎再行加值，Ladybird 則從渲染引擎、JavaScript 引擎到網路與密碼學函式庫全數自建，這也是它以「真正獨立」定位的原因。資金模式同樣不同：專案由非營利組織運作，經費來自願意支持開放網頁的企業與個人贊助者，而非廣告或資料變現。

這條路線的成本直接反映在相容性工作上。團隊逐月處理具體網站的問題，例如讓文章內容正常渲染、修復登入按鈕、實作 CSS 捲動狀態查詢，並在 2025 年通過 Google reCAPTCHA、2026 年通過 Cloudflare Turnstile 等機器人驗證關卡。這些進展以 Web Platform Tests 與網站相容性為衡量基準，而非以市占率為目標。

對開發者而言，專案採用寬鬆的 BSD-2-Clause 授權，程式碼與每月工程月報公開，適合關注引擎實作、沙箱設計與多行程架構的讀者長期追蹤。不過團隊本身也提醒，目前版本只適合開發者，日常使用仍需等待 alpha 之後的進展。

總結：Ladybird 適合哪些開發者關注？

適合關注瀏覽器引擎實作、多行程沙箱與網頁標準進度的開發者；若需要立即可用的日常瀏覽器，現階段仍應選擇成熟產品，等待其 alpha 版本。

2026 年 9 月的進展顯示，這個專案已從「能否運作」的階段，進入以安全審查、效能回收與可診斷性為主的工程階段。Trail of Bits 的審查帶來一份不短的安全待辦清單，同時也讓行程隔離與權限邊界變得更明確；效能與記憶體的修正則針對真實網站的行為，而非實驗室情境。

值得注意的是，專案沒有把資源投放在宣傳或功能競賽，而是集中在相容性測試、沙箱收緊與發佈前的整備，這種節奏與非營利組織的資金結構相符。對引擎開發有興趣的讀者，可以從每月月報追蹤它如何逐步補齊網頁標準；對一般使用者而言，等到 alpha 版本正式釋出後再評估，會是更務實的選擇。
