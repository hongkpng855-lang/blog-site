browser-use 改寫引擎：Pi 接手、砍 5.5 萬行程式碼

2026年10月30日 08:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/browser-use/browser-use

browser-use 是採 MIT 授權的開源瀏覽器代理框架，在程式碼託管平台累積 119,484 顆星標。專案於 2026 年 10 月 24 日提交代號 Pi 的引擎改寫草案，以 TypeScript 撰寫的 Pi 取代原有 Python 規劃器與 Rust 實驗分支，估計刪減 55,184 行程式碼，草案目前尚未合併。

browser-use 是什麼？

browser-use 是採 MIT 授權的開源瀏覽器代理框架，讓大型語言模型操作真實瀏覽器完成網頁任務，GitHub 星標達 119,484 顆。

專案在 2024 年 10 月底建立，定位是讓模型像人一樣操作瀏覽器：開啟頁面、填寫表單、處理驗證碼、完成預約與下單等連續動作。官方提供的示範任務是查詢可預約時段、挑選日期，再完成駕駛考試的預約流程。

使用形態分成三條路徑。完全託管的雲端代理由官方執行代理程式、瀏覽器與基礎設施；命令列工具把瀏覽能力交給既有的編碼代理，文件點名的對象包括 Claude Code、Codex、Hermes、OpenClaw、Pi 與 Cursor；Python 函式庫則讓開發者在自己的應用程式內執行代理，並自訂工具與結構化輸出。

這次引擎改寫的核心變動是什麼？

以 Pi 取代 Python 規劃器與 Rust 實驗分支，同時保留 pip 安裝與匯入路徑。雲端瀏覽器成為預設，模型別名改為 bu-recommended 等三個。

草案說明的替換範圍相當徹底。舊有的規劃器、Watchdog 監控層、DOM 序列化器、各家供應商包裝層與 Rust 實驗分支一併移除，改由 Pi 引擎承接瀏覽決策。原生 TypeScript 直接使用同一套引擎，不再經過 Python 橋接層。

對外介面則刻意維持不變。使用者仍然可以執行 uv add browser-use 或 pip install browser-use，Python 匯入路徑與命令列入口都保留，平台預編譯套件內含私有 Node 執行環境與產生好的引擎檔。

模型與瀏覽器的預設值有明顯調整。雲端瀏覽器成為預設瀏覽器，bu-recommended 成為經由 Browser Use 閘道呼叫的預設模型，並新增 bu-balanced 與 bu-smart 兩個別名。舊有的 BU2 模型需要鎖定 browser-use<1 才能繼續使用，明確指定的 Chrome、Chromium、CDP 連線與各供應商模型字串則維持可用。

為什麼要改用 Pi 作為引擎？

提案把維護兩套執行環境的成本列為主要理由。生產程式碼由 66,924 行降至 11,740 行，單一引擎同時服務兩種語言。

草案公布的程式碼規模變化，是這次改寫最具體的數字。遷移後生產程式碼為 11,740 行，較原先的 66,924 行減少 55,184 行，統計已排除內嵌測試、實驗場、產生資產與相依套件。

從架構角度看，這次改動把「決策」與「執行」分離得更乾淨。Python 端保留安裝體驗與公開 API，實際的瀏覽規劃交給以 TypeScript 撰寫的引擎，原生 TypeScript 專案則直接引用同一份實作。OpenAI 與 Anthropic 的轉接層改用共用的 Pi 瀏覽輔助函式，不再依賴舊版 Python 實作。

改版後的效能表現如何？

凍結基準測試中，Pi 分支得 62.905 分，遷移分支得 58.350 分，滿分為 100。提案明言此輪比較未建立效能對等，仍待修正後重新量測。

比較採用 BU Bench V2.1 的凍結版本，每個分支各執行 200 項任務，合計 400 次獨立嘗試。測試設定為 80 個並行嘗試、配對順序做過平衡、不進行結果重試，兩個分支都使用 Browser Use 雲端瀏覽器與同一個外部模型，推理強度設為 xhigh。這輪比較並未經過新的 Browser Use 閘道。

評分規則對缺漏相對嚴格。未產生結果的任務以零分計，其中一筆遷移分支的判定含有無效 JSON。提案同時註明，在提示、橋接與相容性修正之後並不存在完整比較分數，因此該文件不主張兩個分支已達到效能對等。

專案維護者把發布條件寫得相當具體。合併前需要配套的 Go 閘道提案、經過驗證的預備環境檢查、重新執行且條件匹配的基準比較，另外還有巢狀相依的漏洞更新與各供應商遠端檔案的驗證。可攜式雲端下載、自訂代理網址與閘道價格中繼資料也列為尚未完成項目。

Python 開發者需要改動程式碼嗎？

主要路徑維持不變，Agent 建構式、run 與 final_result 都保留，follow_up 也能延續對話紀錄。已淘汰選項提出警告，不支援的包裝層直接拒絕。

文件列出的相容清單覆蓋了多數日常用法。Browser(use_cloud=True) 與 Browser(cdp_url=...) 保留原本的設定方式，建構式結構化輸出仍可使用，自訂工具、審批、初始化掛鉤、事件回呼、暫停、續跑、轉向與清理也都保留。

行為差異集中在錯誤處理。無害但已淘汰的選項會發出警告，不再支援的模型包裝層與安全設定會明確拒絕，缺少憑證時會直接給出建立 API 金鑰的網址，而不是留下模糊的連線失敗。

驗證規模提供另一個參照點。Python 用戶端 49 項測試通過，命令列與供應商轉接層 75 項通過、1 項跳過，TypeScript 245 項通過、1 項跳過，型別檢查、格式檢查、Ruff、Pyright 與提交前檢查全數通過，五個原生預編譯套件的安裝檢查也已完成。橋接層的輸出上限同時放寬至 64 MB 訊框與 128 MB 待處理輸出，讓 10.5 MB 的基準產出檔得以通過。

遙測與權限邊界有哪些變化？

任務結束時送出單一遙測事件，內含設定、功能計數、用量、任務文字、輸出與錯誤。取消追蹤設定保留，Bash 與檔案工具在應用程式所在機器執行。

遙測設計改成一次集中送出。舊版分散在多個步驟的遙測，改為任務結束時送出單一事件，內容涵蓋設定、功能計數、用量、任務文字、輸出、錯誤與經過清理的 CDP 網址；既有的取消追蹤設定與敏感欄位遮蔽規則一併保留。直接以標準輸入或 MCP 呼叫的路徑，目前不會送出替代的產品遙測。

權限邊界則被明確寫成非目標。提案指出 Bash 與檔案工具在應用程式所在機器執行，瀏覽器服務必須自行落實網路與 CDP 限制，軟體開發套件本身不提供主機沙箱。CDP 連線支援經過驗證的探索、自訂標頭、TLS 驗證、用戶端憑證與初始化腳本，讓需要更強隔離的團隊把隔離責任放在部署層。

開源授權與商業模式如何分工？

Python 函式庫免費且採 MIT 授權，模型推論與託管瀏覽器另行計費。雲端瀏覽器每瀏覽器小時 0.02 美元起，官方稱隱身基準取得 90.5%。

授權與收費切得很清楚。函式庫本身免費且為 MIT 授權，使用者可以用本機瀏覽器搭配本機模型，透過 Ollama 執行，硬體與模型需求由使用者自行承擔。模型推論與託管瀏覽器屬於另一層服務，包含 ChatBrowserUse 在內的供應商呼叫與雲端瀏覽器都按用量計費。

雲端定價為每瀏覽器小時 0.02 美元，另加網路流量，附帶隱身模式、住宅代理、驗證碼處理與即時檢視網址。官方在 Stealth Bench V2 取得 90.5% 的成績，並以 BU2 作為瀏覽自動化的推薦模型；同一個模型也能透過閘道以供應商前綴的識別碼呼叫 Claude 或 Gemini 系列。

與外部代理的整合是另一條產品線。Browser Use 為 Claude 的工具集實作全部 31 個瀏覽動作，可驅動本機瀏覽器、雲端瀏覽器或以 CDP 連線的遠端瀏覽器；Browser Use Actor 則提供 18 個預設瀏覽工具與 6 個選用動作。這條路線的意義是讓既有代理直接取得瀏覽能力，不必自行維護瀏覽器控制層。

總結：browser-use 適合什麼團隊？

適合已用 Python 建立瀏覽自動化流程、且願意接受引擎更換過渡期的團隊。若任務高度依賴舊版規劃器行為或 BU2 模型，應先鎖定版本再評估升級。

這次改寫的關鍵在於節奏與透明度。專案先發布 0.13.14 作為最後一個完整的 Python 執行環境版本，把 Pi 遷移留在獨立的草案中處理，並在提案內如實列出基準比較未達對等、發布條件尚未齊備。對於導入這套框架的團隊，這種把不確定性寫在文件裡的作法，比宣稱效能提升更有參考價值。

實務上的判讀重點有三個。既有專案應確認是否依賴被移除的規劃器行為、Watchdog 設定或供應商包裝層；使用 BU2 模型的部署需要鎖定 browser-use<1；打算長期跟進主線的團隊，則應在切換前自行跑一輪內部任務集，因為官方對外公布的凍結比較僅涵蓋 200 項任務，且明確不主張效能對等。

在瀏覽代理這個競爭激烈的領域，11.9 萬顆星標、10,436 次提交與 361 位具名貢獻者構成了相當厚的基礎。真正的觀察點是配套的閘道提案與重新量測的基準何時到位，那將決定這次換心是平順過渡，還是需要使用者付出額外的調校成本。
