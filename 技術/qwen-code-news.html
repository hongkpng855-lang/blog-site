Qwen Code 開源：28k 星終端編碼代理對標 Claude Code

2026年10月21日 20:00 • 閱讀時間 4 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/QwenLM/qwen-code

阿里雲 QwenLM 團隊維護的 qwen-code 於 2026 年 10 月累積 28,624 顆星標、3,238 個分支與 419 名貢獻者，定位為執行於終端、編輯器、桌面與聊天工具的開源編碼代理。專案自 Google Gemini CLI v0.8.2 分支出來後獨立發展，官方在說明文件中直接把它與 Claude Code 併列比較，並補上多協定支援、多客戶端 Daemon 與跨模型對戰等對方尚未提供的功能。對正在評估編碼代理的團隊而言，這個專案的意義不在於又一個 CLI 工具，而在於把供應商鎖定的問題搬到架構層解決。

Qwen Code 是什麼？

Qwen Code 是阿里雲的開源終端編碼代理，Apache-2.0 授權，可接 OpenAI、Anthropic 與本地模型，累積 28,624 顆星標。

專案的原始碼起點寫得相當坦率。README 說明它最初基於 Google Gemini CLI v0.8.2 開發，從 v0.1 起停止同步上游，轉為獨立的多協定、多平台代理框架。這種出身讓它繼承了一套成熟的終端互動設計，包括工作目錄感知、檔案編輯確認與工具呼叫流程，同時避開從零打造代理迴圈的成本。

目前專案提供六種使用介面，終端以 qwen 指令啟動，桌面版支援 macOS、Windows 與 Linux，另有實驗性的 Web UI 與 VS Code、Zed、JetBrains 三款編輯器外掛。聊天整合涵蓋 Telegram、釘釘、微信與飛書，開發者可透過 qwen channel start 在既有通訊軟體中呼叫代理。這種廣度在同類工具中並不常見，多數競品仍聚焦單一終端場景。

專案的迭代密度構成另一項觀察指標。儲存庫累積 11,247 次提交與 585 個版本標籤，最近一次提交發生在 2026 年 10 月 21 日，最新版本 v0.25.3 於 10 月 19 日發布。官方在 README 中表示，專案正以自身代理與模型處理議題回報、提交合併請求與程式碼審查，形成一定程度的自我循環。

Qwen Code 與 Claude Code 有什麼差異？

兩者在子代理、技能與 MCP 上大致對等；Qwen Code 另有開源模型、多協定支援、Agent Arena 與 Daemon 模式。

README 直接列出一張逐項對照表，把兩者的功能差距攤開。子代理、代理團隊、動態工作流、自動記憶、自動技能、Hooks、內建技能、MCP、計畫模式、LSP 整合、沙箱、Git Worktrees、桌面自動化、IDE 外掛與 SDK，在兩邊都標記為支援。這種對齊程度意味著從 Claude Code 遷移的使用者，不太需要重新學習操作邏輯。

差異集中在四項。第一是開源範圍，Qwen Code 的框架與模型皆為開源，Claude Code 僅開源客戶端工具。第二是協定層，Qwen Code 同時接受 OpenAI、Anthropic、Gemini 與 Qwen 四種 API 格式，並可指向 Ollama 或 vLLM 等本地端點，切換在執行期完成，不需重新安裝。

第三是 Agent Arena，讓多個模型在同一任務上並行作答並互相比較，適合需要為特定專案挑選模型的團隊。第四是 Daemon 模式，透過 qwen serve 以 HTTP 加 SSE 提供服務，多個客戶端可共用同一個代理會話，這種設計讓終端、桌面與聊天工具能維持一致上下文，而非各自開啟獨立程序。

Qwen Code 的技術架構有什麼特點？

架構分終端核心、SDK 與客戶端三層，提供 TypeScript、Python 與 Java 三套 SDK，並以 ACP 協定轉派任務。

代理迴圈沿用主流的觀察、思考、工具呼叫三段結構，差異在於把記憶與技能做成自動化層。Auto-Memory 在使用過程中累積專案知識，Auto-Skills 依任務類型自動載入對應技能，開發者不必手動維護提示檔。內建技能包含 /review、/batch、/loop 與 /bugfix，覆蓋程式碼審查、批次修改、迴圈執行與錯誤修復四種高頻場景。

SDK 層是這套架構能否進入企業流程的關鍵。TypeScript、Python 與 Java 三套 SDK 讓既有系統可以程式化呼叫代理，例如在 CI 流程中以 qwen -p "..." 執行無介面模式，或在 Python 服務中把代理當成函式使用。官方提供的範例以 query 方法啟動任務並迭代回傳訊息，與一般非同步任務佇列的使用方式接近。

協定層則指向代理互通的長期方向。專案支援 ACP，讓 Claude Code 或 Codex 等外部代理把編碼任務轉派給 Qwen Code，官方生態清單中的 Qwen Code Claw 便是一個具體實作。電腦使用能力透過原生 MCP 工具或 Node REPL 加 SDK 提供，可在 Qwen Code、Claude Code 與 Codex 之間共用同一套桌面自動化介面，這種安排減少重複實作，也降低工具鏈斷裂的風險。

Qwen Code 的實測效能表現如何？

官方以同一組 Qwen 3.7 Max 測試七個版本，SWE-bench Verified 平均落在 76.40% 至 77.80%，每版 500 題。

評測方法寫得比多數專案清楚。官方固定使用 Qwen 3.7 Max 作為推理模型，對七個版本的 Qwen Code 各執行 500 個 SWE-bench Verified 任務，每個版本重複三次後取平均，藉此排除模型能力變動的干擾，單獨觀察代理框架本身的差異。結果顯示 v0.0.14 取得 77.80%，v0.15.0 為 77.67%，v0.22.0 為 77.33%，最低的 v0.19.0 仍有 76.40%。

版本間的波動幅度約 1.4 個百分點，這個區間在 500 題的樣本規模下屬於正常震盪，說明框架改版並未帶來顯著的效能退步。換句話說，專案在一年內推進二十多個版本、把介面從終端擴展到桌面與聊天工具之後，核心任務完成能力仍維持在同一水準，這對需要長期穩定性的團隊是一個正面訊號。

專案同時公開完整評測設定與逐版結果，供外部重現。這種透明度在同類工具中仍屬少數，多數競品僅公布單一版本的分數，缺乏跨版本的趨勢觀察。

如何安裝與開始使用 Qwen Code？

Linux 與 macOS 可用安裝腳本或 npm，Windows 另有 PowerShell 腳本；啟動後執行 /auth 設定供應商與金鑰。

安裝路徑分為三種。官方建議的獨立安裝腳本以 curl 或 irm 下載執行，適用於不想引入 Node 環境的使用者；npm 方式需 Node.js 22 以上版本，指令為全域安裝；Homebrew 則提供 macOS 與 Linux 的簡化路徑。三種方式在安裝完成後都需重啟終端，讓環境變數生效。

首次啟動的門檻主要是驗證設定。在專案目錄執行 qwen 進入會話後，透過 /auth 選擇模型供應商並輸入 API 金鑰，之後即可直接以自然語言下達任務。官方建議的第一個指令是要求代理解釋整個儲存庫並指出起點，這種用法能在短時間內驗證檔案讀取與索引是否正常。

自動化場景則走無介面模式。在腳本或 CI 流程中以 qwen -p 帶入提示，代理完成後輸出結果並結束，不需互動。若團隊使用阿里雲百煉平台，官方 CLI 可延伸出圖像與影片生成、知識檢索與模型部署能力，對於已經在該平台運行的服務，整合成本相對較低。

下載數據反映實際使用規模。npm 套件在 2026 年 10 月 12 日至 18 日的一週內錄得 45,040 次下載，這個數字只計 npm 渠道，尚未包含獨立安裝腳本與 Homebrew 的安裝量。對照 28,624 顆星標，下載與收藏的比例接近一點六倍，說明有一定比例的使用者已進入實際部署階段，而非僅止於關注。

專案的活躍度可以從更新頻率判斷。從 2025 年 6 月建立至今約十六個月，累積 585 個版本標籤，平均每月超過三十六個版本，其中包含 nightly 與 preview 通道。這種節奏對追求穩定的企業團隊構成雙面效果：功能推進快速，但版本鎖定與回歸測試必須自行把關。

Qwen Code 適合哪些開發團隊？

需要避免供應商鎖定、要在本地或私有雲執行模型、或希望把編碼代理嵌入既有 CI 與通訊工具的團隊最適合；只追求開箱即用與官方支援的團隊，閉源方案仍較省事。

第一類適合的對象是有資料落地要求的組織。Qwen Code 可指向 Ollama、vLLM 等本地端點，模型與提示不出境，對於處理敏感程式碼或受監管行業的團隊，這條路徑省去逐一申請雲端服務的程序。代價是本地推理需要相應硬體，且小型模型的任務完成率與雲端旗艦存在差距。

第二類是需要多模型策略的團隊。Agent Arena 讓同一任務在多個模型上並行執行並比較結果，這種能力在模型價格與能力快速變動的時期具備實用價值，團隊可以按任務類型分配模型，而非全部押在單一供應商。

第三類是已有自動化流程的工程組織。三套 SDK 與無介面模式讓代理可以成為 CI 流程中的一個步驟，例如在合併請求前自動執行審查或補齊測試。若團隊同時使用多種代理工具，ACP 支援讓任務可以在其間轉派，減少重複維護提示與工具定義的工作。

需要謹慎的情況同樣明確。專案目前有 1,931 個未結議題，版本迭代快速，對於無法承擔升級成本的小型團隊，跟進節奏可能成為負擔。此外，專案以簡體中文與英文文件為主，繁體中文資源仍有限。

出處連結有哪些？

本文整理自 QwenLM 團隊的 qwen-code 儲存庫，涵蓋功能對照、SWE-bench 評測、安裝說明與版本紀錄。

儲存庫網址：https://github.com/QwenLM/qwen-code

官方文件站提供使用者指南、驗證設定、IDE 整合與 Daemon 模式說明，並有簡體中文、德文、法文、日文、韓文、俄文與葡萄牙文版本。評測設定與逐版結果另存於儲存庫的 docs/evaluation.md，供外部核對。

總結：Qwen Code 值得採用嗎？

若重視模型可替換性、需要本地部署，或要把代理嵌入既有流程，Qwen Code 是覆蓋最完整的開源選項之一；若只要穩定支援，閉源方案仍較省事。

這個專案真正的價值不在追平功能清單，而在把選擇權留在使用者手上。當編碼代理逐漸成為開發流程的基礎設施，能否更換模型、能否在本地執行、能否與其他代理互通，會比單次任務的完成率更影響長期成本。Qwen Code 在協定層與 SDK 層的投入，正是針對這三個問題作答。

風險同樣存在。1,931 個未結議題與每月三十多個版本的節奏，意味著使用者需要自行承擔穩定性驗證；繁體中文文件與社群支援仍在起步階段，遇到邊界問題時可依賴的資源有限。較務實的做法是先以單一專案試用，確認代理在自身程式庫的表現與工具鏈整合程度，再決定是否擴大到團隊層級。
