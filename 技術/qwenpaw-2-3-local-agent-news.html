QwenPaw 開源：3.7 萬星本地 AI 助理工作站

2026年11月04日 04:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/agentscope-ai/QwenPaw

QwenPaw 是阿里巴巴 AgentScope 團隊開源的個人 AI 助理工作站，十一月二日推出 v2.3.0-beta.2，在 GitHub 累積三萬七千二百一十七顆星，採 Apache 2.0 授權。它把三層記憶、本地模型推論與五層安全管控整合在同一介面，並可接入釘釘、飛書等通訊渠道。

QwenPaw 是可在本機或雲端自架的個人 AI 助理，自帶 QwenPaw-Flash 系列模型與五層安全機制，可透過網頁主控台、終端介面與多個通訊軟體操作。

專案同時累積三千二百五十四次分叉與三百五十六名貢獻者，主要語言為 TypeScript，後端以 Python 撰寫。完整名稱是 Qwen Personal Agent Workstation，命名取了 Qwen 的縮寫與爪子的意象，README 開頭寫明希望它不是冷冰冰的工具，而是隨時待命的數位夥伴。

QwenPaw 是什麼？

它是一套可自行部署的 AI 助理系統，包含網頁主控台、終端介面與桌面應用，能接入多個通訊軟體，並內建記憶、技能、排程與權限管控，定位接近自架的個人代理平台。

專案於二零二六年二月二十四日建立，主要語言為 TypeScript，後端以 Python 撰寫並要求 3.11 至 3.13 版本。目前仍有約一千一百二十七個未結問題，這個數字反映社群活躍程度，也說明專案仍在快速變動的階段。

與一般聊天前端不同，QwenPaw 把自己定位成工作站。它同時提供網頁介面、全螢幕終端介面與 Tauri 桌面應用，三者驅動同一個代理，共用同一份記憶、技能與工作階段。

QwenPaw 的三層記憶如何運作？

三層分別為即時工作上下文、完整的逐字歷史，以及由 ReMe 支援、會自我演化的個人知識庫。三者都以可編輯的 Markdown 檔案形式保存。

這個設計的關鍵在於把記憶從向量資料庫拉回檔案系統。使用者可以直接用文字編輯器打開記憶檔案，修改錯漏或刪除過期內容，不需要透過黑箱檢索調整。

逐字歷史與知識庫分開存放，意味著舊對話不會被摘要覆蓋。需要回溯某次決策時可以翻原文，需要快速檢索時則查知識庫，兩者各司其職。

QwenPaw 的本地模型方案有什麼特別？

專案自帶 QwenPaw-Flash 系列，參數涵蓋 2B、4B、9B、27B 與 35B-A3B，提供 Q4 與 Q8 量化版本，內建 llama.cpp 並依硬體推薦模型。

這批模型在 ModelScope 與 Hugging Face 同步發布。對沒有獨立顯示卡的使用者，2B 與 4B 版本提供了一條入門路徑；對有較好硬體的使用者，35B-A3B 這類混合專家架構則在記憶體佔用與能力之間取得折衷。

除了自帶模型，專案也支援 Ollama 與 LM Studio 兩種本地方案，以及包含 DashScope、OpenAI、Anthropic、Gemini、DeepSeek、Kimi 與 OpenRouter 在內的十四家以上雲端供應商。使用純本地模型時不需要任何 API 金鑰。

QwenPaw 有哪些安全機制？

共五層：核心層沙盒、工具守衛、檔案守衛、技能掃描器與存取策略。沙盒在三大平台各自提供隔離，工具守衛在每次呼叫前檢查注入與越權。

工具守衛是一套 YAML 規則引擎，內含名為 ShellEvasionGuardian 的模組，專門辨識命令注入、路徑穿越、反向 shell 與混淆攻擊。它的審批等級分為 STRICT、SMART、AUTO、OFF 四段，讓使用者在安全與順手之間自行取捨。

檔案守衛獨立於工具守衛運作，預設保護 ~/.qwenpaw.secret/、~/.ssh 等敏感目錄。技能掃描器則在技能啟用前檢查提示注入、硬編碼密鑰與資料外傳，並支援封鎖、警告、關閉三種模式。

存取策略是宣告式的規則層，可以針對每個能力呼叫指定允許、拒絕或要求人工批准，且能按來源比對。這一層把權限顆粒度細化到單一工具，而不是整個代理。

v2.3.0-beta.2 這次更新改了什麼？

主要變動包括把通訊渠道抽出成外掛並以子進程隔離、加入決策模型支援的工具審批模式、整合 ReMe 記憶，以及新增 Firecrawl 作為搜尋供應商。

渠道外掛化是這次最結構性的改動。把釘釘、飛書這類渠道從核心拆出並放進獨立子進程，單一渠道崩潰不再拖垮整個代理，也讓第三方自行開發渠道變得可行。

工具審批模式引入了決策模型，由一個輕量模型先判斷某次工具呼叫是否危險，再決定放行或轉交人工確認。專案路線圖同時列出把非核心元件全部插件化的目標，理由是降低安裝體積與執行成本。

QwenPaw 與其他自架助理有什麼差別？

差別在渠道覆蓋與模型配套。多數同類專案只提供網頁介面，QwenPaw 另有終端介面、桌面應用與七個通訊渠道，並自帶專為代理任務訓練的模型系列。

另一個差別是多代理能力。它允許啟動帶有獨立記憶與技能的代理，並透過 Agent Communication Protocol 與外部系統編排。這個協定讓 QwenPaw 的代理可以與其他遵循同一規範的系統交換任務。

技能與外掛構成第三層差異。官方市集提供排程、文件、瀏覽器、新聞等技能，也可透過 MCP 接入外部工具，把零散能力組合成固定流程。

安裝與部署需要什麼條件？

需要 Python 3.11 至 3.13，可用 pip、官方腳本、Docker 映像或阿里雲一鍵部署。安裝後執行初始化並啟動，主控台預設在 8088 埠。

三條主要路徑各有取捨。pip 安裝最適合已有 Python 環境的開發者；官方腳本會自動下載 uv 並建立虛擬環境，適合不想手動處理依賴的人；Docker 映像則把資料、密鑰與備份分成三個磁碟區，方便備份與遷移。

Docker 路徑有一個細節要注意。容器內的 localhost 指向容器本身，若模型服務跑在主機上，需要加上主機閘道對應，再把模型服務的位址改為 host.docker.internal 才能連通。

QwenPaw 適合哪些使用者？

適合想把資料留在自己機器、同時需要多個通訊軟體入口的使用者，以及願意為權限管控花時間設定的團隊。純粹想試聊天機器人者，雲端服務更快。

對於同時使用多個通訊軟體的團隊，單一實例接入全部渠道確實省事。排程與推播能力也讓它能夠充當內部資訊彙整的角色，例如每日摘要或報告分發。

對個人使用者而言，價值主要在記憶與檔案工作區。代理可以直接讀寫專案檔案、比對差異、預覽文件，這種貼近檔案系統的操作方式與純聊天介面的體驗差別明顯。

QwenPaw 現階段有什麼限制？

限制包括版本仍處測試階段、未結問題超過一千一百個、Windows 企業環境可能安裝失敗、桌面應用未經簽名，以及安裝體積偏大。

專案本身的體量是另一項成本。README 坦承安裝腳本會一併安裝 Node.js 與前端資源，路線圖也把精簡程式庫列為進行中的項目，說明維護者清楚意識到這個負擔。

安全機制預設值同樣需要留意。工具守衛提供四段審批等級，若為了順手而長期設為自動放行，五層防護的實際效果會大幅衰減。這類系統的風險往往不在機制缺失，而在設定被逐步放寬。

常見問題有哪些？

以下四題處理最常見的疑問，包括是否必須使用阿里雲服務、本地模型的能力落差、記憶資料存放位置，以及與既有助理工具的共存方式。

使用 QwenPaw 是否必須依賴阿里雲服務？

不需要。專案採 Apache 2.0 授權，可完全在本機執行。阿里雲僅是其中一條部署路徑，使用者亦可選擇 Ollama、LM Studio 或其他雲端供應商。

本地模型與雲端模型的能力差距有多大？

官方未公布第三方基準對照。QwenPaw-Flash 系列宣稱針對代理任務訓練，2B 與 4B 版本適合輕量問答與檔案操作，複雜推理仍建議使用雲端模型。

記憶資料實際存放在哪裡？

存放於工作目錄，Docker 部署時位於資料磁碟區，模型供應商設定與 API 金鑰則另存於密鑰磁碟區。備份需要同時涵蓋這兩個位置。

可以與現有的助理工具同時使用嗎？

可以。專案支援 MCP 接入外部工具，並提供 Agent Communication Protocol 與其他系統交換任務，兩套系統可各自保留原有流程。

總結：QwenPaw 值得一試嗎？

值得一試，特別是重視資料留在本機、又需要多個通訊軟體入口的使用者。它的價值在整合度與安全分層，代價是安裝體積偏大、設定項偏多，且專案仍在快速變動。

這個專案真正值得記錄的地方，在於它把代理產品的幾個難題放在同一個屋簷下處理。記憶要有結構、模型要能落地、權限要能分級、渠道要能覆蓋，這些需求通常分散在不同工具裡。

從三萬七千顆星與八個月的開發節奏來看，市場對這種整合型方案確有需求。是否適合長期使用，取決於使用者願意花多少時間在設定與調校，而不是取決於功能清單的長度。
