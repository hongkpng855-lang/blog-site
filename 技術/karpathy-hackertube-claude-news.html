Karpathy 兩小時重造 YouTube：HackerTube 上線

2026年11月03日 00:00 • 閱讀時間 2 分鐘 • Eric Chan • 來源：Karpathy Blog

Andrej Karpathy 於二零二六年十月三十一日公開 HackerTube，把 Hacker News 討論中被反覆推薦的影片整理成瀏覽介面。全站收錄六千四百五十四條影片，分屬一百五十個主題，由 Claude Code 配合 Opus 5.5 建置，約兩小時完成。網站不設帳號，也沒有伺服器端推薦模型。

HackerTube 是什麼？

HackerTube 以 Hacker News 推薦紀錄為資料源，收錄六千四百五十四條影片、一百五十個主題，介面仿照 YouTube，不設帳號。

專案的自我描述只有一句：Hacker News 一直互相推薦觀看的那些 YouTube 影片。定位上它不是新的影音平台，而是一層建立在既有平台之上的策展介面。影片仍然存放在 YouTube，HackerTube 只負責挑選、分類與呈現。

這個分野相當關鍵。它沒有重新打造串流基礎設施，也沒有處理版權授權，因此整個系統的複雜度被壓到極低。專案能否成立，幾乎完全取決於來源社群的品味，以及資料清理是否徹底。

Karpathy 為什麼要自己做一個 YouTube？

他在文章開頭描述某個週五深夜打開 YouTube，看到的盡是誇張縮圖與重複題材，認為推薦結果不適合自己，於是在週六把工作交給 Claude，直接做一個替代介面。

文章原話提到，那種內容對網路中位數使用者或許有效，但對他無效。這個判斷沒有數據支撐，也沒有做使用者研究，屬於相當直白的個人偏好陳述。有趣的是他隨後採取的行動：不是抱怨，而是花一個上午把介面做出來。

這種規模的專案在兩年前需要一個小團隊與數週工時。如今同一個人用一個週末的上午就能完成，落差本身就是這則新聞值得記錄的原因。

這個專案在兩小時內如何完成？

流程分三段：抓取並過濾 Hacker News 全部留言，用 Sonnet 篩走廣告與雜訊，再把四萬條推薦留言對應到影片，最後套上介面部署到 VPS。

依據作者補充，他使用的工具是 macOS 桌面版 Claude Code，預設模型為 Opus 5.5、推理強度設為中等。實際操作上他只負責三件事：在 Google Cloud 主控台申請查詢影片中介資料的 API 金鑰、開一台 VPS、購買網域。

其餘工作全部以對話完成，包括部署、加固、效能調校與程式碼整理。他在文中明言自己已經不做傳統意義上的工程工作，不再手寫程式、不再於終端機執行指令，只與模型對話並讓它完成全部步驟。

資料來源與內容品質如何篩選？

資料源為 Hacker News 由二零零七年起的公開留言，經模型過濾後留下四萬條明確推薦某條影片的留言，去重與去除推廣內容後，對應出六千四百五十四條影片。

這個數量比例值得注意。四萬條留言最終只對應六千多條影片，代表同一條影片往往被多人重複推薦，重複本身就是一種投票訊號。專案沒有採用按讚數或觀看數排序，而是以社群提及的次數與分布作為品質代理指標。

題材分布也反映社群口味。分類頁顯示，喜劇、音樂與影視相關條目合計一千七百三十一條，其中諷刺與惡搞佔三百六十二條，紀錄片與敘事類二百三十九條。技術演講與冷門工具的長片則集中在另一個分類，這正是主流演算法最難推送的內容類型。

沒有帳號的推薦系統如何運作？

網站不設登入，個人化推薦與觀看紀錄全部存放於瀏覽器本機工作階段。使用者開啟無痕視窗或更換裝置，狀態即重新開始，平台端不保留任何行為資料。

這個設計選擇同時解決了兩件事。第一是隱私，網站營運者無從取得使用者行為，也就無從建立畫像或轉售資料。第二是維運成本，沒有帳號資料庫、沒有 session 伺服器、沒有推薦模型推論費用，一台小型 VPS 足以支撐。

代價是推薦品質無法跨裝置累積。使用者換一台電腦，系統就當作初次到訪。對於把這個站當成偶爾挖寶工具的人而言，這個代價可以接受；對於期待長期個人化的人而言，體驗會明顯不足。

與 YouTube 推薦相比有什麼差別？

差別在策展主體。YouTube 由模型依觀看行為排序，HackerTube 由社群十多年的留言紀錄決定，前者追求觀看時長，後者只反映一群人願意具名推薦什麼。

介面還有一個細節值得說明。專案刻意不採用上傳者自選的縮圖，改抓影片中途的畫面作為預覽。這個做法降低了誇張縮圖的影響，也讓點擊決定更依賴標題與頻道名稱。

推薦邏輯因此變得可以被檢視。任何一條影片出現在首頁，背後都能追溯到具體的討論串；相對地，平台演算法的排序依據通常不對外公開，使用者只能從結果反推規則。

開發者可以從中學到什麼？

可複製的做法有三項：以既有社群資料取代自建推薦模型、把個人化狀態留在使用者端、以及把網站資料開放匯出，讓其他人接手改造成自己的版本。

資料匯出是整個專案最容易被忽略的設計。作者明確表示網站資料可以整份下載，交給自己的代理工具，就能長出一個完全不同版本的介面。這種開放態度讓專案的價值不限於單一網站，而是一份可重複使用的策展資料集。

對內容工作者而言，這個案例也提示了一條路徑。與其等待平台分發，不如找到一個有共同標準的社群，讓內容透過人際網絡流通，再由社群紀錄形成長期可見的推薦軌跡。

現階段有什麼限制？

限制包括：內容只覆蓋 Hacker News 社群關注的題材、影片中介資料依賴 YouTube API 配額、以及專案由單人維護，功能與穩定性都沒有服務承諾。

還有一個結構性的問題。專案的推薦品質完全取決於來源社群的組成，社群若逐漸單一化，策展結果也會跟著偏斜。這種偏斜不像演算法那樣可以透過調整參數修正，只能靠引入新的來源社群稀釋。

此外，所有影片仍由 YouTube 托管。一旦某條影片下架、轉為私人或地區封鎖，HackerTube 端只會留下失效的連結，這也是策展層依附於平台時無法回避的風險。

常見問題有哪些？

以下四題處理最常見的疑問，包括是否需要註冊、影片來源是否合法、內容更新頻率，以及一般使用者是否值得長期使用這個站。

使用 HackerTube 需要註冊帳號嗎？

不需要。網站沒有帳號系統，觀看紀錄與偏好設定存放在瀏覽器本機，清除瀏覽資料或更換裝置後即重新開始。

影片內容是否涉及版權問題？

影片本體仍由 YouTube 托管與播放，HackerTube 只提供連結與分類，並未重新上傳或重新編碼任何內容，因此不涉及額外的重製行為。

片庫會持續更新嗎？

目前依賴一次性抓取的留言資料集，作者未承諾固定更新頻率。若要長期使用，需自行以匯出資料重建，或等待後續維護。

一般使用者值得長期使用嗎？

適合當作偶爾挖寶的入口，特別是技術演講與冷門紀錄片。若期待貼合個人偏好的推薦流，現階段的無帳號設計無法滿足。

總結：值得試用嗎？

值得試用，尤其是想找技術演講與冷門紀錄片的人。它的價值不在取代 YouTube，而在示範推薦層可以被拆開、被社群接管，並且維持極低維運成本。

這個專案真正的訊息，不在六小時的影片量，也不在兩小時的建置時間，而在它證明了一件事：推薦可以是一個獨立、可替換的元件。平台把策展權握在手中，並不代表那是唯一可行的安排。

對開發者而言，這是一個成本極低、可完整複製的樣板。對內容經營者而言，這是一個提醒：當分發管道不透明時，把社群關係與紀錄留在可掌握的地方，比追逐演算法更實際。
