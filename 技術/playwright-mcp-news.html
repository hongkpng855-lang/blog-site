Playwright MCP 開源：72 個工具操控瀏覽器

2026年11月13日 08:00 • 閱讀時間 4 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/microsoft/playwright-mcp

Playwright MCP 是微軟開源的瀏覽器自動化伺服器，GitHub 累積 39,552 顆星標。它把 Playwright 的控制能力包裝成 72 個 MCP 工具，讓代理以無障礙樹快照讀取頁面並執行點擊輸入，全程無需視覺模型與截圖比對。

Playwright MCP 是微軟開源的 MCP 伺服器，39,552 星標，把 Playwright 包裝成 72 個工具，以無障礙樹取代截圖。

Playwright MCP 是什麼？

項目由微軟於 2025 年 3 月建立，採 Apache 2.0 授權，主要語言 TypeScript，為語言模型提供瀏覽器自動化能力。

此項目建立於 2025 年 3 月 21 日，是微軟在 Playwright 生態上另設的獨立倉庫。它並不重複實作瀏覽器引擎，而是把上游框架的能力整理成語言模型可呼叫的工具介面。

定位上，它介於「測試框架」與「通用代理工具」之間。開發者用同一套伺服器，既可讓代理執行端對端測試的探索步驟，也可讓代理代替人手完成填表、截圖與資料抓取。授權為 Apache 2.0，程式碼以 TypeScript 撰寫，主要透過 npm 套件 @playwright/mcp 發佈。

Playwright MCP 與 Playwright CLI 有何差別？

微軟指出高頻編碼代理宜用 CLI 加技能檔以節省上下文；MCP 則適合需要持續瀏覽器狀態、頁面內省與反覆推理的長時間流程。

這是少見的官方自我比較。README 直言，現代編碼代理正趨向 CLI 加技能檔的工作方式，原因是每次 CLI 呼叫只需載入精簡指令，不必把大量工具結構與冗長的無障礙樹塞進模型上下文。

MCP 的價值落在另一類場景。當流程需要保留持續的瀏覽器狀態、對頁面結構反覆內省，或進行自我修復測試與長時間自主操作，維持一條連續的瀏覽器連線，往往比節省詞元更重要。微軟同時維護 playwright-cli 倉庫，該項目目前有 15,142 顆星標，最新版本 v0.1.24 於 2026 年 11 月 10 日發佈。

這種雙軌安排說明一件事：協定本身不是效率的萬靈丹。工具數目與上下文成本之間，團隊需要按代理的工作型態自行取捨。

Playwright MCP 提供哪些工具？

README 列出 72 個 browser_ 工具，涵蓋導航、點擊、表單、頁籤、網路攔截、儲存空間、追蹤錄影與 PDF 輸出。

工具清單按能力分層。基礎層是 browser_navigate、browser_click、browser_type、browser_fill_form 與 browser_snapshot，構成代理與頁面互動的最小集合。管理層包括 browser_tabs、browser_resize、browser_handle_dialog 與 browser_file_upload，處理多頁籤與系統對話框。

狀態與網路層覆蓋較深。代理可透過 browser_cookie_*、browser_localstorage_* 與 browser_sessionstorage_* 讀寫儲存空間，亦可用 browser_route、browser_network_requests 攔截或檢視請求。診斷層則有 browser_start_tracing、browser_start_video 與 browser_console_messages。

部分工具需要額外能力旗標才會出現。加上 --caps=vision 後可使用 browser_mouse_click_xy 等座標操作，--caps=pdf 提供 browser_pdf_save，--caps=devtools 則開啟開發者工具相關入口。這種按需展開的設計，令預設工具表不會一次過膨脹。

Playwright MCP 的無障礙樹快照如何運作？

伺服器把頁面轉換為結構化的無障礙樹，以角色、名稱與狀態描述每個元素，代理據此選取目標。這種做法不依賴像素比對，動作可重現，也不需要載入視覺模型。

傳統電腦操作代理多數依賴截圖，再讓視覺模型判斷座標。這種方式的弱點是解析度敏感、字型差異會造成誤判，而且同一頁面在不同縮放比例下的結果並不一致。

無障礙樹路線把頁面壓縮成角色與名稱的組合，例如按鈕、文字框與表格標題。代理看到的是「名為 City 的文字輸入框」，而非某個座標上的矩形，因此動作具備確定性，頁面改版後亦較容易維持。

設定層面亦有對應控制。--snapshot-mode 可設為 full 或 none 以調整回應內容，--snapshot-boxes 會附上每個元素的邊界框，locateOnlyVisible 選項則把定位限制在可見元素，避免選中隱藏的重複節點。

Playwright MCP 如何處理登入狀態與多客戶端並行？

伺服器預設使用持久化設定檔，路徑按工作區雜湊分開存放，登入狀態可跨工作階段保留。同一個設定檔同時只容許一個瀏覽器實例，要多客戶端並行須改用隔離模式或獨立目錄。

持久化設定檔是預設行為。在 Linux 上，資料存放於 ~/.cache/ms-playwright/mcp-{channel}-{workspace-hash}，其中雜湊值取自客戶端的工作區根目錄，因此不同專案會自動分開，不會互相污染登入狀態。

限制同樣明確。README 指出，一個持久化設定檔同時只能被一個瀏覽器實例使用，同一工作區的多個客戶端會互相衝突。並行需求須以 --isolated 啟動，或為每個客戶端指定不同的 --user-data-dir。

第三條路線是連接既有瀏覽器。--extension 模式透過 Chrome 擴充功能接管已登入的頁籤，適合需要沿用真實帳號的流程。v0.0.85 加入 --background 與 --no-tab-group，令被接管的頁籤不再搶走焦點，也不會被強制搬入專屬頁籤群組。

Playwright MCP 有哪些安全風險需要留意？

微軟明言此伺服器不是安全邊界。它預設限制檔案存取於工作區並封鎖 file:// 導航，隔離須靠外層容器。

預設防護集中在檔案層。伺服器只允許存取工作區根目錄，並阻止導航至 file:// 網址，除非開發者主動加上 --allow-unrestricted-file-access。這項預設值可阻擋代理讀取系統敏感檔案。

網路層的設定需要正確理解。--allowed-origins 與 --blocked-origins 控制瀏覽器可請求的來源，但文件明確標注它們不是安全邊界，也不會影響重新導向。真正需要隔離時，--allowed-hosts 限制伺服器綁定的主機，配合容器化執行較為穩妥。

其他可用控制包括以 --secrets 載入 dotenv 格式的憑證檔，以及用 --redact-url-params 把網址中的權杖參數遮蔽。Docker 映像 mcr.microsoft.com/playwright/mcp 目前只支援無頭 Chromium，適合放進受限網路環境。

版本節奏偏向密集修正而非大型功能。v0.0.85 的亮點集中在連線體驗：背景連線、頁籤群組控制、只匹配可見元素的定位選項，以及快照中保留容器與表格標題的名稱。

修正項目同樣貼近實務。browser_snapshot 回退了上一版對 inert 與模態內容的可見性過濾，browser_evaluate 改為以可讀形式回傳 BigInt、NaN 等非 JSON 值，設定檔內的相對路徑亦改為按檔案所在目錄解析。這些都是代理長時間運行時才會浮現的細節問題。

如何開始使用 Playwright MCP？

在客戶端 mcpServers 加入指令 npx @playwright/mcp@latest，需 Node.js 18 以上，重啟後即見工具。

標準設定在多數客戶端通用。在 mcpServers 之下加入名為 playwright 的條目，指令填 npx，參數填 @playwright/mcp@latest，即可完成註冊。VS Code、Cursor、Windsurf、Claude Desktop、Goose、Grok、Junie、Kiro、LM Studio 與 opencode 都沿用同一段結構。

命令列工具另有更快路徑。Codex 可直接執行 codex mcp add playwright npx "@playwright/mcp@latest"，設定會寫入 ~/.codex/config.toml；Copilot CLI 於互動模式輸入 /mcp add 後按指示操作。

需要長期服務時可改用 Docker 或獨立程序。映像啟動後在 8931 埠提供 SSE 傳輸，任何 MCP 客戶端都可連上。首次執行需下載瀏覽器二進位檔，之後啟動只需數秒。

Playwright MCP 與其他瀏覽器代理方案相比如何？

與截圖式代理相比，它以結構化資料換取穩定度與詞元效率，代價是難以處理畫布與純圖形介面，精確度亦受解析度限制。

截圖式方案的優勢在於通用性。任何看得見的介面都能操作，包括遊戲、遠端桌面與 canvas 繪製的圖表。Playwright MCP 在這些場景需要退回座標點擊，精確度取決於解析度，穩定性不及結構化定位。

自建腳本的優勢在於可預期。每一步都是程式碼，錯誤可重現，執行成本極低。MCP 路線把決策交給模型，換來面對未知頁面時的適應力，代價是每次呼叫都帶著推理成本與不確定性。

實務上三者並非互斥。常見組合是以 Playwright 腳本處理穩定流程，把探索與修復步驟交給代理，並在代理工作時以追蹤檔記錄每一步，事後轉為固定腳本。這種分工把模型成本集中在真正需要判斷的環節。

出處連結有哪些？

原始碼位於 GitHub 的 microsoft/playwright-mcp，npm 套件為 @playwright/mcp，Docker 映像由微軟發佈。

倉庫網址為 https://github.com/microsoft/playwright-mcp ，README 內含完整工具清單、各客戶端設定範例與安全章節。上游框架文件位於 https://playwright.dev ，MCP 協定規格則可於 modelcontextprotocol.io 查閱。若只需要命令列工作流，可參考 https://github.com/microsoft/playwright-cli 。

Playwright MCP 常見問題有哪些？

常見疑問集中在視覺模型需求、無頭運行、瀏覽器選擇、本機檔案存取範圍、彈出視窗處理與追蹤檔用途，以下逐項以問答形式回答，並附上官方建議的設定方式。

Playwright MCP 需要視覺模型嗎？

不需要。伺服器以無障礙樹描述頁面，代理只讀結構化文字。只有在 --caps=vision 開啟座標操作，或需要判讀截圖內容時，才涉及視覺能力。

Playwright MCP 可以在無頭環境運行嗎？

可以。加上 --headless 即以無頭模式啟動，並可配合 --idle-timeout 設定閒置多久後關閉瀏覽器，適合伺服器與容器部署。

Playwright MCP 支援哪些瀏覽器？

透過 --browser 可選 chrome、firefox、webkit 或 msedge。預設使用 Chrome for Testing 版本，確保跨機器行為一致。

Playwright MCP 會不會讀取本機檔案？

預設只允許工作區根目錄，並封鎖 file:// 導航。放寬須明確加上 --allow-unrestricted-file-access，不建議在不受信任的環境開啟。

Playwright MCP 如何處理彈出視窗與對話框？

browser_handle_dialog 可接受或拒絕 alert、confirm 與 prompt，browser_tabs 則負責切換與關閉頁籤，避免代理在彈窗出現後卡住。

Playwright MCP 的追蹤檔有什麼用途？

browser_start_tracing 會記錄 DOM 快照、網路請求與操作序列，失敗時可用 Trace Viewer 逐步重播，是把代理行為轉為可除錯證據的主要手段。

Playwright MCP 適合用在生產環境嗎？

適合以容器隔離的方式部署，但不應當作安全邊界。README 明言伺服器本身不提供防護，憑證管理、網路限制與權限回收都需由外層機制負責。

Playwright MCP 與 Playwright 測試框架會衝突嗎？

不會。兩者共用同一套瀏覽器二進位檔與定位模型，可以在同一個專案並存，測試套件與代理工作流各自獨立運行。

總結：Playwright MCP 適合什麼團隊？

適合已用 Playwright 或正建立代理工作流的團隊，尤其是需要穩定頁面讀取與可重播證據的長時間流程。

Playwright MCP 的價值不在工具數量，而在於把不穩定的像素世界轉換為可列舉的結構。72 個工具構成一個完整介面，讓代理能在同一個連線內完成導航、操作、驗證與錄影。

限制同樣清楚。它不是安全邊界，不擅長畫布類介面，工具表本身也佔用上下文。微軟在 README 主動指出 CLI 路線的詞元優勢，這種坦白反而提升了可信度。

對於正在評估代理落地方式的團隊，合理的做法是先以 CLI 處理已知流程，把 MCP 留給需要持續狀態與反覆推理的長流程。兩者共用同一套引擎，切換成本極低。同類的瀏覽器操作路線可對照 Browser Use 1.0 重寫後的取捨，而把工具以 MCP 形式暴露的做法，另可參考 Strapi MCP 伺服器的接口設計。
