Dokploy 3.8 萬星：自架 PaaS 取代 Vercel

2026年11月06日 16:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/Dokploy/dokploy

Dokploy 是一個可以自行架設的平台即服務工具，在 GitHub 累積三萬八千二百六十九顆星標，定位為 Vercel、Netlify 與 Heroku 的開源替代方案。十一月五日發布的 v0.31.0 合併一百三十三項改動，帶入服務跨伺服器遷移與日誌外送能力，讓自架部署流程更貼近商業平台的完整度。

Dokploy 是什麼？

Dokploy 是可自架的平台即服務系統，以 Docker 與 Traefik 為基礎，把應用程式、資料庫與備份集中到單一面板管理，核心採 Apache 2.0 授權。

專案由 Dokploy Technology 維護，二零二四年四月建立，以 TypeScript 撰寫，程式碼量約六百八十萬位元組。它把部署工作中最繁瑣的三件事收進同一個介面：容器編排、網域路由與資料庫生命週期。

定位相當明確。Vercel 與 Netlify 把重點放在前端框架的一鍵部署，Heroku 以應用執行環境為核心，Dokploy 則把伺服器層級的權限交回使用者，包含 Docker 常駐程式、防火牆埠位與憑證簽發。

這種取捨換來的是成本結構改變。使用者負擔的是 VPS 租金與維運時間，平台訂閱費與用量計價不再出現在帳單上。

Dokploy 與 Vercel、Heroku 的差異在哪裡？

商業平台代管伺服器與憑證，Dokploy 把兩者交回使用者，代價是自行處理系統更新與備份還原。功能對等，責任邊界不同，適合已有維運能力或需要資料留境的團隊。

差異落在責任邊界。商業平台承擔底層主機、憑證更新與可用性，使用者只需推送程式碼；Dokploy 把這層責任交回團隊，換取完全的控制權與可預期的固定成本。

對資料留境有要求的場景，這個差別具有實質意義。所有容器、資料庫檔案與備份目的地都在自己手上的機器，稽核時不需要向第三方索取證明。

維運成本需要誠實評估。系統更新、憑證到期、磁碟容量與備份還原演練，這些工作原本由平台吸收，自架之後必須有人負責，否則一次磁碟寫滿就足以讓整個環境停擺。

部署流程如何運作？

安裝腳本在 VPS 配置 Docker 與 Traefik，面板連接 Git 倉庫或 Compose 檔。推送程式碼觸發建置，Traefik 依網域轉發並自動申請憑證。

官方提供的安裝方式是單行指令。腳本在目標主機準備 Docker 環境、拉取面板映像並啟動 Traefik 反向代理，完成後以瀏覽器開啟面板即可操作。

應用來源支援多種形式。除了直接指向 Git 倉庫，也可以貼上 Docker Compose 檔，或用預先建置的映像部署；語言支援涵蓋 Node.js、PHP、Python、Go、Ruby 等常見執行環境。

版本更新讓流程更順。v0.31.0 加入部署時自動拉取最新映像的開關、可轉移的服務設定，以及把 compose 檔中的 YAML 合併鍵正確展開的修正，減少手動改檔的機會。

資料庫與備份功能涵蓋哪些範圍？

面板可一鍵建立 MySQL、PostgreSQL、MongoDB 等六種資料庫，備份排程送至外部儲存。v0.31.0 加入備份檔下載與自訂檔名，並在日誌遮蔽 S3 憑證。

資料庫以容器形式建立，規格與版本在面板選擇。對於中小型專案，這種做法省去另外維護資料庫主機的成本，備份與還原也能與應用程式共用同一套排程。

備份支援外部儲存目的地。v0.31.0 新增備份檔下載功能與自訂檔名選項，並修正了 S3 憑證在備份日誌中以不同引號形式外洩的問題。

刪除行為亦有收緊。Compose 服務刪除時，磁碟區預設保留而不一併清除，同時把「全新磁碟區」選項移入需輸入確認的危險區域，降低誤刪資料的機會。

多節點與多伺服器架構如何運作？

多節點以 Docker Swarm 組成叢集，服務可分散到多台主機，遠端伺服器可獨立納管。v0.31.0 支援服務跨伺服器轉移。

擴展方式沿用 Docker 原生機制。面板把多台主機組成 Swarm 叢集，服務可設定副本數並分散到不同節點，Traefik 在叢集中負責流量入口。

遠端主機同樣可以納管。團隊可保留一台控制面板，把應用部署到其他 VPS 或內部機器，適合把資料庫與前端分開放置的架構。

v0.31.0 的服務轉移功能補上一塊缺口。以往把服務搬到另一台主機需要重建設定，現在可直接轉移，對於更換供應商或調整區域時相當實用。

v0.31.0 修補了哪些安全問題？

該版本處理六個高危依賴告警，把 Next.js 升至 16.3.4、Node.js 升至 24.22.1，並改以標準輸入傳遞倉庫密碼，停止經錯誤物件洩漏密鑰。

修補集中在依賴鏈。Next.js 16.3.4 對應的遠端程式碼執行公告、Node.js 24.22.1 的安全更新，以及多筆 Dependabot 高危告警，都在同一個版本一併處理。

憑證處理方式有明顯改動。映像倉庫密碼改由標準輸入傳入 docker login，避免出現在程序參數或日誌中；執行錯誤物件不再夾帶密鑰內容，容器終端則綁定至所屬服務，防止跨服務存取。

Traefik 的檔案存取範圍亦有收緊。面板對 Traefik 設定檔的讀寫被限制在指定目錄內，路由設定錯誤不再有機會波及其他路徑。

監控與日誌可以接到哪些外部平台？

容器日誌與主機指標可經 Vector 外送到 Grafana、Datadog、Elasticsearch 與 CloudWatch，並依專案與環境標籤分類。

內建監控涵蓋即時用量。面板顯示每個資源的處理器、記憶體、儲存與網路讀數，足夠日常排查，但歷史資料的保存期限有限。

外送能力是這次版本的重點。透過 Vector 代理，日誌與指標可以送到 Loki、Prometheus 或 Mimir、Datadog、New Relic、InfluxDB、VictoriaMetrics、Better Stack、Elasticsearch 與 OpenSearch、Splunk 以及 AWS CloudWatch，並以專案、環境與應用三層標籤分類。

通知渠道同樣齊備。部署成功或失敗可推送至 Slack、Discord、Telegram 或電郵，v0.31.0 另外修正了 Telegram 通知中 HTML 未轉義與長訊息截斷的問題。

自架的硬體與安裝門檻是什麼？

需要一台可執行 Docker 的 Linux 主機，官方建議全新 VPS，記憶體至少兩 GB。安裝腳本自動配置環境，面板以瀏覽器操作，亦可改用雲端版本省去主機維護。

門檻主要在主機準備。官方文件以全新 VPS 為前提，要求 Linux 環境與 Docker 支援，安裝腳本會處理其餘設定；面板、Traefik 與資料庫容器共用同一台機器時，記憶體需求會明顯上升。

網路設定需要事先規劃。面板埠位、應用埠位與憑證簽發都依賴正確的 DNS 指向，v0.31.0 加入面板埠位切換功能，讓管理介面可以從預設埠移開以降低暴露風險。

不想自行維運的團隊有替代路徑。官方提供雲端版本，功能與自架版一致，v0.31.0 同時加入帳單週期切換與帳號刪除流程。

授權條款對商業使用有何限制？

倉庫根目錄程式碼採 Apache 2.0，可自由商用與修改；proprietary 目錄下的企業功能另有專屬條款，使用前宜先確認落在哪一類。

授權結構屬於混合模式。LICENSE 檔明言，位於 proprietary 目錄下的內容依 LICENSE_PROPRIETARY 授權，目錄以外的程式碼則為 Apache 2.0，GitHub 介面因此顯示為 Other。

對多數自架使用者，實際適用的是 Apache 2.0 部分。商用部署、修改原始碼與內部散布都不需要額外授權，也不需要公開衍生作品。

企業功能需要個別確認。單一登入、自訂品牌與角色權限等模組若落在 proprietary 目錄，使用條款會與 Apache 2.0 不同，採購前宜先閱讀對應授權檔。

Dokploy 的專案數據與社群規模如何？

專案現有三萬八千二百六十九顆星標、三千一百五十六個分支、四百一十九位貢獻者，主要語言為 TypeScript，二零二四年四月建立，近七日提交五十三次。

成長曲線相當陡峭。專案在兩年半內累積近三萬八千顆星標，四百一十九位貢獻者對照七十六個月的專案年齡，說明外部參與比例不低。

議題壓力同時存在。未結議題七百六十三項包含拉取請求，對照近七日五十三次提交與十五項合併請求，維護節奏穩定但排隊情況明顯。

版本節奏偏密。v0.30 系列在九月至十月間推出七個修訂版，v0.31.0 相隔約兩週，內容以穩定性與安全修補為主。

出處連結有哪些？

原始碼與版本紀錄集中於 GitHub 的 Dokploy 組織，官方網站提供安裝腳本與文件，雲端版本可另行申請。三處連結均已列於文末參考來源。

總結：Dokploy 適合什麼團隊？

已有基本 Linux 維運能力、需要把資料與部署流程留在自有主機的團隊最合適。若團隊沒有專人處理系統更新與備份演練，託管平台的成本反而更低。

核心價值在責任與成本的可預期性。固定伺服器租金取代用量計價，資料位置明確，功能覆蓋從部署、資料庫、備份到監控的完整鏈路。

主要限制是維運負擔。系統更新、憑證到期與磁碟容量都需要有人負責，這些工作在託管平台上由供應商吸收，自架後成為團隊的日常事項。

對於已經在用 Docker 的小型團隊，遷移成本相對可控。較務實的做法是先在一台測試 VPS 部署單一應用，驗證憑證簽發與備份還原流程，確認維運節奏可以承受後，再逐步把正式服務搬過去。
