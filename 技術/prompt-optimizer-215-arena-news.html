Prompt Optimizer 2.15：Arena 多模型對比

2026年11月15日 20:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/linshenkx/prompt-optimizer

Prompt Optimizer 於 2026 年 11 月連續推出 2.15.0、2.15.1 與 2.15.2 三個版本，把提示詞優化工具從單次改寫推進到多模型並行對比。專案以 TypeScript 撰寫，累積 41,535 顆星標與 4,663 個分叉，依 AGPL-3.0 釋出。

核心變化是 Arena。過去使用者按一次優化、看一份結果，判斷好壞全憑閱讀；2.15.0 之後，同一段輸入可以開出多條測試欄，每欄各自指定連線與模型，一次跑完再並排比較。這個改動把提示詞工程從「寫得好」推向「量得出來」。

Prompt Optimizer 是開源提示詞優化工具，2025 年 2 月建立，採 TypeScript 撰寫並依 AGPL-3.0 釋出，現累積 41,535 顆星標。

Prompt Optimizer 是什麼？

此項目把提示詞的撰寫、優化、測試、評估與收藏收進同一介面，定位為提示詞資產管理工作台。專案於 2025 年 2 月 12 日建立，以 TypeScript 撰寫。

專案於 2025 年 2 月 12 日建立於 GitHub，作者為 linshenkx。它的自我定位相當明確：提示詞可以手寫、可以由範本開始、可以從本機檔案匯入，也可以取自官方的 Prompt Garden 目錄；這些來源進入工具之後，會經過優化、測試、評估，最後存成可重用的資產。README 把整條鏈路寫成一句話，提示詞在這裡被優化、被測試、被評估，然後被保存。

GitHub 上的十個標籤指向同一件事：ai-prompts、prompt-engineering、prompt-optimization、prompt-testing、prompt-toolkit、prompt-tuning。這種標籤組合說明項目想做的是工具鏈，單點功能並非重點。

授權條款值得先看清。專案採 GNU AGPL-3.0，README 用一段淺白說明解釋含義：個人使用、研究、企業內部使用與商業專案修改都不受限制，但若把改動後的版本做成網站或對外服務，就必須公開原始碼。對打算把此工具整合進商業產品的團隊，這一點會直接影響架構決策。

Arena 模式解決了什麼問題？

Arena 讓同一段提示詞與參考圖同時送往多條測試欄，各欄自行選擇連線與模型，支援單欄或批次執行，並沿用既有的工作階段還原機制保存輸入、模型選擇與先前結果。

2.15.0 的發佈說明用「一個輸入、多個模型」概括這次改動。使用者在 Arena 輸入一次提示詞，需要時附上參考圖，然後為每條測試欄選擇連線與模型，可以全部一起執行，也可以逐欄單獨測試。輸出沿用既有的預覽、原始碼、複製、推理過程顯示與全螢幕控制。

版面的處理方式帶有取捨。桌面版讓各欄平均分配可用寬度，手機版固定顯示兩欄，其餘欄位改為橫向捲動。這個設計承認了小螢幕的物理限制，寧可保留兩欄可視對比，也不把欄位壓成難以閱讀的窄條。

工作階段還原同樣延伸到 Arena。輸入內容、模型選擇與先前結果都會被保存，切換工作區再回來時仍在原位。2.15.1 進一步把 Prompt Garden 的評估類提示詞直接接入 Arena，匯入時可帶入範例變數與參考圖，且不會自動觸發模型請求。

這個功能解決的是判斷問題。提示詞的改動往往只差幾個字，單看一份輸出無法分辨是提示詞變好，還是模型這次答得剛好。並排跑多次、換模型再跑，才有比較基礎。同類思路也出現在代理技能的自動優化上，SkillOpt 以評估回圈迭代技能內容，兩者都把「哪個版本更好」交給可記錄的比較。

提示詞優化在技術上如何運作？

系統以多輪迭代方式改寫提示詞，區分系統提示與使用者提示兩條路徑，並提供分析、單結果評估與多結果比較三種評量方式，讓使用者判斷改寫是否真的帶來改善。

README 對機制的描述集中在兩點：一鍵優化與多輪迭代。工具會把原始提示詞送往使用者自選的模型，取回改寫版本，必要時再迭代。系統提示與使用者提示分成兩條路徑處理，因為兩者的約束條件不同，前者管角色與邊界，後者管具體任務。

評估環節是這套流程的核心。除了分析與單結果評估，2.15 系列強調多結果比較評估，讓同一段提示詞在不同模型下的表現可以對照。這種設計把「哪個版本更好」從主觀感受變成可記錄的判斷。

進階測試模式另外提供三件事：上下文變數管理、多輪對話測試與 Function Calling 支援。變數可以批次替換並即時預覽，多輪測試模擬真實對話的推進，工具呼叫則對接 OpenAI 與 Gemini 兩家的介面。這三項功能讓提示詞的驗證得以覆蓋比單輪問答更接近實務的情境。

多模型接入與隱私架構如何設計？

網頁版為純前端應用，資料留於瀏覽器，請求直接送往使用者配置的供應商，不經中間伺服器。代價是受跨來源政策限制，連本地模型須改用桌面版或 Docker。

隱私設計是這個專案最值得注意的一段。README 明言網頁版為純客戶端處理，應用資料存在瀏覽器，模型請求由瀏覽器直接送往供應商，不經過任何中間伺服器。這種架構意味著提示詞與輸出不會被專案方記錄，對處理內部文件的團隊是實際優勢。

代價出現在連線層。純前端應用受瀏覽器同源政策約束，若供應商未開放跨來源資源共享，請求會被攔截。專案對此給出三條路徑：桌面版作為原生應用不受此限，可直接連本地 Ollama 或政策嚴格的商業 API；自架代理服務居中轉發；或改用 Docker 部署，讓應用與本地模型同處 HTTP 協定。

另一個常見障礙是混合內容政策。HTTPS 的線上版本無法向 HTTP 的本機 Ollama 發出請求，這是瀏覽器的安全規則，與專案實作無關。官方文件建議改用 http://localhost:8081 的 Docker 部署，或使用桌面版與擴充功能。

已接供應商涵蓋 OpenAI、Gemini、DeepSeek、Grok、智譜、SiliconFlow 與 MiniMax，另可自訂 OpenAI 相容介面。每個模型可獨立設定 llmParams，以鍵值對形式傳遞溫度、輸出上限與逾時等參數。README 同時提醒，公開前端部署不應預先寫入 VITE_ 開頭的金鑰，因為這些值會被包進瀏覽器資產。若希望在多家供應商之間做統一調度，把多家免費模型併成單一介面的方案可作另一個層級的對照。

星標與分叉的比例值得留意。四萬一千餘顆星標對四千六百餘個分叉，約為九比一，屬於圍觀多於實際分叉的比例。這種分佈在提示詞類工具相當常見，因為多數使用者傾向直接使用線上版本，未必需要取走原始碼。

貢獻者數量偏少同樣說明維護結構。三十三位貢獻者支撐四萬餘顆星標的專案，意味著核心維護集中於少數人。專案另提供 Docker 映像與 Vercel、Cloudflare Pages 一鍵部署入口，降低了使用門檻，也讓議題壓力集中回原始倉庫。

版本節奏呈現明顯的兩段。11 月 3 日同日發佈 2.15.0 與 2.15.1，前者帶來 Arena，後者修正介面排版與預覽錯誤；11 月 9 日再補 2.15.2。三版集中在七日內，屬於大功能落地後密集收尾的模式。

2.15.2 修復了哪些問題？

2.15.2 恢復流式輸出自動換行與單獨停止控制，修正長回應橫向溢出，並更新兩個安全性相依套件。另有 Garden 瀏覽改善，PNG 仍為圖像預設格式。

這次修補的重點在閱讀體驗。長篇流式回應與原始碼檢視不再出現橫向溢出，使用者可以在一般工作區與全螢幕檢視中單獨停止某一條文字流，不必中斷整個工作階段。

Garden 的瀏覽能力同時補強。網頁版可以在推薦與全部提示詞之間切換，就地搜尋目錄、載入更多結果，失敗時重試；在相同工作區與語言下關閉再開彈出視窗，瀏覽位置與已載入結果都會保留。

相依套件方面，專案把 Vue I18n 固定於 11.4.14，並覆寫 Hono Node Server 至 2.1.3，包含其 MCP SDK 依賴路徑。發佈說明把這兩項列為安全性相關更新，屬於供應鏈層面的收緊。

圖像輸出的調整較細微。相容 GPT Image 2.6 的端點可以選擇 GIF 格式，幀數與延遲參數為選填，PNG 仍是預設。核心層同時保留動畫資料貫穿預覽、儲存與下載三個環節。

如何開始使用 Prompt Optimizer？

最快方式為直接開啟線上版本，於模型管理填入一組可用的文字模型金鑰。需連本地模型或政策嚴格 API 時，改用桌面安裝版或 8081 連接埠的 Docker 部署。

線上版本位址為 prompt.always200.com，應用資料存於瀏覽器，模型請求直接送往使用者配置的供應商。首次使用只需在模型管理中接入一個可用的文字模型，再依官方教學完成一次優化與複製。

自架部署有三種選擇。Vercel 提供一鍵入口，建議先分叉再匯入以便日後同步上游；Cloudflare 可透過 Workers 按鈕建立倉庫並部署，記得清空自動填入的建置指令，因為 wrangler 設定檔會自行建置前端並發佈靜態資產。Docker 則以單行指令啟動，對外連接埠預設 8081。

MCP 整合是另一條路徑。Docker 部署時 MCP 服務隨應用啟動，位於同一連接埠的 /mcp 路徑，Claude Desktop 可在服務設定檔加入對應條目。可用工具包括使用者提示優化、系統提示優化與依需求迭代三項。

桌面版另有兩個實務注意點。安裝版支援自動更新，壓縮檔版本則否；macOS 版本未經 Apple 開發者憑證簽署，首次開啟可能被系統標示為損毀或未驗證，需在終端機移除隔離屬性後方能啟動。

出處連結有哪些？

主要出處為 GitHub 倉庫 linshenkx/prompt-optimizer，版本紀錄見 Releases 頁，線上版本與文件站位於 always200.com。

原始碼與版本紀錄位於 github.com/linshenkx/prompt-optimizer，2.15.0、2.15.1、2.15.2 的完整變更清單可在 Releases 頁面查閱。線上版本為 prompt.always200.com，提示詞目錄為 garden.always200.com，文件站為 docs.always200.com。

部署文件另分為 Vercel、Cloudflare Pages 與 MCP 三份指南，放在倉庫的 docs 目錄。專案在 README 中說明部分設計靈感來自 LangGPT 在結構化提示詞方面的做法。

總結：Prompt Optimizer 適合什麼團隊？

適合反覆調整提示詞、同時使用多間模型供應商的團隊。若須把工具嵌入商業產品而不願公開改動，需先評估 AGPL-3.0 的義務。

2.15 系列的方向清楚：把提示詞從一次性輸入變成可比較、可保存、可回溯的資產。Arena 補上了最缺的一環，也就是對照組。四萬餘顆星標說明需求真實存在，三十三位貢獻者與七日三版的節奏則反映維護壓力。

採用之前值得先確認三件事。授權條款是否與商業模式相容，資料是否需要留在瀏覽器之外，以及團隊實際會用幾間供應商。對同時跑多個模型、經常比較提示詞版本的團隊，這套工具可以省下大量手工對照的時間。對一年只寫幾十條提示詞的使用者，線上版本已足夠，不必急著自架。
