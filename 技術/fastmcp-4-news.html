FastMCP 4 正式版：28k 星 MCP 框架轉向新協議

2026年10月22日 00:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/PrefectHQ/fastmcp

FastMCP 4 於 2026 年 8 月 31 日發布，是首個建構在 MCP 2026-07-28 協議修訂與 Python SDK v2 之上的版本。該框架目前擁有約 2.8 萬顆星，PyPI 單月下載超過五千萬次，官方稱約七成的 MCP 伺服器使用其某個版本。本文整理新版協議帶來的架構變化、主要功能、升級風險與近期的憑證安全更新。

FastMCP 4 是什麼？

FastMCP 4 是 Prefect 維護的 MCP 應用框架，涵蓋伺服器、客戶端與互動式應用三層，並以 MCP 2026-07-28 協議與 Python SDK v2 為基礎。

FastMCP 的定位並非單純的工具函式庫，而是一套完整的應用框架。開發者以普通的 Python 函式宣告工具，框架便自動產生結構描述、參數驗證與文件；反過來，客戶端只需提供一個 URL，傳輸協商、認證與協議生命週期都由框架處理。專案把能力分成伺服器、客戶端與應用三個支柱，應用層允許工具在對話中直接渲染互動介面，而非只能回傳純文字。

專案的歷史與官方 SDK 交纏。FastMCP 1.0 於 2024 年被併入官方的 MCP Python SDK，此後獨立專案持續演進，目前由 Prefect 團隊維護，並提供 TypeScript 版本作為對應實作。這樣的雙軌關係，使它在協議修訂時往往比官方 SDK 更早推出高階封裝。

v4 的發布節奏值得注意。從 8 月 31 日的正式版到 10 月 20 日的 v4.1.3，團隊在七週內推出多個修補版本，同時維持 3.4 系列的安全更新。這種並行維護策略，反映企業用戶對於「先修補、後升級」的實際需求。

為什麼 MCP 協議改版會影響框架設計？

因為新協議要求請求本身自足且無需連線狀態，舊框架依賴的長連線與伺服器推送模型必須改寫，才能讓任何副本在普通負載平衡器後回答請求。

2026 年 7 月 28 日，MCP 發布新的協議修訂，同日重寫的 Python SDK v2 上線。這次修訂的核心是「現代請求」的概念：每個請求自我描述、不依賴先前建立的連線狀態。對於框架而言，這意味著過去以工作階段為中心的設計必須讓位，否則部署在多副本環境時會出現請求被導向錯誤節點的問題。

舊模型還包含伺服器主動發起的取樣與 roots 能力。這類推送式設計在單機或長連線環境可行，但在無狀態的請求路徑中難以維持，因為伺服器沒有穩定的通道回呼客戶端。FastMCP 4 因此移除伺服器端的取樣與 roots API，改以多輪往返的方式處理需要額外輸入的情境。

協議版本協商是另一個連帶變化。同一個部署需要同時服務新舊客戶端，框架因此在連線建立時判斷雙方支援的最高版本，新客戶端取得新協議，舊客戶端維持原有行為。這項設計讓升級不必一次到位，也讓框架承擔了過去由應用程式碼處理的相容判斷。

FastMCP 4 帶來哪些架構變化？

核心變化有三：請求改為無狀態自足、連線時自動協商協議版本、以及移除伺服器端取樣與 roots 等推送能力，改以多輪往返工具取代。

無狀態化的直接結果是水平擴充變得簡單。任何一個副本都能獨立回答請求，部署時不再需要黏性工作階段或共享的連線狀態，普通的負載平衡器即可運作。對於以容器編排部署的團隊，這減少了過去常見的連線中斷與重試問題。

第二項變化是工作階段狀態的重新設計。框架引入 UserSession 與 SessionId 的概念，把需要跨請求保留的資訊顯式存放，而非依附在連線上。這樣的切割讓開發者能清楚區分「請求內」與「請求間」的資料，也讓除錯時的狀態追蹤更為直接。

第三項變化在認證層。v4 加入伺服器端的身分斷言（SEP-990 ID-JAG），並把多輪往返工具以守衛模式實作（SEP-2322）。前者讓伺服器能驗證呼叫者身分而不必自行持有憑證，後者則處理工具需要中途取得使用者確認或補充欄位的情況。兩者都指向同一個方向：把安全與互動的責任從應用程式碼移往協議層。

FastMCP 4 有哪些核心功能？

版本新增互動式工具、背景任務、無狀態工作階段與伺服器擴充 API；工具可暫停要求使用者確認或補欄位，再帶答案重新執行。

互動式工具是最直觀的改變。工具在執行途中可以回傳一個「需要輸入」的請求，例如要求核准某個動作，或指出缺少的欄位；客戶端提供答案後，工具帶著同一份上下文重新執行。對於涉及寫入操作的自動化流程，這種設計取代了過去把確認邏輯硬寫進提示詞的做法。

背景任務針對長時間工作。以 @mcp.tool(task=True) 標記的工具會脫離請求路徑執行，透過任務擴充傳回進度與結果。官方把這部分獨立成 fastmcp-tasks 套件，執行引擎沿用既有的 Docket。對於需要抓取網頁、執行批次分析或等待外部系統回應的工具，這避免請求逾時，也讓客戶端可以輪詢狀態。

伺服器擴充 API（SEP-2133）則開放框架自身的掛鉤點。團隊可以在訊息進入時插入中介層、調整工具目錄，或替代理連線加入自訂的標頭轉發規則。v4.1 系列進一步把這些掛鉤用於認證快取、上傳保留期限與 JWKS 更新共享，顯示擴充點已進入實際生產使用。

升級到 FastMCP 4 需要注意什麼？

主要風險在移除的相容層：伺服器端取樣與 roots 已刪除、HTTP 工作階段改為三十分鐘閒置逾時、Regex 工具搜尋不再支援前後環視。

官方說明多數 3.x 應用可以無須修改程式碼即完成升級，但這句話的前提是應用沒有使用已棄用的介面。v4 移除了三系列遺留的模組別名、物件模式裝飾器與多個已標記棄用的參數，若專案曾以相容層維持舊寫法，升級時會直接遇到匯入錯誤。

行為層面的變化更容易被忽略。HTTP 工作階段過去預設永不過期，v4 改為跟隨 SDK 的三十分鐘閒置上限，長時間掛著的客戶端會需要重新建立連線。Regex 工具搜尋改用 Pydantic 的正則引擎，不再支援前後環視與反向引用，既有搜尋樣式若有使用這類語法，必須改寫。

認證相關的調整影響最大。MultiAuth 現在會依來源區分客戶端身分，既有工作階段與任務會進入新的歸屬範圍，官方建議在升級前先清空待處理任務。代理的後端連線也會鏡射前端的協議版本，若後端服務尚未支援新協議，需確認降級路徑是否如預期運作。

FastMCP 的使用規模有多大？

專案現有 28,159 顆星、2,496 次分支與 337 位貢獻者；PyPI 單月下載約 5,369 萬次，v4.1.0 一個版本即有三十二位首次貢獻者。

下載數據的說服力高於星標。PyPI 統計顯示最近一日約 256 萬次、最近一週約 1,374 萬次、最近一月約 5,369 萬次，這種量級通常出現在被 CI 流程反覆安裝的依賴上，而非單純的嚐鮮下載。官方在 README 中稱專案每日下載達百萬次，並估計約七成的 MCP 伺服器使用其某個版本，這個比例與下載曲線相互印證。

貢獻者結構反映專案的開放程度。v4.1.0 的版本說明列出 48 位貢獻者，其中 21 位是首次提交；v4.1.3 則有 11 位，6 位為首次貢獻。對於一個由單一公司主導的框架，這種外部參與比例意味著它已被納入不少團隊的生產流程，而不只是文件範例。

官方 MCP SDK 與 FastMCP 有什麼分別？

官方 SDK 提供協議底層實作，FastMCP 1.0 於 2024 年被併入其中；獨立專案則加上驗證、認證、代理與互動應用的高階封裝。

兩者的分工可以用層級理解。官方 SDK 定義訊息格式、傳輸方式與生命週期，屬於協議的參考實作；FastMCP 在此之上提供宣告式的工具定義、自動產生的結構描述、認證提供者與代理機制。若專案只需要最基本的功能，直接使用 SDK 可以減少依賴；若需要多人協作、權限控管與可觀測性，框架節省的工作量相當可觀。

這種分層也帶來版本耦合的風險。FastMCP 4 緊跟 SDK v2 與新的協議修訂，當協議再次調整時，框架使用者需要跟隨其升級節奏。官方對此的做法是提供多份升級指南，涵蓋從三系列、二系列以及兩種 SDK 版本遷移的路徑，並附上可交給編碼代理執行的稽核提示。

v4.1.3 修復了哪些安全問題？

v4.1.3 要求 certifi 2026.10.19 以上版本，並改用系統信任庫，以回應十月的憑證機構事故；同時修正公開客戶端的 OAuth 認證。

這版發布於 10 月 20 日，主因是十月的憑證機構事故。FastMCP 4 預設採用系統信任庫，框架本身只負責要求較新的 certifi 版本；換言之，單獨升級套件並不足以解決問題，作業系統、容器映像與自訂信任庫都必須同步更新。官方在安全公告中明確列出這條界線，避免使用者誤以為一次 pip install 即可修補。

其餘修正偏向穩定性。公開客戶端的 OAuth 認證在沒有客戶端密鑰時改為預設不帶上游權杖，空白的可見性選擇不再被清空，產生器轉換的結果會在工具執行時正確具現化，每個伺服器的自訂逾時也終於被遵守。這些項目多半來自社群回報，顯示 4.x 在生產環境的使用密度正在提高。

出處連結有哪些？

本文數據來自 FastMCP 官方儲存庫、v4.0.0 與 v4.1.3 版本說明，以及 PyPI 下載統計，皆於 2026 年 10 月 21 日讀取。

官方儲存庫：https://github.com/PrefectHQ/fastmcp

完整文件位於 gofastmcp.com，另提供 llms.txt 與 llms-full.txt 兩種機器可讀格式，方便編碼代理直接取用。版本說明與升級指南可在儲存庫的 Releases 與文件網站的遷移章節中找到。

總結：哪些團隊適合升級 FastMCP 4？

已部署多副本 MCP 服務、需要互動式工具或背景任務的團隊最適合；仍依賴伺服器端取樣與舊版相容層的專案，應先完成盤點再升級。

FastMCP 4 的價值不在功能清單變長，而在於把部署形態的假設換掉。無狀態請求讓 MCP 服務可以像一般 Web 服務一樣水平擴充，協議協商讓新舊客戶端並存，互動式工具與背景任務則補上過去需要自行搭建的環節。對於已經把工具接入生產流程的團隊，這些變化直接影響維運成本。

升級的判斷標準相對清楚。若服務跑在多個副本、需要跨版本相容，或工具涉及寫入操作而需要中途確認，v4 帶來的好處明顯；若專案仍大量使用三系列的相容介面，或依賴伺服器主動取樣，升級前應先以官方指南做一次完整稽核。憑證事故也提醒一件事：框架版本只是供應鏈的一環，信任庫的更新節奏同樣需要納入維運清單。
