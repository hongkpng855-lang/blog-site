1.75 萬星 Cursor 外掛市集：154 個外掛開放

2026年11月20日 15:59 • 閱讀時間 4 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/cursor/plugins

Cursor 在 GitHub 維護的 plugins 倉庫於 2026 年 1 月 23 日建立，至 11 月 19 日累積 17,513 顆星標、1,928 個分支與 819 次提交。倉庫目前收錄 154 個外掛，137 個由第三方服務商提供，讓代理在編輯器內直接操作財務、人資、廣告與專案管理系統。

這個倉庫的定位並非單一工具，而是一份規格與市集清單。根目錄的 .cursor-plugin/marketplace.json 列出全部上架項目，每個外掛資料夾再自帶 plugin.json，兩層結構讓同一份外掛可以被打包、驗證與分發。

倉庫同時放置 .claude-plugin/marketplace.json，讓 Claude Code 也能讀取同一批外掛。目前該清單只列兩個項目，分別是 origin-apps 與 pstack，顯示跨客戶端支援仍在起步階段。

程式碼組成相當集中。GitHub 語言統計顯示 TypeScript 佔 89.0%，其餘為 TLA、JavaScript、Mermaid、Shell 與少量 Java 與 CSS。主要內容是清單檔、驗證腳本與技能說明，並非大型應用程式。

Cursor 外掛市集是什麼？

Cursor 外掛市集是官方 GitHub 倉庫，以 marketplace.json 登記 154 個項目，每項自帶 plugin.json，用 /add-plugin 安裝。

外掛的作用是把外部系統的能力接到代理手上。一個外掛通常包含三層內容：技能說明檔、規則檔，以及描述 MCP 伺服器連線方式的設定檔。代理讀取技能說明後，才知道在什麼情境呼叫哪些工具。

清單檔的欄位設計相當克制。schemas/plugin.schema.json 只要求 name 一個必填欄位，其餘如 displayName、version、author、category、tags、skills、rules、commands、agents、hooks 與 mcpServers 全部可選。這種寬鬆設計降低了上架門檻，也讓不同成熟度的外掛可以並存。

倉庫裡面有哪些類型的插件？

說明文件列出 144 個外掛，整合類 118 個，開發工具 16 個，生產力 8 個。整合類佔八成以上，集中於企業 SaaS 資料存取。

整合類外掛覆蓋的範圍接近一份企業軟體採購清單。Google Workspace 全家桶在列，包括 Gmail、Drive、Calendar、Docs、Sheets 與 Slides；客戶關係管理有 Salesforce、HubSpot、Attio、Close 與 Zoho CRM；財務系統有 Intuit QuickBooks、Xero、NetSuite、PayPal、Square 與 Brex。

人資與協作場景同樣齊備。Workday、Gusto、Rippling 處理人事與薪資資料，Zoom、Otter、Fireflies 與 Fathom 負責會議紀錄，Lark、Feishu 與 Lark Base 覆蓋華人市場常用的協作工具。廣告投放則有 Google Ads、Meta Ads、TikTok for Business 與 X Ads。

開發工具類的外掛數量不多，但針對性強。GitHub、Playwright、Excalidraw 與 BigQuery 屬於此類，另有 thermos 這種以分支審查為核心的代理編排外掛，內含兩個子代理與兩套技能，用並行方式對差異內容做正確性與安全審查。

插件清單為何與實際數量不一致？

清單登記 154 個外掛，說明表格只列 144 個，差額含 Greenhouse、OneDrive 與 Trello。倉庫已有議題記錄落差。

落差反映的是合併節奏。11 月 17 日至 19 日期間，倉庫接連加入 LMTY、CreateOS、HQ、Item、Rillet、Expensify 與 Strava 等外掛，並把 QuickBooks 外掛更名為 Intuit QuickBooks 同時更新標誌與分類。說明文件由人工維護，追不上每日變動。

維護壓力的另一項指標是待審佇列。倉庫目前有 134 個開啟議題與 553 個待合併請求，合計 687 項，累計已合併請求達 1,291 個。對一個以清單與說明檔為主體的倉庫而言，審查負擔主要落在格式驗證與描述品質上。

倉庫已備有自動化工具處理這類工作。scripts/validate-plugins.mjs 負責檢查清單與外掛結構，create-plugin 外掛則提供腳手架與驗證流程，讓提交者先自行檢查再送出。

這些插件與 Grok 有什麼關係？

說明文件 9 處提及 Grok，集中於財務與生活服務外掛。這些外掛讓 Grok 讀取帳戶、持倉與訂單，屬收購後整合。

具體線索寫在描述文字裡。finance 外掛說明它連接帳戶後，Grok 可以回答支出、訂閱與投資問題；quickbooks-online 描述它與 Grok Bot 協作處理企業財務；shopify-store、tesla、strava、expensify 與 gopuff 的說明也直接以 Grok 作為操作主體。

這種寫法把外掛層從單純的工具適配，推向消費級代理的入口。以 Robinhood、Coinbase、Webull 與 Interactive Brokers 為例，外掛讓代理讀取持倉與即時行情，並在下單前要求使用者確認。權限邊界寫得明確，但涉及的資料敏感度極高。

如何安裝並使用 Cursor 外掛？

在 Cursor 內輸入 /add-plugin 加外掛名稱即可安裝，例如 /add-plugin thermos。外部服務需另行授權，金鑰由使用者自行填入。

安裝流程刻意做得很短。以 thermos 為例，外掛說明只寫一行 /add-plugin thermos，其餘架構細節交給 README 的流程圖交代，包含編排器、兩個子代理與兩套技能之間的呼叫關係。

需要跨客戶端使用的團隊可以走另一條路。倉庫的 .claude-plugin/marketplace.json 供 Claude Code 讀取，目前收錄 origin-apps 與 pstack 兩項；前者針對 Cursor Origin API 的憑證、範圍、webhook 與分頁規則提供技能，後者是一套強調先深後快的代理工作流。

憑證管理是最需要留意的一環。orchestrate 外掛明確要求使用個人層級的 CURSOR_API_KEY，並要求先讀完 cursor-sdk 技能內的身分驗證章節再動手。倉庫本身不含密鑰，但外掛一旦接上企業系統，權限範圍由使用者的授權決定。

開發者可以自己發佈外掛嗎？

可以。倉庫是多外掛市集，第三方提交放在 third_party 目錄，目前有 137 個資料夾，提交前可用 create-plugin 生成骨架。

貢獻者數量約 34 人，已合併請求 1,291 個，第三方目錄下 137 個外掛資料夾。多數外掛由服務商自行提交，Cursor 團隊負責審查與格式統一，審查週期可從 11 月中旬的合併紀錄觀察，單日可合併多個新外掛。

值得注意的是部分外掛由個人開發者撰寫。continual-learning、cursor-team-kit、cli-for-agent 出自 Eric Zakariasson，pstack 出自 Lauren Tan，dyl-stack 出自 Dylan Gattey。市集並非只收官方項目，個人的工作流也能上架。

這個市集對代理工具生態有什麼影響？

它把 MCP 從規格層推進到打包層，讓企業系統整合變成可安裝項目。倉庫集中管理 137 個第三方外掛，規模與審查壓力同步放大。

外掛化的意義在於標準化封裝。同一份技能說明檔可以同時被不同代理讀取，開發者不必為每個客戶端重寫整合邏輯。Claude Code、Codex 與 Gemini CLI 都已支援類似的技能或擴充機制，封裝格式正在收斂。同類清單在 Copilot 生態亦已出現，Copilot 外掛市集 以相近結構集中管理千件技能；n8n-MCP 則把單一平台的節點知識包成工具集。

風險集中在治理與憑證兩端。137 個第三方外掛意味著 137 套授權流程與資料處理方式，任何一個外掛的描述誇大或權限過寬，都會把風險傳導到使用者帳戶。倉庫目前靠格式驗證與人工審查把關，並未見到權限清單之類的機制。

商業訊號同樣明顯。財務、人資與廣告類外掛密集上架，顯示代理工具的競爭點已從模型能力轉向可觸及的資料範圍。哪一方的代理能讀到更多企業系統，哪一方就更容易成為工作入口。

出處連結有哪些？

倉庫位於 github.com/cursor/plugins，清單檔在 .cursor-plugin 目錄，結構規範放在 schemas 內。

主要入口是 https://github.com/cursor/plugins，倉庫首頁可直接看到 17.5k 星標與 819 次提交。想確認某個外掛是否已上架，查閱 .cursor-plugin/marketplace.json 最準確，說明文件的表格存在滯後。

需要自行開發外掛的讀者，可先讀 schemas/plugin.schema.json 與 schemas/marketplace.schema.json，再參考 thermos 或 orchestrate 的資料夾結構，兩者都包含完整的清單檔、技能目錄與流程圖。

總結：哪些團隊適合使用 Cursor 外掛市集？

已使用 Cursor 且需要讓代理讀取企業系統的團隊最適合，尤其是財務、人資與廣告場景。只做本機編碼、不接外部服務的團隊，效益有限。

價值判斷取決於資料邊界。若團隊的日常工作大量涉及 Salesforce、Workday、QuickBooks 這類系統，外掛能把查詢與整理動作壓縮成一句指令，節省的時間相當可觀。若工作集中在程式碼與版本控制，現有的 GitHub 與 Playwright 外掛已足夠，其餘清單可以暫時略過。

採用前建議先確認三件事：外掛的授權條款是否逐個附帶、憑證由誰保管、以及代理在涉及金錢或人事資料時是否要求確認。上述三點在倉庫文件中有交代，但分散在不同外掛的 README 內，需要逐項核對。

常見問題有哪些？

以下五題說明外掛與 MCP 的差異、免費與付費界線、企業資料的處理方式、與其他客戶端的相容性，以及第三方外掛的審查機制。

外掛與 MCP 伺服器是同一件事嗎？

不完全相同。MCP 伺服器負責提供工具介面，外掛則是把技能說明、規則、指令與 MCP 連線設定打包成一個可安裝單位。安裝一個外掛，可能同時引入數個 MCP 伺服器。

使用這些外掛需要額外付費嗎？

外掛本身免費，倉庫逐個外掛附帶 MIT 授權。但外掛連接的服務多數需要各自的訂閱或 API 額度，例如 Salesforce、QuickBooks 與 Zoom 均按原廠方案計費，代理呼叫時消耗的是該服務的額度。

企業資料會不會離開自己的環境？

取決於外掛連接的服務。外掛以 MCP 連線呼叫外部 API，資料會傳到對應服務商。少數外掛如 tailscale 允許代理存取私有網路內的 MCP 伺服器，資料路徑因此留在自建網路中。

可以在 Claude Code 或 Codex 使用同一批外掛嗎？

部分可以。倉庫另備 Claude Code 版清單，目前只列 origin-apps 與 pstack 兩項。Codex 與 Gemini CLI 尚未見到對應清單，技能格式相近但需自行調整目錄結構。

第三方外掛由誰審查？

由 Cursor 團隊審查後合併，提交者需符合清單格式與描述規範。倉庫提供 validate-plugins.mjs 與 create-plugin 腳手架降低退件率，但審查標準未公開成文，目前仍有 553 個待合併請求排隊。
