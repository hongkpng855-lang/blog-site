LlamaIndex 大改版：520 套件棄 Python 3.10

2026年11月18日 20:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/run-llama/llama_index

LlamaIndex 是累積 5.29 萬顆星標的開源文件框架，於 2026 年 11 月 13 日發布 0.14.26 版。此次把核心套件最低 Python 版本由 3.10 升至 3.11，連帶調整 520 個整合套件的相依宣告，重心亦轉向 LlamaParse 解析平台。

這個專案由 Jerry Liu 於 2022 年 11 月建立，最初定位為連接大型語言模型與私有資料的「資料框架」。三年之間，它從單一檢索管線工具長成包含三百餘個整合套件的生態，如今則把主力產品移往雲端文件解析服務。

LlamaIndex 是什麼？

2022 年 11 月建立的開源資料框架，以 Python 撰寫，採 MIT 授權。提供連接器、索引與檢索介面，把私有文件接上大型語言模型。

框架的設計分成兩層。核心套件 llama-index-core 只保留抽象介面與管線骨架，各家模型、向量儲存與檔案解析器則以獨立套件形式發佈，使用者按需要安裝。這種拆分讓核心保持輕量，代價是版本對齊變得複雜。

README 現時把專案描述為「建構代理式應用程式的開源框架」，同時明確指出公司的首要產品已改為 LlamaParse，一個處理代理式 OCR、解析、抽取、索引與切分的企業平台。文件亦提到 LiteParse 專案，定位為免費而快速的純文字解析器。

0.14.26 版本帶來哪些變動？

版本於 11 月 13 日發佈，核心套件最低 Python 版本升至 3.11，520 個整合套件同步改寫相依宣告，並清理五萬五千餘筆安全警示。

版本說明以機械式清單列出每個套件的變更，主軸是兩支合併請求。第一支僅重寫 528 個 uv.lock 鎖定檔，把各套件開發環境內被警示的相依升級至首個修補版本，不動任何對外發佈的版本範圍。

第二支則改動對外契約。它在 520 個 pyproject.toml 內把 requires-python 由 3.9 或 3.10 抬升至 3.11，另有 25 個套件同時調整執行期相依下限。維護者在請求說明中標明此舉屬於破壞性變更，每個受影響套件都需要新的主版本號。

模型登記亦有更新。版本說明列出 Claude Opus 5.5、Sonnet 5.5、Haiku 5.5，以及 GPT-6 Astra、Sol、Luna 與 GPT-6.1 Sol 的支援，Bedrock 通道另修正了對 Claude Opus 5.5 強制送出工具選擇參數的問題。

為何 520 個套件要同步抬升 Python 門檻？

上游相依已不支援舊解譯器。Pillow 13 需要 3.11，aiohttp 需要 3.10，而 Python 3.9 與 3.10 均已終止支援。

維護者在請求說明中列出三條具體約束。Pillow 12.1.1 起需要 Python 3.10 以上，Pillow 13 需要 3.11；aiohttp 3.14.4 起需要 3.10。安全修補一旦落在這些版本，舊解譯器就無法安裝，配套的修補也無法送達使用者。

第二層原因是語言的支援週期。Python 3.9 與 3.10 已進入終止支援階段，仍留在這兩個版本的專案將無法取得安全性更新。維護者把抬升與重新鎖定綁在同一次提交，避免出現宣告已改而鎖定未跟的中間狀態。

這種做法對使用者的實際影響取決於部署環境。以 3.11 以上執行環境部署的服務不受影響，僅在重新安裝時取得較新的相依版本。仍停留在 3.10 的環境則會在升級時遇到安裝失敗，需要先處理解譯器版本。

安全性維護的實際規模有多大？

待處理機器人警示為 59,709 筆，兩支請求合計清除 55,516 筆，餘下 252 筆。其中約四十五筆屬上游未修補，鎖定版本已在受影響範圍外。

這個數字來自 GitHub 對鎖定檔的掃描。由於專案把三百餘個整合套件放在同一個儲存庫，每個套件各自持有一份鎖定檔，同一筆上游公告會在數百個檔案內重複出現，警示總量因此被放大。

維護者在這輪處理中分批推進。第一支請求按讀取器、模型、嵌入、工具、向量儲存等類別切分，只升級各套件開發與持續整合環境所用的鎖定。第二支請求才改動對外發佈的版本範圍，並把仍允許脆弱版本的上限一併收緊。

剩餘項目的性質值得留意。維護者說明約四十五筆屬於尚無修補版本的公告，而鎖定中的實際版本已高於受影響範圍，屬於掃描器的誤報。這類項目無法透過升級消除，只能等待上游發佈或調整掃描設定。

專案重心轉向何處？

重心移至 LlamaParse 雲端平台，涵蓋代理式 OCR、結構化抽取、索引與切分。框架仍持續維護，另以 LiteParse 提供免費解析器。

README 的提示區塊直接承認這次轉向。文件寫道，公司自框架三年前推出以來已有演進，早期以廣泛的編排工具讓開發者建構檢索與代理應用，如今重心轉向 LlamaParse，以及 LiteParse 與兩套公開基準測試。

這個取向背後的判斷是代理已成為文件的新消費者。文件指出，無論是處理大量文件的 AI 新創或需要自動化文件流程的企業，真正瓶頸在於準確而低成本地從最難的文件中取出上下文，這也是解析服務被視為核心產品的原因。

LiteParse 於 2026 年 2 月建立，累積 1.3 萬顆星標，採 Apache 2.0 授權，定位為免費而快速的文字解析器。它與商業平台並存，讓不願付費的使用者仍有一條可自架的路徑，同時也為商業產品提供對照基準。

與同類框架相比有何差異？

差異在於整合廣度與抽象層次。框架提供三百餘個整合套件與兩層介面，高階介面數行即可查詢文件，低階介面可替換連接器與檢索模組。

同類框架多數把管線封裝成固定形狀，優點是上手快，缺點是遇到非典型文件時難以繞道。LlamaIndex 的做法是同時提供兩套介面，讓使用者先以高階介面驗證流程，再逐段替換成自訂實作。

代價落在版本管理。核心與整合套件分開發佈，每一支整合都有自己的版本節奏，一次例行升級可能同時牽動數十個套件的版本下限。此次把 Python 門檻統一抬升，某種程度上是在收拾這種分散發佈累積的債務。

若需要先釐清檢索架構的基本取捨，可參考圖譜檢索框架實測的比較框架；若是評估代理式文件流程，則文件解析工具比較提供另一組對照樣本。

如何開始使用 LlamaIndex 0.14.26？

先確認解譯器為 Python 3.11 以上，再安裝 llama-index 或只裝核心並按需要加入整合套件。升級前宜重建虛擬環境。

入門路徑由一個套件組成。llama-index 內含核心與一批常用整合，適合先跑通文件載入、切分、索引與查詢的完整流程。需要精簡依賴的專案則只安裝 llama-index-core，再逐一加入模型、嵌入與向量儲存套件。

安裝指令與文件一致。範例先安裝核心，再分別加入 OpenAI、Ollama 與 Hugging Face 嵌入套件，這種組合讓使用者可按實際使用的模型替換，不必為未使用的供應商付出安裝成本。

升級時有兩個實務要點。第一是重建環境，若在同一個虛擬環境內直接升級，殘留的舊版套件可能與新的 Python 門檻衝突。第二是檢查自訂整合，凡自行修改過相依宣告的套件，都需要手動比對新的版本下限。

專案有哪些實際使用限制？

主要限制有三：整合套件版本分散，升級須逐項比對；文件部分章節落後於程式碼；進階解析與抽取能力集中於付費雲端服務，自架功能較基本。

版本分散是最常見的摩擦點。三百餘個整合套件各自發佈，主版本號與核心並非同步推進，一次升級可能需要同時處理多個套件的相依衝突，對長期維護的專案形成額外負擔。

文件落差亦需留意。README 自行註明更新頻率不及官方文件，部分快速入門內容可能對應較早的介面。實際開發時應以官方文件站為準，並以套件版本號核對可用的參數。

功能邊界則取決於部署形態。代理式 OCR、結構化抽取與大規模切分能力集中在雲端平台，開源部分提供的是編排骨架與社群整合。若需求落在高難度文件的準確抽取，付費服務與自架方案之間存在實質差距。

總結：LlamaIndex 適合什麼團隊？

需要快速搭建文件問答或檢索管線、並願意自行管理相依版本的團隊最適合。若追求開箱即用的高難度文件解析，或無法承擔升級維護成本，直接採用託管服務更為省事。

這個框架的價值在於把文件處理拆成可替換的環節。索引、檢索、重排與生成各自獨立，團隊可以先用預設組合驗證效果，再針對薄弱環節替換實作，不必從零搭建管線。

限制與維護成本同樣清晰。此次版本把 Python 門檻統一抬升至 3.11，短期內會迫使部分環境升級；長期而言，減少支援版本反而降低維護分支的負擔。對於已在 3.11 以上環境運行的專案，這次更新的實際衝擊接近於零。

對於仍在評估文件解析方案的使用者，值得把框架與解析服務分開判斷。框架解決的是編排與檢索，解析服務解決的是取字準確度，兩者可以並用，也可以只取其一。
