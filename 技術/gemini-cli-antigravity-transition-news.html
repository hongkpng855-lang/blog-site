Gemini CLI 十萬星之後：Antigravity CLI 接棒

2026年10月21日 08:00 • 閱讀時間 4 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/google-gemini/gemini-cli

Gemini CLI 是 Google 開源的終端機 AI 代理，GitHub 星標達 107,471，fork 數 14,746，累積 701 位貢獻者，採 Apache-2.0 授權。這個專案在 2026 年 5 月被官方宣告由 Antigravity CLI 接棒，並自 6 月 18 日起停止為免費與 Pro 用戶提供請求服務。值得注意的是，專案並未封存，10 月 20 日仍照常發布 v0.65.0 穩定版。這種「專案活著、服務結束」的狀態，正是本次事件最容易被誤讀的部分。

Gemini CLI 是 Google 開源的終端機 AI 代理，星標 10.7 萬。官方自 2026 年 6 月 18 日起停止為個人用戶服務，改由 Antigravity CLI 接手。

README 的第一屏已經不再是功能介紹，而是兩段黃色提示框。這種排版在大型開源專案中並不常見，通常意味著維護團隊希望每一位進入頁面的開發者，在閱讀安裝指令之前先理解一件事：專案的方向已經改變。

Gemini CLI 是什麼？

Gemini CLI 於 2025 年 4 月開源，以 TypeScript 撰寫，讓開發者在終端機直接呼叫 Gemini，並支援 MCP 伺服器與腳本化模式。

專案建立於 2025 年 4 月 17 日，主要語言為 TypeScript，主題標籤涵蓋 ai、ai-agents、cli、gemini、gemini-api 與 mcp-client。它的核心價值在於把模型能力從瀏覽器搬回終端機：開發者可以在同一個工作目錄內讀寫檔案、執行 shell 指令、查詢 pull request，或是以 gemini -p 的無互動模式把模型接入自動化流程。

安裝路徑相當多元，npm 全域安裝、Homebrew、MacPorts、conda 與 npx 即時執行皆可，這種廣度反映它在 2025 年快速擴散的策略。授權採 Apache-2.0，官方文件站與 npm 套件獨立維護，並提供免費課程與公開的產品路線圖專案板。

Gemini CLI 為什麼被 Antigravity CLI 取代？

官方稱工作流程已轉向多代理協作，終端工具需與其他環節共用後端，因此把資源集中到 Antigravity 平台。

官方在 2026 年 5 月 19 日的公告中給出的解釋相當直接：開發者的需求已經從單一代理轉向多個代理互相協作，終端機工具因此需要與工作流程的其他部分共用同一套後端。公告同時列出社群規模作為對照，包括超過 100,000 顆星標、6,000 個已合併的 pull request，以及數百位貢獻者。

這項決策的關鍵詞是「統一」。Antigravity CLI 與 Antigravity 2.0 桌面應用共用同一套代理框架，官方稱之為 agent harness，意味著核心代理能力的後續改良會同時套用到所有入口。對 Google 而言，這是把維護成本從兩條產品線收斂為一條；對開發者而言，則代表過去在 Gemini CLI 上累積的肌肉記憶與腳本，需要在一個新工具上重新驗證。

Antigravity CLI 有哪些技術改動？

Antigravity CLI 以 Go 重寫，啟動更快，可在背景下非同步編排多個代理，並保留 Agent Skills、Hooks、Subagents 與外掛機制。

語言選擇是最明顯的差異。Antigravity CLI 以 Go 編寫，官方形容為更快、反應更靈敏。對命令列工具而言，啟動延遲直接影響使用頻率，這也是許多 JavaScript 生態工具近年改用 Go 或 Rust 重寫的共通原因。

第二項改動是工作模式。官方明確提到非同步工作流程：Antigravity CLI 可以在背景下協調多個代理處理複雜任務，讓使用者在大規模重構或同時研究多個主題時，不必鎖住終端機工作階段。這一點正好對應公告中所說的多代理現實。

功能面上，官方承認新工具上線時不會與舊版一一對應，但保留了四項被視為關鍵的能力：Agent Skills、Hooks、Subagents，以及原本稱為 Extensions、現已改稱 Antigravity 外掛的擴充機制。對重度使用者而言，這四項的實際行為是否一致，比功能清單的長度更值得驗證。

Gemini CLI 目前還會更新嗎？

會。專案維持穩定版與預覽版每週、nightly 每日三條通道，2026 年 10 月 20 日仍發布 v0.65.0 穩定版。

這是本次事件最容易被忽略的細節。README 記載的發布節奏仍然完整：預覽版每週二 UTC 23:59 發布，被視為尚未完整驗證的版本；穩定版每週二 UTC 20:00 發布，內容是前一週預覽版的完整晉升加上修正；nightly 則每日 UTC 00:00 從主分支建置。

實際比對版本紀錄可以印證這條節奏沒有中斷。v0.63.0 於 10 月 6 日發布，v0.64.0 於 10 月 13 日，v0.65.0 於 10 月 20 日，中間每晚皆有對應的 nightly 標籤。v0.65.0 的變更清單以修正為主，涵蓋非信任資料夾中的唯讀工作區設定、恢復工作階段時的重複工具回應、終端機在 Ctrl+O 展開時的畫面重繪，以及 OAuth 回呼的 iss 參數驗證對齊 RFC 9207 規範。過去七日內，主分支至少累積 30 個提交。

換言之，專案並未進入維護凍結狀態。Google 對企業客戶的承諾，讓這條發布流水線必須繼續運作。

企業用戶與付費用戶的支援有何不同？

透過 Gemini Code Assist Standard 或 Enterprise 授權的組織存取不變；個人與 Pro 用戶則自 6 月 18 日起停止服務。

這條分界線的判斷依據不是使用量，而是合約形式。官方說明，若組織透過 Gemini Code Assist Standard 或 Enterprise 授權使用 Gemini CLI 或 IDE 擴充功能，或是透過 Google Cloud 使用 Gemini Code Assist for GitHub，存取權限維持不變，並會繼續獲得最新 Gemini 模型的支援。此外，付費的 Gemini 與 Gemini Enterprise Agent Platform API 金鑰仍可存取 Gemini CLI。

受影響的範圍則包括以 Google AI Pro、Ultra 訂閱使用的用戶，以及以免費的 Gemini Code Assist for individuals 使用的開發者。Gemini Code Assist for GitHub 亦同步受限，自 6 月 18 日起，GitHub 組織無法再進行新安裝，後續數週內既有請求也將停止服務。

這個設計留下一個實務上的模糊地帶：同一間公司內部，採用企業授權的團隊可以繼續使用 Gemini CLI，而以個人帳號試用的成員則必須轉換工具。對需要統一開發環境的組織而言，這種並存狀態本身就是維運成本。

開發者應否從 Gemini CLI 遷移到 Antigravity CLI？

若依賴免費或 Pro 額度，遷移已屬必要；企業授權用戶可先以小專案驗證多代理編排與外掛相容性，再安排切換。

判斷的起點是存取權限，而不是功能偏好。個人開發者與 Pro 訂閱者在 6 月 18 日之後已無法透過 Gemini CLI 取得模型請求，繼續留戀舊工具沒有實際意義，真正的問題是 Antigravity CLI 能否承接既有自動化腳本。

第二層考量是整合深度。若既有流程依賴 gemini -p 的無互動輸出，並以 --output-format json 或 stream-json 解析結果，遷移時必須逐一驗證新工具的輸出結構與錯誤處理行為。官方已表明新工具上線時不會有一一對應的功能，這種落差在批次腳本中往往比互動使用更早暴露。

第三層是團隊治理。Gemini CLI 的企業文件涵蓋信任資料夾、沙盒執行與遙測設定，v0.65.0 亦強化了非信任資料夾中的唯讀工作區設定。若組織的合規要求建立在這些機制上，切換前應先確認 Antigravity CLI 是否提供對等控制，而不是等到事故發生後補救。

下載數據值得單獨解讀。服務已在 6 月中停止為個人用戶提供，但 npm 套件在 2026 年 9 月 19 日至 10 月 18 日的區間仍有 1,602,990 次下載，近一週亦有 227,214 次。這些數字一部分來自企業授權環境的自動化安裝，一部分來自 CI 流程中尚未移除的依賴，也有一部分是開發者在切換工具期間的並行使用。單看下載量會高估活躍度，但它確實說明這個套件仍深度嵌入既有的工具鏈。

出處連結有哪些？

資料來自 Gemini CLI 的 GitHub 儲存庫、npm 下載統計，以及 Google 於 2026 年 5 月 19 日發布的轉換公告。

主要出處為 GitHub 上的 Gemini CLI 儲存庫，網址是 https://github.com/google-gemini/gemini-cli ，README、版本紀錄與貢獻者統計皆可於該處查證。官方轉換說明發表於 Google Developers Blog，標題為「An important update: Transitioning Gemini CLI to Antigravity CLI」，發布日期為 2026 年 5 月 19 日。npm 下載量取自 npm registry 的公開統計端點，@google/gemini-cli 套件的週下載與月下載數字如上表所示。

總結：Gemini CLI 適合什麼團隊？

Gemini CLI 適合持有企業授權、需要穩定終端代理的組織；個人開發者應直接評估 Antigravity CLI。

這個案例的價值不在於「十萬星專案被取代」的戲劇性，而在於它展示了大型開源專案的一種常見歸宿：社群規模與產品生命週期並不完全同步。專案仍在更新、貢獻者仍在提交、套件仍有下載，但官方服務的對象已經重新劃定。

對技術決策者而言，可執行的結論有三點。第一，評估開源工具時應把「服務條款與授權形式的變化風險」納入考量，而非只看星標與功能。第二，凡是納入自動化流程的模型呼叫，都應保留可替換的介面層，降低單一工具退場時的改寫成本。第三，企業授權帶來的穩定性是真實的，但它同時意味著團隊會被綁定在一個官方已宣告不再是主要投資方向的產品上，這個取捨需要定期重新檢視。
