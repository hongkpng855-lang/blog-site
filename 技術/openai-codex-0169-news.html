Codex CLI 0.169：13.5 萬星的終端工作區擴張

2026年11月14日 20:00 • 閱讀時間 3 分鐘 • Eric Chan • 來源：GitHub

內容創作者： https://github.com/openai/codex

OpenAI 開源的 Codex CLI 於 2026 年 11 月 13 日推出 0.169.0 版，這個以 Rust 撰寫的終端編程代理在 GitHub 累積 135,179 顆星標。新版本把終端工作區擴充為可同時開啟多個側邊對話分頁，並補上自訂模型供應商設定、裝置碼授權與 Cloud 連線，同時收緊未受信任目錄的執行邊界。

Codex CLI 是什麼？

Codex CLI 是 OpenAI 以 Rust 撰寫的終端編程代理，可於本機讀寫儲存庫並執行指令，採 Apache-2.0 授權，2026 年 11 月累積 135,179 顆星標。

官方文件把它定位為跑在使用者電腦上的編程代理，並提供三條使用路徑：終端機、編輯器整合與桌面應用程式。倉庫同時是發佈管道，每個版本附上對應平台的執行檔，包含 macOS 的 Apple Silicon 與 x86_64、Linux 的 musl 靜態版本。

安裝方式分為四類。官方提供 shell 與 PowerShell 的一行安裝腳本，亦支援 npm 全域安裝、Homebrew cask，以及直接下載二進位檔。安裝器預設從官方發佈站下載，若中繼資料或檔案不可用才回退至 GitHub Releases，亦可透過環境變數強制指定來源。

授權模式與帳號綁定。使用者可以透過 ChatGPT 的 Plus、Pro、Business、Edu 或 Enterprise 方案登入，亦可以使用 API 金鑰，但後者需要額外設定驗證流程。這個安排把成本計算與既有訂閱綁在一起，企業採購時通常會影響決策。

0.169.0 版為終端工作區加入哪些能力？

0.169.0 版讓終端工作區支援多個側邊對話分頁，並可依名稱、提示詞預覽或工作目錄搜尋舊任務，另加入折疊回合細節與診斷壓縮檔的本機儲存。

版本紀錄把新功能分成六項，其中三項直接改變終端的操作方式。工作區可以同時開多個側邊對話分頁，以鍵盤或滑鼠切換，重啟之後仍能回復已儲存的本地側聊。這讓同一個專案可以並行處理互不相關的問題，而不必開多個終端視窗。

第二項是任務檢索。代理指令中心支援以名稱、提示詞預覽或工作目錄搜尋舊任務，過去的對話不再只能靠時間序列翻找。長期使用之後，這種檢索能力往往比新增功能更影響日常效率。

第三項與輸出可讀性有關。全屏逐字稿提供折疊回合細節的開關，已完成的活動會收在對應提示詞之下，答案保持可見，工具輸出仍可搜尋。對於動輒數十回合的長任務，這個調整直接影響回顧成本。

另外三項偏向邊緣場景。終端報告編輯器可以按 Ctrl+S 把診斷壓縮檔存在本機，即使上傳功能被停用；鍵盤快捷鍵與側邊欄選擇器亦補上尺寸調整與浮動面板。這些改動單獨看很小，合起來則說明維護團隊正在處理長時間使用的細節。

側邊對話分頁解決什麼實際問題？

單一對話序列難以承載並行工作。分頁把不相關的追問隔離在獨立上下文，避免主線被支線內容稀釋，重啟後亦可續接原本的討論。

終端代理的預設模型是線性對話。使用者提出一個問題，代理回答，接著追問，上下文沿著單一軌跡累積。這種設計在短任務上很有效率，一旦出現「順便問一下」的需求，支線內容就會混進主線上下文。

混入的代價是雙向的。支線的無關細節佔用上下文額度，主線的長篇推理亦會干擾支線的判斷。當上下文接近上限而觸發壓縮，兩條線索的內容都可能被摘要，細節一併流失。

分頁把兩者分離。每個側邊分頁持有獨立的對話狀態，主線與支線各自累積，互不稀釋。這個做法與編輯器的分割視窗類似，差別在於切分的是上下文而非畫面。

本地保存則是延續性問題。重啟之後仍能回復已儲存的側聊，意味著分頁不只是暫時的視窗，而是可以跨工作階段存續的物件。對需要分日推進的長任務，這一點比切分本身更關鍵。

自訂模型供應商與裝置碼授權意味著什麼？

終端現在可以直接新增或編輯自訂模型供應商，並在登入時以裝置碼完成網關授權。這讓 SSH 或無本機瀏覽器的環境不必依賴圖形介面。

模型供應商的設定過去偏向設定檔作業。使用者要開啟檔案，手動填入端點與模型名稱，再回到終端驗證。新版把這一步搬進終端介面，可以在登入流程中建立供應商，所選設定即時生效。

裝置碼授權處理的是環境限制。在 SSH 連線或沒有本機瀏覽器的主機上，傳統的 OAuth 回呼無法完成，使用者往往只能退回長期有效的 API 金鑰。裝置碼把授權拆成兩步：終端顯示一組代碼，使用者在另一台裝置確認，憑證再回寫到原主機。

兩項改動合起來，指向同一個方向。代理的模型來源與身分驗證，正從「個人本機的一次性設定」變成「可在遠端主機重複執行的流程」。對需要在大批伺服器上部署代理的團隊，這是能否自動化的分界線。

版本紀錄亦提到應用伺服器端的能力補齊。用戶端可以列出可用模型，或為已設定的供應商授權網關，而不改變預設供應商。這類介面變動通常不會出現在使用者的第一印象裡，卻決定了整合層能否穩定運作。

Cloud 連線把哪些功能搬進終端？

macOS 與 Linux 的 Cloud 連線屬於選用功能，開啟後可在終端傳送圖片、選擇模型與推理強度，並封存或還原雲端對話。

雲端與本機兩條路線過去分工明確。終端代理處理本機儲存庫，網頁版本處理雲端任務，兩者共用帳號但介面分離。新版把部分雲端操作拉回終端，讓同一個視窗可以涵蓋兩類工作。

具體能力包含三項。使用者可以在終端傳送圖片給支援視覺的模型，選擇模型與推理強度，以及封存或還原雲端對話。這些操作過去需要切換到瀏覽器完成。

選擇性設計值得注意。Cloud 連線在 macOS 與 Linux 上屬於需主動開啟的選項，而非預設行為。這種安排反映出企業環境的顧慮：本機執行的代理一旦預設連上雲端，資料流向就會改變，稽核邊界亦需重新界定。

對個人使用者而言，這項改動降低的是切換成本。對組織而言，真正的問題是政策：哪些專案允許送往雲端，哪些必須留在本機。工具提供了通道，邊界仍要靠規範劃定。

未受信任目錄的執行邊界如何收緊？

codex exec 在未受信任目錄會停用專案設定與 MCP 伺服器，即使加上 --sandbox workspace-write，需以 --trust 標記信任。

專案設定與 MCP 伺服器都來自儲存庫內的檔案。這些檔案一旦被載入，就等於讓專案內容影響代理的執行環境，包括可呼叫的外部工具與連線位址。在未經審查的儲存庫上執行代理，這條路徑本身就是風險。

過去的假設是沙箱模式足以隔離。實際上 --sandbox workspace-write 只限制寫入範圍，並不處理設定載入；代理仍可能讀入專案層級的設定，並依此建立外部連線。新版本把兩件事分開處理。

修正後的預設值是停用。在未受信任的目錄中，codex exec 與 codex review 會保持專案設定與 MCP 伺服器關閉，使用者必須以 --trust 明確標記，專案信任才會被保存。這個設計把風險判斷交回使用者，而非交給路徑啟發式規則。

同批修正還包括幾項互動層面的整頓。中斷的回合現在會乾淨結束，延遲的中止或檔案授權取消不會干擾下一個回合；終端亦不再因為共享應用伺服器未回報的 MCP 伺服器而持續等待。這些問題在自動化腳本中特別明顯，因為沒有人會在旁邊手動重試。

星標對分支比約為 6.3 比 1，與前一個月觀察到的比例一致。這個數字低於工具類專案常見的十倍區間，通常意味著採用者傾向直接使用官方發佈的執行檔，而非複製倉庫自行修改。

未結問題數升至 27,534 項，較 10 月下旬的 25,051 項增加約一成。對照 477 位貢獻者與每日多次提交的節奏，問題佇列的吸收速度仍跟不上使用者增長，這是高速擴張階段常見的現象。

版本節奏維持高頻。0.168.0 與 0.169.0 同在 11 月 13 日發佈，倉庫累計版本數達 1,291 個；同期還有數個 alpha 版本在推進。這種小步快跑的策略讓修補能快速落地，代價是使用者需要主動追蹤變更。

語言組成說明重心。Rust 約 86.1 MB，Python 約 1.7 MB，其餘為 Starlark、TypeScript、PowerShell 與 Shell 等輔助部分。主體以系統語言撰寫，與需要低延遲啟動的終端工具定位相符。

與其他終端編程代理相比定位如何？

同期競品為約 10.8 萬星的 Gemini CLI 與 22.6 萬星的 OpenCode。Codex CLI 以 Rust 實作、綁定 ChatGPT 訂閱，重心放在權限治理。

同類工具的規模接近。Gemini CLI 在查詢當日累積約 108,813 顆星標，定位同樣是終端內的編程代理，並以開源方式釋出；OpenCode 累積約 226,604 顆星標，以 TypeScript 撰寫。三者的使用者群高度重疊，選擇往往取決於既有訂閱與模型偏好。

差異出現在實作與治理兩層。Codex CLI 以 Rust 撰寫，啟動延遲與記憶體佔用較低；權限設計分成多個設定檔，配合沙箱、網路代理與專案信任標記控制外部存取。這些安排對需要在受管裝置上執行代理的組織更有吸引力。

生態整合是另一個分野。官方同時提供編輯器擴充與桌面應用程式，同一帳號可在多個入口使用；一體化路線降低切換成本，但也意味著使用深度與訂閱方案綁定。若團隊同時使用多間供應商，以單一閘道轉發多家模型的開源方案可降低硬綁定風險；而同期的 Qwen Code 1.0 預覽版則把重心放在把既有代理能力併入終端。

評估時值得先釐清需求邊界。若重點在模型能力比較，多數工具都能切換供應商；若重點在權限稽核與憑證治理，近幾個版本反覆出現的沙箱、信任標記與認證修補，會比任何功能清單更能說明維護團隊的優先順序。

升級到 0.169.0 前應注意什麼？

既有腳本應先確認 codex exec 在未受信任目錄的行為變化，並檢查是否依賴沙箱模式自動載入專案設定。跨主機部署需重測裝置碼授權。

專案信任的行為變化是第一項要驗證的。若既有腳本依賴專案內的設定或 MCP 伺服器在沙箱模式下自動生效，升級後會靜默失效，且不一定出現錯誤訊息。這類依賴通常不會寫在文件裡，需要實際跑一次流程確認。

裝置碼授權改變的是登入路徑。透過 SSH 管理的主機過去多以環境變數保存長期憑證，改用裝置碼之後，憑證的發放與輪換流程需要一併規劃，否則容易退回舊做法。

多分頁工作區會改變記憶體曲線。每個側邊分頁持有獨立上下文，同時開啟多個分頁意味著更高的常駐用量；在記憶體受限的環境中，這個成本需要預先評估。

最後是版本鎖定。同日推出兩個穩定版的節奏，意味著團隊不宜長期停留在浮動版本。在正式環境採用固定版本並保留回退方案，比追求最新功能更符合維運現實。

出處連結有哪些？

專案原始碼與文件位於 https://github.com/openai/codex，版本紀錄與執行檔在同一倉庫的 Releases 頁面發佈。0.169.0 版的完整變更清單可於該頁對照前一版本查閱。

## 常見問題有哪些？ 常見問題集中在安裝方式、訂閱要求、專案信任與企業導入四類。以下依官方文件與版本紀錄整理，答案以 2026 年 11 月 13 日的倉庫狀態為準。 ### Codex CLI 是否必須付費才能使用？ 工具本身以 Apache-2.0 授權開源，但實際執行需要模型存取權限。官方建議以 ChatGPT 的付費方案登入，亦可以使用 API 金鑰，成本依用量計算。 ### 支援哪些作業系統？ 官方提供 macOS、Linux 與 Windows 的安裝路徑，包括 shell 與 PowerShell 安裝腳本、npm 與 Homebrew 套件，以及各平台的預編譯執行檔。 ### 側邊對話分頁與一般新開任務有何差別？ 分頁附屬於同一個工作區，可在主線旁邊並行追問並快速切換；新開任務則建立獨立的執行環境。分頁的側聊在重啟後可以回復。 ### 為何在未受信任目錄中專案設定不生效？ 專案設定與 MCP 伺服器來自儲存庫檔案，載入即等於讓專案內容影響執行環境。新版要求以 `--trust` 明確標記信任，設定才會被保存與載入。 ### 企業導入需要哪些前置條件？ 需要可用的身分驗證機制，包含支援裝置碼授權的網關設定。同時應規劃憑證輪換、版本鎖定與專案信任政策，並為沙箱與網路代理安排測試。

總結：哪些團隊適合升級到 0.169.0？

需要在本機或受管裝置執行編程代理、且要求權限邊界可稽核的團隊最適合。若只需單線任務，多分頁與 Cloud 連線帶來的效益有限，可先觀望。

0.169.0 版的改動沒有新增模型能力，重心落在並行工作的容納量與執行邊界。多分頁工作區與任務檢索處理的是長時間使用的組織問題，專案信任標記與執行邊界修補處理的則是採用門檻。

這種取向說明專案的階段。當工具從個人試用走向組織部署，版本更新的重心自然從功能清單轉向可維運性；星標規模、貢獻者數量與問題佇列的增長速度，亦支持這個判斷。

評估時值得先問一個問題：團隊目前卡住的是產出速度，還是稽核與合規。若是前者，分頁與檢索帶來的效率提升值得先試；若是後者，近幾個版本反覆出現的信任標記與沙箱修補，會比任何功能介紹都更值得細讀。
